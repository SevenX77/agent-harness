# 领域分析

目标：把非结构化的领域材料变成 skill 设计能直接消费的结构化框架，而不是一篇读后感。

## 流程
1. **通读材料**：用户粘贴的 + @mention 圈的 + 让用户 Read 指认的文件，先读全再动笔。
2. **抽结构化框架**，固定五层输出：
   - **实体**：领域里的名词及其属性（谁/什么，有哪些字段）。
   - **流程**：动作序列与分支（什么触发、什么顺序、哪里有判断点）。
   - **规则**：显式约束与隐含惯例（什么必须/禁止，边界条件）。
   - **术语表**：领域黑话 → 明确定义（后续 prompt 与 io 字段命名的依据）。
   - **未决问题**：材料没讲清、需要用户补充的点（列出来问，不要脑补）。
3. **映射到 skill 设计**：哪些流程段是确定性逻辑、哪些需要 agent 判断、根 io 的候选形状——直接为 graph-design 技能铺路。

## 外部第二视角（可选增强，按序降级）
分析复杂领域时，独立模型的第二意见能暴露盲区：
1. **本机装了 Antigravity CLI（`agy`）时**：可经 Bash（需用户审批）跑
   `agy --print "<聚焦的分析问题>"` 拿 Gemini 的独立分析，与你的结论交叉比对，分歧点显式列出。
2. **agy 不可用、但 Settings 配了可用的 Gemini 角色**：提示用户可在输入框的 role 选择器切到该角色再跑一轮对照。
3. **两者都没有**：直接用当前模型完成分析，并**明确告知**"本轮未使用外部分析器"——不静默降级。

## 反模式
- ❌ 输出散文式总结而不是五层框架。
- ❌ 材料没读全就开始抽框架。
- ❌ 把自己的行业常识当成材料里的事实混进去（区分"材料说的"与"我补充的"）。
- ❌ 未决问题自行脑补答案。
