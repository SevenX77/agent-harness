# 决议:编译缓存键必须覆盖编译真正读过的文件

- 日期:2026-08-15
- 范围:`packages/graph-agent/src/graph_agent/core/cache.py`
- 相关 PR:本决议同 PR 落地
- 触发:`story-deconstruction-v3-lab` 缺陷排查中,同一份坏树两次编译给出互相矛盾的答案

## 决策

`compute_cache_key` 的输入集合,从「`GRAPH.md` + `phases/**/*.md`」扩大为
「skill 根目录下所有非点目录中的 `.md` 与 `.py`」。

## 为什么这是正确性问题,不是性能调优

缓存键的作用是回答一个问题:**磁盘上这棵树,和上次编译的那棵树,是不是同一棵?**
键漏掉一个编译会读的文件,这个问题就被答错——编译器会把上一棵树的结论当作这一棵树的
结论返回。对使用者而言,现象不是"慢",而是**改了文件、编译说没问题、运行照样炸**。

方向性在这里是不对称的:

- 键**多**收一个文件:代价是一次本可省掉的重编译,结论仍然正确。
- 键**少**收一个文件:代价是一个错误的结论,且错得没有任何提示。

所以在拿不准的时候必须往多的一侧倒。这不是本仓的发明:ccache 用 depfile 把编译器
实际打开过的头文件全部记进键,Bazel 要求 action 显式声明全部输入并在沙箱里强制执行——
两者都把「输入集合不完备」定性为 correctness bug 而不是可调参数,原因正是上面这条
不对称。本次采用它们的取舍立场;它们更精确的做法(记录编译器实际读过的文件)本次没有
采用,原因见下面"已知遗留"。

## 实测证据(修复前)

被测对象:`D:/coding/skills/story-deconstruction-v3-lab`(133 个 `.md`,27 个 `.py`)。

| 观察 | 修复前 | 修复后 |
|---|---|---|
| 键里的 `.md` | 5 / 133 | 41 / 139(其余 98 个全部位于点目录内) |
| 键里的 `.py` | 0 / 27 | 27 / 27 |
| 破坏一个 subgraph 阶段后编译 | `issues=0`(答的是上一棵树) | `SkillLoadError`,7 条诊断 |
| 同样的破坏 + 改根 `GRAPH.md` mtime | `SkillLoadError`,7 条诊断 | 同左 |

修复前那两行是因果证据而不是巧合:第二次编译**内容完全没变**,只把根 `GRAPH.md` 的
mtime 往前推了 1 秒,答案就从"干净"翻成"7 条错"。唯一的差别是缓存键,所以缓存键就是
病因。

## 为什么点目录被排除

排除点目录不是为了整洁,三个目录各有各的实证理由:

- `.workspace/`:存的是 run / predict 的输出。编译从不读它,而每跑一次就重写一次——
  收进键会让缓存在每次运行后失效,缓存等于不存在。
- `.git/`:体积大到会让遍历本身成为主要开销,内容与编译无关。
- `__pycache__/`:是键已经覆盖的源码的镜像,mtime 随 import 变动而不是随编辑变动,
  收进它会带来虚假失效。

`.ah/`、`.claude/` 同形——写在 skill 旁边,编译器不读。

代价方面诚实说明:这次会把 `tests/test_mvp1_contract.py` 这类文件也收进键,它确实不是
编译输入。按上面的不对称原则,这属于可接受的一侧。

## 已知遗留(明确不装作已解决)

**从 skill 根目录之外链接进来的 subgraph 仍然不在键内。** 因为真实的读取集合只有编译
之后才知道;要覆盖它,需要 loader 上报自己实际读过哪些文件,并让 `CompiledSkill` 与
缓存快照把这份读取集合带上——那是另一次独立改动。本次把窟窿从「根目录下除
`GRAPH.md` 和 `phases/` 之外的一切」缩小到「只剩跨根链接」。

## 验收判据

`packages/graph-agent/tests/core/test_compile_cache_key_covers_inputs.py`:

1. 编辑嵌套 subgraph 的阶段文件 → 键必须变化;
2. 编辑 validator(`.py`)→ 键必须变化;
3. 在 `.workspace/` 里写入运行产物 → 键必须**不**变化(过度近似也有边界)。
