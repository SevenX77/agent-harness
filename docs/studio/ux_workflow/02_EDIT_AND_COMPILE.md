# Node 2: 编辑与编译 (Edit & Compile)

## 1. 业务目标
PM 在此节点将业务逻辑转化为严谨的 `graph_skill`。这个过程包含宏观的全局契约定义、中观的拓扑流转搭建、以及微观的节点类型与 Prompt 填充。系统通过实时的 Lint (Compile) 机制，强制保证上下文数据流的正确性，**编译是通往动态试飞的唯一通行证**。

## 2. 界面布局流派 (双线探索)
在进入具体的工作流之前，我们保留两种 UI 布局分支，以适应不同 PM 的操作偏好：

### 流派 A: Canvas-first (画布优先 / 蓝图模式)
- **视觉中心**: React Flow 拓扑图占据屏幕 80% 核心区。
- **操作心智**: PM 的眼睛始终跟着“流程节点”走。
- **交互方式**:
  - 全局与输入输出：通过点击画布上的特定虚拟节点（Global/Input/Output）在右侧滑出抽屉配置。
  - 节点编辑：双击画布上的某个 Phase，右侧（或覆盖层）滑出该节点的表单与局部 Monaco 编辑器（仅展示该节点的 Prompt）。
  - Copilot 始终悬浮在最右侧。

### 流派 B: VS-Code 式 (代码与画布分屏并重)
- **视觉中心**: 上下分屏（或左右分屏）。例如上方 70% 是全局的 Monaco 代码编辑器，下方 30% 是随动的拓扑可视化。
- **操作心智**: PM 的心智锚点是 `SKILL.md` 全文，图只是代码的倒影。
- **交互方式**: 
  - PM 直接在 1000 行的 Markdown/XML 中编写，下方的图实时刷新。
  - 点击图上的节点，代码区自动滚动跳转到对应的 `<phase>` 标签行。

## 3. PM 的高颗粒度工作流 (Macro -> Meso -> Micro)

在实际的技能开发中，PM 的操作顺序通常是三段式的：

### 3.1 宏观 (Macro)：全局基础与 I/O 契约定义
**核心理念：输入输出在视觉上也必须是“图”上的独立节点。**

1. **头部信息配置**: 配置 `name`, `description`, `type` (simple/graph)。
2. **起点 (Input Node)**: 
   - 确定技能的初始原料。
   - **Schema 自动推导**: PM 导入一个现成的测试文件（如一段包含 `scene_id` 和 `text` 的 JSON），系统自动推导出 `io.inputs` 的 Schema 结构。
   - **Copilot 辅助**: 如果没有现成文件，PM 必须在右侧和 Copilot 讨论明确输入结构。如果这里留空，系统标红。
   - 定义 `context_mapping`，将 Input 数据映射到画布的第一块黑板上。
3. **终点 (Output Node)**:
   - 明确技能跑完后必须交出的产物（Schema）。

### 3.2 中观 (Meso)：拓扑搭建与 Subgraph 展开
确立起点和终点后，PM 开始在中间画节点。

1. **节点连线 (Topology)**: 通过声明 `depends_on` 建立串并行关系。
2. **处理 Subgraph (子图)**: 
   - 当某个节点是另一个复杂的 `SKILL.md` 时，交互上必须提供**两种兼容的模式**：
     - **树状展开 (Inline Expand)**: 在当前主画布中直接将子图的拓扑展开，方便 PM 在全局上下文中查阅脉络。
     - **下钻专注 (Drill-down)**: 双击节点直接进入子图的独立画布进行沉浸式编辑。界面顶部必须提供**面包屑 (Breadcrumbs)** 或 `[ ← 返回上一层 ]` 按钮，保证导航不迷失。
   - **数据桥接 (Context Bridge)**: 对于嵌入的子图，输入输出大部分由系统自动推导和绑定。但如果某个节点需要产出特殊的 Artifact（比如直接落盘一张图片，而不是传给下一个节点），PM 可以在 Bridge 属性中单独设定。

### 3.3 微观 (Micro)：节点类型决策与填充
双击某个具体节点，进入最核心的 Body 编写。PM 必须先决定该节点的**类型**，这决定了接下来填什么表单：

#### 类型 A: Agent-Loop 节点 (交由智能大模型)
- **角色 (Tier)**: 下拉选择（fast, balanced, creative 等）。
- **Prompt (核心)**: 在 Monaco 中编写 `<system_prompt>` 和 `<user_prompt_builder>`。
- **挂载依赖**: 
  - **静态知识**: 绑定 `references/` 下的规则文件。
  - **动态能力**: 挂载 Python `tools` 列表，或者挂载 `sub_skills` 让大模型自己决定是否调用。
- **数据结构 (Data Architecture)**: 声明该节点期望的数据边界和约束。
- **控制逻辑 (Control)**: 配置重试上限 (`max_retries`)、偏航提醒上限 (`max_nudges`)，以及最重要的 **质检器 (`validator`)** 及其失败后的 **`retry_target`**。

#### 类型 B: Subgraph 节点 (委派给成熟子流程)
- 仅需配置被引用子图的路径，以及上文提到的 `context_bridge`。

#### 类型 C: Code-only 节点 (纯确定性计算)
- 不写 Prompt，不消耗 LLM。仅顺序配置 Python 工具函数列表。

### 3.4 严酷的交通警察：实时 Compile
在上述操作的每一秒，后台 Compile 都在执行。
- **严格匹配**: 如果 PM 在 Phase 2 的 Prompt 里写了使用变量 `{xxx}`，但前置节点的 Schema 根本没产出这个字段，系统会立刻在两个节点之间打上**红叉**。
- 只有整张图没有任何数据断层、没有语法错误时，**Compile 绿灯亮起，右下角的 `[ Predict ]` 按钮才会从灰色解锁，允许进入下一环节。**
