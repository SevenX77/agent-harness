# 需求挖掘 → 设计 → 文档 框架 (Design Process Framework)

> **用途**: 复用型框架。任何"从模糊需求到可落地设计文档"的工作都按此推进。源自 Skill Studio 重组 (2026-06), 适用于任何 feature/重构的设计阶段。
> **核心理念**: 设计的真相(含**模块间接口契约**) + 它的依据(用户原话)必须**永久留底**、**自包含**(主体内容写进本文, 不靠引用临时文档代替)、**唯一真相源**; 过程可临时, 结论不可丢。

---

## 1. 四阶段循环 (一个 part 一个 part 走)

把大需求切成"part"(一个工作流节点 / 一个能力 / 一个机制), 每个 part 走一遍这四步:

### Phase 1 — 挖掘 (Discovery)
- **核实优先 (verify-before-asking)**: 动手前先读代码 / spec / 文档, 把能自查的查完, 结论带证据 (file:line)。不凭印象、不拿子 agent 转述当事实。
- **现状/数据优先**: 先看真实代码现状、真实数据样本, 再设计——不先造框架再找数据。
- **开放式提问**: 把"需要人类判断的取舍"整理成**表格**(项 | 选项 | 我的建议), 一次说清; 不没头没尾、不默认用户读过代码。
- **区分 verify vs judge**: 事实性问题(现状/配置/实现与否)自己查; 只有价值判断 / 业务意图 / 优先级才问用户。

### Phase 2 — 记录 (Capture, 当轮落盘)
- **原话留底 (铁律)**: 用户的设计阐述——尤其**举例、机制描述、流程推演**——逐字记录, 不用提炼替代。这些是设计决策的隐含依据。
- **决策 + 动机**: 每个决策记"选了什么 + 为什么"。
- **落盘归属**: 工作过程 → 工作日志(可临时); **最终设计 + 原话依据 → 永久设计文档**(见 §4 永久 vs 临时)。

### Phase 3 — 组织 + 查缺补漏 (Organize + Gap-find)
- 把用户的零散描述组织成清晰机制: **状态机 / 时序 / 表格**。
- **钉死接口契约**: 把跨模块/跨层边界的契约(签名·数据 schema·错误·归属)定稿, 在任何模块动工前确定。详见 §3。
- **复述确认**: 用自己的话复述一遍(尤其复杂机制), 让用户确认"理解没歪"。
- **查缺补漏**: 列出未决 gap + 与现有代码/引擎能力的冲突(如"引擎无此原语")。

### Phase 4 — 定稿文档 (SSOT doc → 永久区)
- 写进永久设计文档, 按 §2 模板。
- 跨 part / 交叉功能**双向互相链接**(A↔B 两侧都登记依赖, 不是单向; 防认知丢失、防各设计各的)。详见 §3.5。

## 2. 设计文档模板 (每份永久设计文档必含)

> 下面是**必含元素**(不是死板章节顺序): 定义 · 接口契约 · 数据流/机制 · 决策+动机 · 设计决策基础(原话) · 测试关键点 · 涉及 region/platform · gaps · 交叉引用。
> **组织方式按模块复杂度二选一**(详见 §2.2): **多功能模块(大多数 capability / region)→ 逐功能为索引**(默认); 单一机制 → 章节式。两者都必须覆盖下列元素, 区别只在"按功能收齐"还是"按章节分列"。

```
# <能力 / 机制名>
> Tier / Owns(一句话边界) / Status / Related(交叉链接)
- 定义               — 一句话:它是什么、管什么
- 接口契约           — 跨边界的签名+schema+错误+归属(模块级, 详见框架 §3)
- 数据流 / 机制       — 状态机 / 时序 / 上下游
- 决策 + 动机         — 选了什么 + 为什么(对比被否决做法)
- 设计决策基础(原话)  — 原话留底, 永久
- 测试关键点          — 每个关键决策"测试时必须验证什么"(防漏)
- 涉及 region / platform
- gaps / 待设计
- 交叉引用(双向 [[link]], 不复制)
```
> ⚠️ **决策 / 原话 / 测试这三项不是各自独立的章节** —— 多功能模块里它们**跟着各自的功能走**(见 §2.2), **绝不**把全模块的决策塞一段、原话塞一段、测试塞一段(= 总结文反模式, 见 §6)。

### 三条硬性栏目(本框架强调, 最易漏)
- **接口契约(模板 ##3)**: 跨模块/跨层边界的契约**单独成段**写清(签名·数据 schema·错误·归属·稳定性)——不能混在"数据流/机制"里。详见 §3。
- **设计决策基础·原话(模板 ##4)**: 关键决策背后的用户原话**全量写进本永久文档**(不能只留工作日志)。
- **测试关键点(模板 ##6)**: 每个关键业务决策标注"测试时必须验证什么"——防止写测试时漏掉关键业务逻辑。例: golden 失效规则 → 测"改 prompt 不失效 / 改 output schema 缺字段触发编译错误"。

### 2.1 文件架构(模块 = 文件夹; baseline 对齐代码 + alignment 对齐目标)

- **一个模块 = 一个文件夹**(如 `docs/.../mvp1/02-orch-role-resolution/`)。
- 文件夹内**两份文档, 职责二分**:
  - **`baseline.md` — 对齐代码现状**: 当前源码怎么跑(覆盖代码 + `file:line` + 编号执行流程 + 现状 gap), 只描述"现在是什么"。是 brownfield 改造的起点基线。
  - **`<里程碑>-alignment.md`(如 `mvp1-alignment.md`)— 对齐目标设计**: 覆盖 §2 必含元素 + 三硬栏, **按 §2.2 组织(多功能模块逐功能为索引)**, 写"目标 + 决策 + 接口契约 + 原话 + 测试关键点 + gaps"。是永久设计文档主体。
- **两份配套, 互链不复制**: alignment 的 ##2 数据流/机制**引 baseline 现状**(不照抄); baseline 在反转 / 关键处**指回 alignment 的 ##4/##5**(决策依据)。
- **新建模块**(目标代码尚不存在): baseline 也要诚实声明"现源码不存在 / 职责暂由谁代管", 不能凭空捏造现状。

### 2.2 正文组织: 逐功能为索引 (多功能模块默认; 最易写歪)

> **铁律(PM 2026-06-03)**: 一个模块若含多个功能(大多数 capability / region 都是), `alignment.md` 正文**以每个功能为索引**, **绝不写成按章节归纳的总结文**(把所有功能的决策塞一段、原话塞一段、测试塞一段)。

- **模块级(只这两块)**: 「定义」(它是什么、管什么) + 「接口契约」(跨功能共享的边界契约, 框架 §3)。
- **逐功能(正文主体)**: 每个功能(F1 / F2 / …)**一段**, 段内**就地**收齐该功能的: **机制/数据流 · 决策+动机 · 原话 · 测试点 · status · 归属(region/platform)**。一个功能的全部信息在它自己段里, 不散到别处。
- **为什么**: 总结文把一个功能的决策/原话/测试拆到三个章节, 读者要跳着拼、改一处漏一处; 逐功能则**一段看全、一段改全**。

**逐功能骨架**:
```
# <能力名>
> Tier / Owns / Status / Related
## 定义
## 接口契约               ← 模块级, 跨功能共享 (框架 §3)
## 功能逐项
### F1 <功能名>
  - 机制/数据流 · 决策+动机 · 原话 · 测试点 · status · 归属
### F2 <功能名>  …
## gaps / 待设计
## 交叉引用 (双向 [[link]])
```

**范例(照它写)**: [`docs/studio/mvp1/02_capabilities/copilot-assist/mvp1-alignment.md`](studio/mvp1/02_capabilities/copilot-assist/mvp1-alignment.md) —— 「定义」+「接口契约」模块级, 然后 F1 对话流式 / F2 多 session / F3 领域脑子 / … / F8 生命周期 **逐功能**, 每段自带机制·决策·原话·测试·status·归属; 配套 baseline 见同目录 [`baseline.md`](studio/mvp1/02_capabilities/copilot-assist/baseline.md)。

## 3. 接口契约 (Interface Contract) — 单独模块, 必写

> **第一性原理**: 模块的 bug 绝大多数不在模块内部, 而在**边界**上——上游输出的形状, 和下游假设的形状对不上。接口契约若不在**设计期**钉死, 每个模块(每个 AI / 每个人)会各自脑补一份契约, 写完才在集成时发现对不上 → 返工。所以接口必须**先于实现确定**, 且**独立成章**——混进"数据流/机制"里就会找不到、审不动、改字段漏改下游。

### 3.1 一条接口契约必须钉死的七项

每一条**跨模块 / 跨层 / 跨进程**边界, 都要写清这七项:

| 项 | 内容 | 备注 |
|---|---|---|
| **签名 (signature)** | 函数名 + 参数(名·类型·必填/可选) + 返回类型 | 服务边界 = endpoint + method + request/response |
| **数据契约 (schema)** | 跨边界数据结构: 字段名·类型·嵌套·必填可选·枚举 | 枚举用 discriminated union, 不要 stringly-typed |
| **方向 + 归属** | 谁 producer 谁 consumer; 契约 owner 是哪侧 | owner 改契约 → 负责通知全部 consumer |
| **错误契约** | 哪些错误跨边界 · 错误码/形状 · 失败语义 | 抛异常 / 返回 error 值 / 降级, 三选一写明; 对接 error-code spec |
| **不变量·前后置** | 调用前必须为真什么, 调用后保证什么 | 例: 前置 workspace 已初始化; 后置 state 已落盘 |
| **稳定性·版本** | 哪些字段 FROZEN(改即全链路同步), 哪些可扩展 | 接口演进 / 向后兼容策略 |
| **SSOT 落点** | 契约权威源在哪(类型文件 / FROZEN spec / proto) | 设计文档只写形状+归属+稳定性, 字段级定义**链接不复制**(见 §5) |

### 3.2 落点: 自有接口 vs 共享接口

- **模块自有接口** → 写进该模块设计文档的 **模板 ##3 接口契约**段。
- **跨模块 / 共享接口**(平台层: IPC、event-bus、gateway、错误码等被多个模块依赖的契约) → **独立成一份接口文档**, 作为该契约的 **SSOT**; 所有 consumer 的设计文档**只链接, 不复制**(见 §5)。
- **真实样例**: [`ipc-bridge-baseline.md` 的 `## API` 段](studio/mvp0/03_platform/state-engine/ipc-bridge-baseline.md)——Rust 命令签名 + 前端 command union + data model schema + 错误形状 + 能力 gap 表 + `file:line` 全齐, 这就是一条接口契约写到位的样子。

### 3.3 写法模板(填进设计文档 ##3 段)

```
## 接口契约
### <边界名>: <Producer> → <Consumer>
- 签名:     `fn name(arg: Type, *, opt?: Type) -> Result<Out, Err>`   (src/...:NN)
- 数据契约:  见下表 / 链接 FROZEN spec `docs/.../xxx-spec.md#anchor`
- 方向·归属: producer=X, consumer=Y, owner=X
- 错误契约:  `Err = {code: Literal[...], detail: str}`; 失败时 <抛/返回/降级>
- 不变量:    前置 <…> / 后置 <…>
- 稳定性:    FROZEN=[字段…]; 可扩展=[字段…]
- SSOT 落点: <类型文件 file:line / spec 链接>
- 测试关键点: <改 X 必须触发 Y>(同步进模板 ##6)

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
```

### 3.4 何时钉 + 和测试联动

- **闸门**: 接口契约在 **Phase 3 组织 / Phase 4 定稿**钉死, 在**任何模块动工前**确定。接口没钉死 = 还没到执行阶段。多模块 / 多 AI 并行开发时, 共享接口契约就是它们唯一的对齐基线。
- **联动测试关键点(模板 ##6)**: 每条契约落一条测试点——producer 输出的 shape 是否被 consumer 正确消费? 改字段后所有 (de)serialization 点是否同步? 对应 code-review 的 data-flow tracing(从入口到出口逐段验字段名/类型/嵌套一致)。

### 3.5 模块边界模糊 / 交叉时: 双向引用防冲突

> **场景**: 功能复杂到模块**不好切、互相交叉**(一个行为横跨多个组件, 模块间多对多)。这时 3.1 的"方向 + 归属"本身就分不清——没有干净的 producer→consumer。**最大的坑: 两份设计各自描述同一个交叉点 → 两份互相矛盾。**(studio 旧体系实况: `canvas-topology` 与 `trace-inspector` 两份文档都去写 `ContextEdge → Properties 面板` 的实现 → 打架。)

防冲突三件套(studio 三维治理总纲 [`docs/studio/INDEX.md`](studio/INDEX.md) 已验证):

1. **所有权不变量(谁拥有谁写实现)**: 每个交叉点 / 事实**只指定一处 owner 写实现**, 其余位置**只链接、不重述**(即 §5 SSOT 落到交叉场景)。owner 凭"这事实最贴谁的职责"判定(组件实现归 UI 文档, 跨组件数据流归能力文档)。—— 缺这条, 光有双向链接两边照样各写各的。
2. **双向引用(A↔B 互指, 不是单向)**: 正向登记"我用到谁"(`能力→区域: 在 X 渲染`), 反向登记"我被谁用"(`区域→能力: 本区域承载 Y`; `平台→能力: 被哪些能力依赖`)。两侧都登记 = 任一侧一改, 对端立刻可见, 不会各改各的、漏掉对方。
3. **正交分轴, 不硬塞成一棵树**: 边界天然多对多时, 拆成几条**正交轴**做成"互相链接的独立树"(studio: 旅程 × 能力 × UI 区域, 两两多对多), 每条轴只回答一个独立问题, 轴间靠双向链接挂接, 不互相嵌套。

**落点**: 复杂 / 交叉系统**先立治理总纲**(定义轴 + 所有权不变量 + 唯一词表 / 注册表), 再写各模块文档; 模块之间靠双向链接对齐, 而非各写各的。

## 4. 永久 vs 临时 (durability 铁律)

| 类别 | 位置 | 寿命 |
|---|---|---|
| 最终设计 + 接口契约 + 原话依据 + 测试关键点 | **永久设计区**(如 `docs/studio/mvp1/`) | 永久 |
| 工作日志(逐轮决策流水 + 原话流水) | 工作区(如 `_reorg/alignment-notes.md`) | 工作期, 完成后可归档/清理 |

**铁律**: 任何设计关键的内容(尤其接口契约、原话依据)**不能只活在工作区/临时文档**。工作日志可清, 所以定稿时必须把"设计 + 接口契约 + 原话依据 + 测试关键点"迁进永久设计文档。

## 5. 唯一真相源 (SSOT, 防 drift)

- 一个事实只在**一处权威源**写实现(字段/接口定义 → FROZEN spec 或类型文件; 决策 → 决策日志→定稿迁永久; UI 组件 → region 文档)。
- 其余位置**只链接, 不复制**。复制 = 多份会漂移、互相打架(已踩过的坑)。
- 采信任何文档前先问"它过时了吗?", 交叉验证: spec + 代码 + git。

### 5.1 引用规范(只引稳定源; 临时文档内容写进正式文档)

- **引用对象白名单**: 只能引 ① 代码 `file:line` ② 正式 docs(永久设计区 `docs/.../mvp1/`、FROZEN spec) ③ 同体系其他 mvp 模块 `[[link]]`。
- **绝不引临时任务文档**: `.kiro/specs/...`、`temp/...`、工作日志**会被删**——引它们 = 临时文档一删, 正式文档就断链 / 丢决策。**临时文档(`.kiro` spec 等)里的决策 / 原话, 定稿时完整写进正式文档, 不留路径引用。**
- **scope 内主体自写, 引用只作线索证据**: 本模块 scope 内该写的主体(决策逻辑 / 原话 / 机制)**完整写进本模块**; 引用只能作线索 / 证据补充(如 `file:line` 佐证), **不能用一句"见 xxx"引用代替主体内容**。
- **跨模块引正式 mvp 文档 + 双向**: 引别的模块只引它的 **mvp 设计文档**(不是 kiro); 跨模块共享内容**重复写没关系**, 但两侧加双向 `[[link]]` 索引互相验证、防 drift(见 §3.5)。

## 6. 反模式 (本项目踩过的)

- ❌ 过度复杂化: 把"配置项"当成"独立设计议题"列一堆伪问题(predict 的 input/validate/batch 曾被错当独立议题)。
- ❌ 没头没尾抛术语: 默认用户读过代码 → 用户看不懂、浪费时间。
- ❌ 原话只留工作区: 设计依据随临时文档被清掉。
- ❌ 字段/契约多处复制: 漂移、矛盾。
- ❌ 接口埋在实现里/脑子里: 没在设计期钉死契约 → 各模块各自脑补, 集成才发现对不上。
- ❌ 接口和内部机制混写: 边界契约塞进"数据流/机制"段 → 找不到、审不动、改字段漏改 consumer。
- ❌ 只写 happy-path 签名: 不定义错误契约/失败语义 → 下游到处 try/except 乱兜底。
- ❌ 交叉模块各写各的: 两份设计描述同一交叉点 → 互相矛盾(studio 旧体系 canvas / trace 争抢 `ContextEdge→Properties` 的实况); 缺所有权不变量 + 双向引用。
- ❌ 引临时任务文档: 设计文档引 `.kiro` / `temp` / 工作日志 → 临时文档一删就断链、丢决策(临时内容应完整写进正式文档, 见 §5.1)。
- ❌ 用引用代替主体: scope 内该自己写的主体内容, 只甩一句"见 xxx" → 主体空心、读者被迫跳外部文件(引用只作线索证据)。
