## 1. 先给结论

当前 V2.1 engine 的真实模型，是“按 GRAPH.md 图纸跑一条流水线”。

用户把输入交给 `run_skill()`，engine 把这些输入放到一块共享业务黑板 `data` 上。

然后每个 phase 节点按图纸顺序跑。

LOGIC 节点直接读黑板，算出 delta，再把 delta 合回黑板。

SKILL 节点让大模型看 prompt、调工具、最后按 `finish_task` 交卷，engine 把交卷结果放回黑板。

SUBGRAPH 节点会启动另一条完整小流水线，再把小流水线产生的 delta 合回父黑板。

subagent 看起来像工具，背后也会启动子 skill，但结果先回到父大模型，不会自动写父图黑板。

MVP0 的 18 个 Q，本质是在问四件大事。

第一，编译阶段要不要让每个 phase 先把“我要读什么、我要写什么”讲清楚。

第二，运行时要不要把共享黑板切成更干净的格子，让每个节点只看到自己该看的数据。

第三，真正执行时，大模型、子图、子代理、错误这些运行细节要怎么补齐。

第四，Studio 以后要怎么看到这条流水线每一步到底发生了什么。

如果这 18 个 Q 都按 a2 当前推荐路线拍完，engine 会从今天的：

- 外部输入基本原样进 `data`。
- 每个 phase 大多能看全局黑板。
- 顺序覆盖同名 key 会被误判成冲突。
- SKILL phase 没有真实模型解析就会直接挂。
- exit contract 会在对话历史里重复堆积。
- callbacks / trace 没有真正接回 V2.1 主线。

变成后面的：

- 编译时就知道每个 phase 大概要读写哪些字段。
- 运行入口先把输入过漏斗，只放行数据说明书里声明过的字段。
- 每个 phase 只拿自己的局部输入切片。
- phase 输出进入更清楚的分区，顺序更新和并行冲突能区分。
- 子图和 subagent 不再偷偷继承父黑板全集，只能靠明确输入跨边界。
- 大模型由外层或 engine 解析出真实模型，不再只靠 mock。
- 大模型每轮的临时交卷规则不再污染历史消息。
- 错误从自由文本变成前端能读懂的错误码。
- 每个节点开始、结束、模型调用、工具调用、子代理进入退出、异常，都能被 trace 记录。

一句话：

> 当前 engine 是“大家共用一块黑板，各自自觉读写”；MVP0 想改成“每个节点按授权拿材料、交成果，飞行记录仪把每一步记下来”。

## 3. Block 1: skill-compilation (3 个 Q)

### 3.0 这块在 engine 哪里，现在怎么跑

Block 1 管的是“开跑前，engine 能不能读懂这份 skill 目录”。

今天的流程是：

- 用户给 engine 一个 skill 目录。
- engine 先找 `GRAPH.md`。
- engine 读根输入和根输出的数据说明书。
- engine 找每个 phase 节点。
- engine 检查图纸有没有环、有没有孤岛、有没有缺文件。
- engine 加载 LOGIC 的 action。
- engine 加载 SKILL 的 tools。
- engine 编译 subagent 信息。
- 编译成功后，把这份“已经读懂的图纸”交给 runtime 去跑。

人话：

> Block 1 不是跑任务，而是验图纸。

今天它已经能验“图纸结构”。

比如：

- 有没有根图纸。
- phase 目录在不在。
- phase 依赖顺序是不是合法。
- 根输入/输出的数据说明书是不是合法 JSON。
- LOGIC 节点写出的顶层 key 有没有超出根输出范围。

但它还没有真正验“每个 phase 自己要读什么、写什么”。

所以今天会出现这种情况：

- 图纸上写了 phase A 先跑，phase B 后跑。
- 编译器知道 A 在 B 前面。
- 但编译器不知道 A 产不产 `clean_text`。
- 编译器也不知道 B 是不是必须读 `clean_text`。
- 如果 B 跑起来才发现没有这个字段，那就是运行时才爆。

Block 1 的 3 个 Q，就围绕这件事。

第一，每个 phase 要不要在自己的文件头写 `io`。

这里的 `io` 可以先理解成“这个节点的读写说明”。

第二，编译器要不要沿着图纸检查“后面的节点要读的字段，前面到底有没有人写”。

第三，编译报错要不要变成 Studio 能定位的结构化问题，而不是只有一行自由文本。

### 3.1 Q-A7: io frontmatter 走哪条路

**现在 engine 怎么跑**

今天 phase 节点文件里，LOGIC 大多只写自己调用哪个 action，SKILL 大多只写 system prompt、交卷规则、tools 和 subagents。

它们没有稳定写“我这个节点要读哪些字段、要交哪些字段”。

所以 engine 只知道“这个节点在图纸上的位置”，不知道“这个节点的数据边界”。

人话：

> 今天 phase 像一个工位，但工位门口没有贴“我需要什么材料、我会产出什么零件”的牌子。

**候选 A**

候选 A 是硬强制。

拍了 A 以后，每个 LOGIC 和 SKILL phase 文件都必须写自己的 `io` 说明。

如果没写，编译直接失败。

现实表现：

- PM 写新 skill 时，每个 phase 文件头部都要补一段读写说明。
- 老 fixture 里没写这段的，马上全部红。
- 好处是后面的 Q-A8 和 Block 2 有可靠依据：每个节点都必须先报清楚读写范围。
- 代价是迁移会非常硬，现有四套 V2.1 fixture 都要补。

候选 A 更像：

> 所有工位今天起必须贴材料清单，不贴不准开工。

**候选 B**

候选 B 是软兼容。

拍了 B 以后，phase 可以写 `io`，也可以不写。

没写也不报错、不报警，engine 照常编译。

现实表现：

- 现有 fixture 不会被打断。
- 新 skill 可以慢慢补写。
- 但后面的数据流检查会遇到空白：节点自己没说要读写什么，编译器就没法证明数据有没有接上。

候选 B 更像：

> 工位可以贴材料清单，但不贴也没事。

**候选 C**

候选 C 是中间路径。

拍了 C 以后，phase 的 `io` 先不是硬必填。

没写不会立刻让编译失败。

但 engine 会发出比较重的编译 warning，提醒这份节点以后必须补。

现实表现：

- 老 fixture 暂时还能跑。
- 新工作会被 warning 催着补 `io`。
- 下一个里程碑可以把 warning 升级成真正失败。
- 后面的 Q-A8 可以先在有 `io` 的节点上做检查，缺 `io` 的节点先标出来。

候选 C 更像：

> 工位暂时可以不贴材料清单，但门口会挂黄牌，下一轮不补就不准开工。

**a2 推荐**

a2 推荐候选 C。

a2 的理由是：现在直接硬强制会把测试资产大面积打红；先用强 warning 推着大家补，风险更可控。

**PM 你拍的影响**

拍 A，是把数据边界一次性立起来，但要接受现有文件批量迁移。

拍 C，是先保运行，再逐步把数据边界补齐。

拍 B，是最不打扰当前资产，但后面的强数据治理会缺依据。

**跳源 verify:** `.kiro/specs/engine-mvp0-skill-compilation/design.md:78`

### 3.2 Q-A8: 编译期数据流检查做到多深

**现在 engine 怎么跑**

今天 engine 会检查 phase 的执行顺序。

它知道：

- 谁先跑。
- 谁后跑。
- 有没有环。
- 有没有孤岛。

但它不知道：

- 后面的节点要读 `clean_text`。
- 前面的节点有没有写 `clean_text`。
- 上游写的是文本，下游要的是数字。

人话：

> 今天 engine 会检查流水线站位有没有排错，但不会检查材料有没有真的传到下一个工位。

**候选 A**

候选 A 只做 key 可见性检查。

也就是先不深究字段类型，只看名字能不能接上。

例子：

- 根输入里有 `text`。
- prepare phase 声明输出 `clean_text`。
- analyze phase 声明需要 `clean_text`。
- 编译器沿着图纸走一遍，确认 analyze 之前确实有人产出 `clean_text`。

如果 analyze 声明需要 `clean_text`，但前面没人写，编译期就报。

现实表现：

- 能拦住最常见的“忘了接字段”。
- 实现轻。
- 运行前就能发现很多错。
- 但不会判断“这个字段类型是不是刚好兼容”。

候选 A 更像：

> 先检查每个工位要的材料名字，前面有没有人准备。

**候选 B**

候选 B 做更深的类型兼容检查。

不只看有没有 `count`，还要看上游产出的 `count` 是不是下游要的那种形状。

现实表现：

- 能挡更多错。
- 但判断成本高。
- 容易遇到复杂数据说明书造成误报。
- MVP0 会多很多实现负担。

候选 B 更像：

> 不只检查材料有没有，还要检查材料规格、尺寸、形状都完全对得上。

**a2 推荐**

a2 推荐候选 A。

a2 的理由是：MVP0 先拦字段缺失就能挡住大部分断流问题；类型深推可以留到后面。

**PM 你拍的影响**

拍 A，engine 会先变成“字段名字能接上”的轻量检查器。

拍 B，engine 会变成更严格的数据说明书检查器，但实现和误报成本都更高。

**跳源 verify:** `.kiro/specs/engine-mvp0-skill-compilation/design.md:97`

### 3.3 Q-ISSUE: 编译错误怎么给 Studio 看

**现在 engine 怎么跑**

今天编译失败时，engine 多数是抛一个带文字前缀的错误。

开发者看日志能懂大概哪里错。

但 Studio 很难稳定知道：

- 哪个 phase 错。
- 哪个字段缺。
- 哪个文件。
- 哪一行。
- 严重程度是什么。

人话：

> 今天 engine 像在对人喊“这里坏了”，但没给 Studio 一张可定位的维修单。

**候选 A**

候选 A 是改编译入口的返回方式。

拍了 A 以后，编译不再只是“成功给图纸，失败抛错”。

它会返回一个更像“编译结果包”的东西，里面同时有：

- 编译产物。
- warning。
- error。
- 每个问题的位置。

现实表现：

- 这像标准编译器。
- Studio 读取最舒服。
- 但所有现在调用编译入口的地方都要跟着改。
- runtime、测试、工具脚本都会被牵动。

候选 A 更像：

> 以后验图纸不再只说“过/不过”，而是交一份完整验收报告。

**候选 B**

候选 B 是保留今天的主流程。

成功时仍然直接返回编译产物。

失败时仍然抛异常。

但异常里面多挂一份结构化问题列表。

现实表现：

- 大部分调用方不用改。
- Studio 或后端想要结构化问题时，可以抓异常，再取里面的问题列表。
- 不会马上打乱 runtime。
- 代价是“warning 当正常结果返回”的能力没候选 A 那么自然。

候选 B 更像：

> 还是按老方式说“不过”，但这次把维修单夹在错误里。

**a2 推荐**

a2 推荐候选 B。

a2 的理由是：现在 runtime 还没稳定，不要过早改掉编译入口的调用方式。

**PM 你拍的影响**

拍 A，是一次性把编译系统改成更标准的报告式返回，但牵动很大。

拍 B，是先让错误可被 Studio 定位，同时保住现有调用路径。

**跳源 verify:** `.kiro/specs/engine-mvp0-skill-compilation/design.md:117`

## 4. Block 2: state-and-io-contract (5 个 Q)

### 4.0 这块在 engine 哪里，现在怎么跑

Block 2 管的是“运行时黑板怎么管、输入怎么进、每个节点能看什么、子图边界怎么隔离”。

今天 V2.1 的核心黑板是 `data`。

用户传进 `run_skill()` 的参数，基本会直接变成初始 `data`。

后面每个 phase 节点大多能读这块全局黑板。

LOGIC 节点拿到一份黑板副本，通过 Context 读写，再把 delta 合回去。

SUBGRAPH 节点会把父图全量 data 给子图。

subagent 子图也会拿“父图全量 data + LLM 传入的 input”作为初始 data。

这带来五类问题。

第一，当前合并器太死板。

它看到同名 key 就报冲突。

这能拦并行分支撞车，但也会误伤正常顺序覆盖。

第二，外部输入没有入场检查。

你传什么 keyword，基本都会进 data。

第三，每个 phase 没有局部输入沙箱。

一个节点理论上能看见整块黑板。

第四，SUBGRAPH 和 subagent 的父子边界太松。

子图很容易偷看或误改父图数据。

第五，需要一个专门的“黑板分发员”。

它负责从全局黑板里切出这个 phase 该看的输入，也负责把 phase 的输出放回正确位置。

Block 2 的 5 个 Q，就是围绕这五件事。

### 4.1 Q-S-P0-3: 顺序覆盖和并行冲突怎么区分

**现在 engine 怎么跑**

今天 `data` 的合并器看到同一个顶层 key 被写两次，就会报冲突。

这本来是为了保护并行分支。

例子：

- branch_a 写 `summary`。
- branch_b 也写 `summary`。
- 两个分支同时回来，engine 不知道该信谁，所以报冲突。

这个保护是对的。

但今天的问题是，顺序更新也会被误伤。

例子：

- prepare 先写 `status = draft`。
- review 后写 `status = approved`。
- 这是合理的后一步更新前一步。
- 但当前合并器仍可能把它当冲突。

人话：

> 今天黑板管理员只看到“有人写了同一个格子”，分不清是两个人同时抢格子，还是后一步正常改前一步。

**候选 A**

候选 A 是换成更聪明的合并器。

它允许先后顺序里的同名覆盖。

但并行分支同一时刻写同名 key，仍然拦住。

现实表现：

- 顺序流水线可以更新同一个字段。
- 并行 fan-in 撞同一个字段继续报。
- 对今天的写法影响较小。
- 但要让合并器知道“这是同一步并行，还是前后步骤”。

候选 A 更像：

> 黑板管理员开始看时间线：后一步改前一步可以，同时两个人抢同一格不行。

**候选 B**

候选 B 是引入 `phase_outputs` 这种输出分区。

每个 phase 的结果放到自己的格子里。

例如：

- prepare 的输出放 prepare 格。
- analyze 的输出放 analyze 格。
- assemble 的输出放 assemble 格。

这样顶层 key 不容易撞。

现实表现：

- 从根上减少冲突。
- 数据来源更清楚。
- 但现有 action / prompt / 后续读取方式要改。
- 原来直接读 `summary` 的地方，可能要改成读某个 phase 的 summary。

候选 B 更像：

> 不再让所有人往同一张大黑板顶层写，而是每个工位有自己的提交栏。

**候选 C**

候选 C 是 A + B。

短期先用聪明合并器解决顺序覆盖误伤。

同时引入 phase 输出分区，为后面更清楚的数据流做准备。

现实表现：

- 旧写法不会一下子全部翻掉。
- 新写法逐步走向“每个节点有自己的输出格”。
- 后面的 StateMapper 和 trace 也更容易知道数据来源。

**a2 推荐**

a2 推荐候选 C。

a2 的理由是：它同时解决眼前的顺序覆盖问题，也给未来的黑板分区留路。

**PM 你拍的影响**

拍 A，主要修当前冲突误伤。

拍 B，主要改数据存放模型，迁移更大。

拍 C，是先止痛再铺路。

**跳源 verify:** `.kiro/specs/engine-mvp0-state-io-contract/design.md:45`

### 4.2 Q-S-A1: Runtime Input Funnel 要不要严格

**现在 engine 怎么跑**

今天用户调用 `run_skill(root, text="hello", debug_token="xxx")`。

engine 基本会把这些 keyword 全部放进 data。

它不会先按根输入说明书过滤。

也不会稳定检查：

- required 字段有没有缺。
- 字段类型是不是对。
- 未声明字段要不要丢。
- 默认值要不要补。

人话：

> 今天入口像一个敞开的大门，谁带什么包都能进黑板。

**候选 A**

候选 A 是显式输入漏斗。

拍了 A 以后，外部输入先进漏斗。

漏斗按根输入说明书检查。

现实表现：

- 声明过的字段才进黑板。
- 缺 required 字段会在开跑前报。
- 明显错类型会在开跑前报或被安全转换。
- 未声明字段按 PM 选的严格度丢弃或拒绝。

例子：

- 说明书只允许 `text`。
- 调用方多传 `debug_token`。
- 候选 A 下，这个字段不会再悄悄进入整张图。

候选 A 更像：

> 进流水线前先过安检，只把任务需要的材料放进托盘。

**候选 B**

候选 B 是把老版输入管理器接回 V2.1。

现实表现：

- 可以复用旧能力。
- 但旧能力带文件输入、artifact 等更多历史包袱。
- V2.1 本来是更直接的“目录图纸 -> 黑板运行”，重新接旧系统可能让主线变复杂。

候选 B 更像：

> 把旧仓库管理员请回来管新流水线入口。

**候选 C**

候选 C 是不做漏斗，继续信任调用方。

现实表现：

- 当前行为不变。
- 最兼容。
- 但脏字段会继续进黑板。
- 后续 phase 可能读到不该读的数据。

候选 C 更像：

> 大门继续敞开，后面出事再说。

**a2 推荐**

a2 推荐候选 A。

a2 的理由是：入口越干净，后面 phase 沙箱和 trace 才越可解释。

**PM 你拍的影响**

拍 A，运行入口会更严格，调用方传错字段会更早暴露。

拍 B，能复用旧逻辑，但可能把 V2.1 主线变重。

拍 C，保留今天行为，但后续隔离会很难真正干净。

**跳源 verify:** `.kiro/specs/engine-mvp0-state-io-contract/design.md:61`

### 4.3 Q-S-A2: phase 节点能不能继续看全局黑板

**现在 engine 怎么跑**

今天 LOGIC 节点拿到的是全量 data 的副本。

SUBGRAPH 也拿全量父 data。

SKILL 节点虽然没有自动拿一个 Context，但整体运行仍围绕全局 data 和 messages。

所以一个节点理论上很容易看到超过自己需要的材料。

人话：

> 今天每个工位不只是拿自己的托盘，而是能看到整张总黑板。

**候选 A**

候选 A 是强沙箱。

拍了 A 以后，每个 phase 启动前，engine 会按它声明的输入，切出一个局部 phase_input。

节点只拿这份局部输入。

现实表现：

- phase 只能看到自己声明要看的字段。
- 没声明就读不到。
- 黑板污染明显减少。
- 但旧节点如果以前靠偷看全局 data，会立刻报错。

候选 A 更像：

> 每个工位只拿自己托盘里的材料，不准翻总仓库。

**候选 B**

候选 B 是 warning-only。

engine 继续把全量 data 给节点。

但 trace 或检查器发现节点读了不该读的字段，就报警。

现实表现：

- 兼容性最好。
- 老节点不容易挂。
- 但安全边界没有真正拦住，只是事后记录。

候选 B 更像：

> 工位仍能翻总仓库，只是摄像头看到越界会打警告。

**候选 C**

候选 C 是和显式映射思想调和。

默认按 phase 输出分区和字段名字匹配，把需要的数据切给节点。

如果默认匹配不够，就让人写明确映射。

现实表现：

- 有沙箱。
- 也允许复杂场景指定“从哪里拿什么字段”。
- 依赖 Block 1 的 phase 读写说明，也依赖 StateMapper。

候选 C 更像：

> 平常按材料名自动配托盘；遇到同名或特殊来源时，人工写清楚从哪个工位拿。

**a2 推荐**

a2 推荐候选 C。

a2 的理由是：它既走向隔离，也保留复杂数据流的明确表达空间。

**PM 你拍的影响**

拍 A，边界最硬，但迁移最疼。

拍 B，兼容最好，但数据治理最弱。

拍 C，让默认切片和显式映射一起工作，是中间演进路线。

**跳源 verify:** `.kiro/specs/engine-mvp0-state-io-contract/design.md:81`

### 4.4 Q-S-A3-A6: 子图和 subagent 是否彻底隔离父黑板

**现在 engine 怎么跑**

今天 SUBGRAPH 执行时，会把父图当前 data 全量给子图。

今天 subagent 子图执行时，会把“父图全量 data + LLM 传入的 input”给子图。

这让子图很方便。

但也让边界很脏。

子图可能：

- 看见父图不该给它看的字段。
- 修改父图已有 key。
- 依赖一个没有写在入参里的隐式字段。
- 让 trace 无法说明子图到底是靠哪些输入跑出来的。

人话：

> 今天父流水线叫小流水线帮忙时，经常把整张黑板都复印给它。

**候选 A**

候选 A 是全隔离。

SUBGRAPH 和 subagent 都不再继承父 data 全集。

它们启动时只拿明确输入。

现实表现：

- 子图看不到父图多余字段。
- 子图必须靠明确传入的数据运行。
- 隐式依赖会暴露。
- 旧子图如果以前偷读父 data，会挂。

候选 A 更像：

> 叫外包工位时，只发任务单和必要材料，不发整张公司白板。

**候选 B**

候选 B 是只隔离 subagent，SUBGRAPH 继续拿全量 data。

现实表现：

- 工具型子代理更干净。
- 固定流程子图保持兼容。
- 但 SUBGRAPH 的污染风险还在。

候选 B 更像：

> 临时外援要隔离，固定分厂继续共享总黑板。

**候选 C**

候选 C 是加明确输入/输出映射字段。

也就是跨父子边界时，写清楚：

- 给子图哪些输入。
- 子图结束后哪些输出可以回父图。

现实表现：

- 能严格隔离。
- 又能按需要跨边界传数据。
- 需要和 Block 1 的 phase 读写说明、Block 2 的 StateMapper 一起工作。

候选 C 更像：

> 父子流水线之间只通过交接单传材料，交接单上写清楚进出项。

**a2 推荐**

a2 推荐候选 C 搭配候选 A。

a2 的意思是：切断隐式继承，同时通过明确映射保留必要通信。

**PM 你拍的影响**

拍 A/C，子图边界会变干净，但旧的偷读父 data 写法要迁移。

拍 B，迁移更轻，但 SUBGRAPH 仍可能污染父黑板。

**跳源 verify:** `.kiro/specs/engine-mvp0-state-io-contract/design.md:100`

### 4.5 Q-S-StateMapper: 状态分发由谁做

**现在 engine 怎么跑**

今天没有一个统一的“黑板分发员”。

LOGIC、SUBGRAPH、SKILL 各自在自己的 node builder 里处理输入输出。

所以要做沙箱时，如果没有统一组件，很容易出现：

- LOGIC 按一套切。
- SKILL 按另一套切。
- SUBGRAPH 又绕过去。
- trace 看到的输入输出和实际执行不一致。

人话：

> 今天每个工位自己拿材料，没有一个统一配料员。

**候选 A**

候选 A 是独立 StateMapper。

它负责：

- 按 phase 的读写说明，从 inputs 和前面 phase 输出里切出 phase_input。
- 检查缺字段。
- 包装 phase_output。
- 做深拷贝，避免嵌套对象污染父黑板。
- 给 trace 提供同一份输入输出切片。

现实表现：

- 逻辑集中。
- 更容易测试。
- Studio / trace 可以复用同一套理解。
- 多一层组件，但边界清楚。

候选 A 更像：

> 增加一个统一配料员，每个工位从它那里拿托盘，交成果也交给它入库。

**候选 B**

候选 B 是直接写在 phase wrapper 里。

现实表现：

- 实现更短。
- 少一个显式组件。
- 但复用难。
- 以后 trace、调试、Studio 想重放切片规则时不方便。

候选 B 更像：

> 每个工位门口临时写一段配料逻辑，先跑起来，但以后难统一。

**a2 推荐**

a2 推荐候选 A。

a2 的理由是：独立封装更利于测试和复用，尤其 Block 4 tracing 也要拿 phase_input / phase_output。

**PM 你拍的影响**

拍 A，状态分发变成独立能力，后续 trace 和 Studio 更容易对齐。

拍 B，实现更轻，但长期维护和复用弱。

**跳源 verify:** `.kiro/specs/engine-mvp0-state-io-contract/design.md:113`

## 5. Block 3: execution-runtime (6 个 Q)

### 5.0 这块在 engine 哪里，现在怎么跑

Block 3 管的是“图纸已经编译好以后，engine 具体怎么跑”。

今天 V2.1 主线很直接：

- `run_skill()` 收到 skill root 和输入。
- 编译 skill。
- 装配成图。
- 把初始 data / flow / messages 丢给图。
- 图按 phase 执行。
- 返回最终 data。

这条主线已经能跑 LOGIC、SKILL、SUBGRAPH 和 subagent。

但执行层还有几处缺口。

第一，真实模型从哪里来还没接好。

如果没传 mock，SKILL phase 需要模型时会直接挂。

第二，subagent 的深度只写到运行配置里，没有写进 child flow。

子图自己看 flow 时不知道自己第几层。

第三，SKILL phase 每轮都会把临时交卷规则塞回消息历史。

跑多轮后同一段规则会重复堆。

第四，subagent 太重。

今天它必须是完整 skill root，不能只是一个轻量 Prompt 文件。

第五，LLM 还不能像调工具一样调“预注册的完整子图”。

第六，运行时错误还主要是自由文本，不方便 Studio 稳定识别。

### 5.1 Q-R-P0-1: ModelResolver 放在哪里

**现在 engine 怎么跑**

今天 V2.1 SKILL phase 要跑大模型，必须有 chat model。

如果调用方传了 mock，就用 mock。

如果没传，engine 不会自动去找真实模型。

SKILL phase 跑到需要模型时会直接报“需要 chat_model”。

人话：

> 今天流水线里有大模型工位，但没人负责给它接电源；除非测试时手动塞一个假电源。

**候选 A**

候选 A 是外层 Studio 注入模型解析器。

Studio 后端负责读模型角色配置、密钥、供应商信息，把可用模型对象传给 engine。

engine 只负责跑图。

现实表现：

- Engine 保持轻。
- 厂商 SDK、密钥、模型路由都留在 Studio 后端。
- CLI 或脱离 Studio 的纯 engine 跑法会更依赖外部传入 resolver。
- `run_skill()` 入口需要能接收这个外部模型解析能力。

候选 A 更像：

> engine 只管流水线，Studio 负责把大模型电源插好再开工。

**候选 B**

候选 B 是把模型解析下沉到 graph-agent 自己。

engine 直接读模型配置，自己实例化真实模型。

现实表现：

- CLI 独立跑会更方便。
- 但 engine 包会变重。
- 厂商依赖和密钥处理会进核心库。
- Studio 可能要反过来复用 engine 的模型解析。

候选 B 更像：

> 流水线自己内置发电厂，不再等 Studio 插电。

**候选 C**

候选 C 是短期继续 mock-only。

现实表现：

- 不动结构。
- 测试能继续靠 mock。
- 真实业务接入仍然痛苦。
- 无模型时只把错误变得更清楚。

候选 C 更像：

> 暂时只允许演练模式，真实生产电源以后再接。

**a2 推荐**

a2 推荐候选 A。

a2 的理由是：让执行引擎保持图编排职责，真实模型路由留给 Studio 后端。

**PM 你拍的影响**

拍 A，engine 更轻，但外层必须注入模型能力。

拍 B，engine 更独立，但核心依赖更重。

拍 C，短期少改，但真实 SKILL phase 仍不能自然跑。

**跳源 verify:** `.kiro/specs/engine-mvp0-execution-runtime/design.md:37`

### 5.2 Q-R-P1-2: child flow 里要不要写 subagent_depth

**现在 engine 怎么跑**

今天 subagent 调子图时，engine 会在运行配置里记录 child 的深度。

但传给子图 state 的 flow，仍然是父图 flow。

所以子图内部如果看 flow，不一定知道自己已经在 subagent 第几层。

而且父子 flow 可能共享引用，子图改了控制字段可能污染父图。

人话：

> 今天派外援时，外援的外层信封写了“你是第 1 层”，但外援拿到的任务单里没写。

**候选 A**

候选 A 是深拷贝父 flow，并把新的 subagent_depth 写进去。

现实表现：

- 子图内部能读到自己深度。
- 子图改 flow 不会反向污染父 flow。
- 父图里有用的控制信息仍能正向传给子图。

候选 A 更像：

> 复印一份控制任务单给外援，在复印件上写“你现在是第几层”。

**候选 B**

候选 B 是只传 subagent_depth，其他 flow 都不继承。

现实表现：

- 隔离最强。
- 子图拿不到父图其他控制信息。
- 如果以后 trace_id、run flags 这类信息需要下发，会丢。

候选 B 更像：

> 只给外援一张写着层级的小纸条，其他控制信息都不给。

**a2 推荐**

a2 推荐候选 A。

a2 的理由是：既阻断父子双向污染，又保留必要控制信息的正向传递。

**PM 你拍的影响**

拍 A，子图会更知道自己在哪层，也保留父图控制上下文。

拍 B，隔离更硬，但可能丢掉有用控制字段。

**跳源 verify:** `.kiro/specs/engine-mvp0-execution-runtime/design.md:52`

### 5.3 Q-R-P1-3: exit_contract 怎么不污染 messages

**现在 engine 怎么跑**

SKILL phase 每轮大模型调用前，engine 会把 exit contract 临时加进 prompt。

但今天它把加了 exit contract 的 prompt 也保存回 messages。

下一轮再加一次。

多轮后，同一段交卷规则会重复出现在历史里。

人话：

> 每次提醒工位“交卷格式是什么”，今天都会把这张提醒纸永久贴进历史档案，贴一轮多一张。

**候选 A**

候选 A 是给临时提醒纸打 marker，模型回复后再从历史里剥掉。

现实表现：

- 发送给模型时仍有 exit contract。
- 保存回 messages 前删掉临时规则。
- 实现比较直接，但需要识别哪条消息是临时的。

候选 A 更像：

> 临时贴纸先贴上，模型看完后再撕掉。

**候选 B**

候选 B 是每轮单独拼 prompt_messages。

exit contract 只在这次模型调用的临时 prompt 里出现。

它从一开始就不进入长期 messages。

现实表现：

- 历史消息更干净。
- 不需要事后从历史里找 marker。
- 交卷规则仍能每轮给模型看。

候选 B 更像：

> 提醒纸只拿给工位看一眼，不贴进档案。

**a2 推荐**

a2 推荐候选 B。

a2 的理由是：它从根上避免历史污染，也减少状态更新压力。

**PM 你拍的影响**

拍 A，走“写进去再剥离”。

拍 B，走“只临时拼，不写进去”。

两者目标相同，都是让 messages 不再无限堆交卷规则。

**跳源 verify:** `.kiro/specs/engine-mvp0-execution-runtime/design.md:66`

### 5.4 Q-R-A4: 轻量 subagent 怎么支持

**现在 engine 怎么跑**

今天父 SKILL phase 里要声明 subagent，subagent path 必须指向一个完整 skill root。

它要有自己的图纸、输入输出说明书、phases 目录。

这很完整，但也很重。

如果只是想让父 agent 临时叫一个“小专家 prompt”，配置成本偏高。

人话：

> 今天叫一个小外援，也必须给它建一整条小流水线。

**候选 A**

候选 A 是支持 path 指向单个 `.md` 文件。

engine 看到这是单文件，就在内存里把它包装成一个虚拟单节点子图。

现实表现：

- 用户可以更轻量地写 subagent。
- 不用每次都搭完整目录。
- 不新增复杂配置语法。
- loader/runtime 要能识别“目录型”和“单文件型”两种 subagent。

候选 A 更像：

> 小外援可以只交一张任务卡，engine 临时帮它搭一个最小工位。

**候选 B**

候选 B 是新增显式字段区分 lightweight。

现实表现：

- 配置层级更清楚。
- 但写法更复杂。
- 现有 subagent 配置模型要改。

候选 B 更像：

> 仍然走登记表，只是在登记表里新增“这是轻量外援”一栏。

**a2 推荐**

a2 推荐候选 A。

a2 的理由是：基于文件形态自动识别，用户心智负担更小。

**PM 你拍的影响**

拍 A，用户写轻量 subagent 更省事，但 loader 要更聪明。

拍 B，配置更显式，但语法更重。

**跳源 verify:** `.kiro/specs/engine-mvp0-execution-runtime/design.md:80`

### 5.5 Q-R-A5: call_subgraph 是预注册还是任意路径

**现在 engine 怎么跑**

今天有两种子图相关能力。

一种是 SUBGRAPH phase，图纸跑到这个节点时自动调用子图。

另一种是 subagent tool，父 LLM 可以调用预先声明的子 agent。

但今天没有一个通用的“LLM 在 SKILL phase 里按需调完整大图”的 call_subgraph 工具。

人话：

> 今天 LLM 可以叫登记过的外援，但还不能安全地说“帮我跑这条已登记的大流水线”。

**候选 A**

候选 A 是预注册工具族。

用户在 phase 配置里先登记可调用的 subgraph。

engine 只把登记过的子图变成工具。

工具名类似“call 某个登记名”。

现实表现：

- LLM 只能调用白名单里的子图。
- 不容易幻觉路径。
- 更安全、更可追踪。
- 灵活性小一点。

候选 A 更像：

> 外援名单先登记好，LLM 只能拨名单里的分机。

**候选 B**

候选 B 是通用路径工具。

LLM 可以传一个 path 和 inputs。

engine 按 path 去找子图。

现实表现：

- 灵活。
- 但 LLM 可能编不存在的路径。
- 可能传错参数。
- 安全边界更难守。

候选 B 更像：

> 给 LLM 一张万能通行证，让它自己写要去哪个车间。

**a2 推荐**

a2 推荐候选 A。

a2 的理由是：生产流程里，预注册带来的确定性比动态探查更重要。

**PM 你拍的影响**

拍 A，call_subgraph 更安全、更可控。

拍 B，call_subgraph 更灵活，但更依赖运行时防错。

这个 Q 还强依赖 Block 2：没有子图输入隔离时，不应该放开大图调用。

**跳源 verify:** `.kiro/specs/engine-mvp0-execution-runtime/design.md:94`

### 5.6 Q-R-ERROR: 运行时错误怎么结构化

**现在 engine 怎么跑**

今天很多运行时错误是自由文本。

比如缺模型、深度超限、工具参数错，都可能靠字符串说明。

开发者看日志可以懂。

但 Studio 要稳定展示和过滤，就很难。

人话：

> 今天故障灯会亮，但灯上经常只贴一段人读的文字，不是机器能稳定识别的故障码。

**候选 A**

候选 A 是在现有错误对象上增加 code 和 metadata。

运行仍然用抛错方式。

但错误里会有机器可读的字段。

现实表现：

- 缺模型可以变成 `MODEL_NOT_FOUND`。
- 深度超限可以变成 `DEPTH_LIMIT_REACHED`。
- 工具参数错可以变成 `INVALID_TOOL_ARGS`。
- Studio 能按错误码展示。
- 主流程不用改成结果对象控制流。

候选 A 更像：

> 保留故障抛出，但每次故障都带标准故障码和定位信息。

**候选 B**

候选 B 是全面改成结果对象。

运行时预期错误不再主要靠抛错，而是返回带 error_code 的结果。

现实表现：

- 边界更显式。
- 但重构很大。
- 许多调用方和测试都要改。

候选 B 更像：

> 不再拉急停绳，而是每个工位都交一份“成功/失败报告”。

**a2 推荐**

a2 推荐候选 A。

Block 3 tasks 也按候选 A 拆了主要实施路径。

**PM 你拍的影响**

拍 A，错误会更好给 Studio 解析，同时保留当前异常流。

拍 B，错误控制流更彻底，但会全局重构。

**跳源 verify:** `.kiro/specs/engine-mvp0-execution-runtime/design.md:98`

## 6. Block 4: tracing-and-observability (4 个 Q)

### 6.0 这块在 engine 哪里，现在怎么跑

Block 4 管的是“engine 跑的时候，外面能不能看见它每一步发生了什么”。

今天旧 harness 有 callbacks 和 trace。

但 V2.1 主线直接把 callbacks 丢掉。

它走的是：

- 编译。
- 装配。
- 图执行。

没有稳定给 Studio 发：

- 哪个节点开始。
- 哪个节点结束。
- 模型什么时候调用。
- 工具什么时候调用。
- subagent 什么时候进入和退出。
- 哪里抛了结构化异常。

Predict 私有路径已有一部分 trace 能力。

但普通 V2.1 主线还没有统一飞行记录仪。

Block 4 的 4 个 Q，就是决定这个飞行记录仪怎么造。

### 6.1 Q-T-1: V2TracingCallback 接口怎么设计

**现在 engine 怎么跑**

今天有旧 TracingCallback，也有 Predict 专用的追踪能力。

但 V2.1 主线没有一个公开、统一、能接 node 生命周期的 V2TracingCallback。

人话：

> 今天有旧记录本，也有 Predict 小黑匣子，但主流水线没有统一飞行记录仪。

**候选 A**

候选 A 是完全独立新写。

不继承 Predict。

runtime 在关键位置手工调用它。

现实表现：

- 设计直接。
- 不被旧框架复杂性拖住。
- 但 Predict 和普通运行会各有一套逻辑。
- 共享清洗和事件规则会少。

候选 A 更像：

> 给主流水线单独装一套新摄像头，和 Predict 摄像头分开维护。

**候选 B**

候选 B 是走框架标准回调。

它更贴近 LangGraph / LangChain 的回调体系。

现实表现：

- 框架味更浓。
- 但很难精准拿到业务含义上的 phase 输入切片、子代理深度等。
- 可能要反向猜状态。

候选 B 更像：

> 尽量接厂商提供的监控总线，但要从总线消息里反推工位材料。

**候选 C**

候选 C 是抽一个公共底座。

普通 V2TracingCallback 和 PredictTracingCallback 都用这套底座。

现实表现：

- 主线和 Predict 共享清洗、事件外壳、生命周期基础逻辑。
- Predict 仍保持私有，但不重复造一套。
- 实现会比 A 更系统。

候选 C 更像：

> 造一套通用飞行记录底座，主航班和演练航班都插同一套记录仪核心。

**a2 推荐**

a2 推荐候选 C。

a2 的理由是：统一内外日志底座，避免普通运行和 Predict 继续分裂。

**PM 你拍的影响**

拍 A，主线 tracing 上得快，但长期两套体系。

拍 B，更依赖框架回调，但业务切片可能难拿准。

拍 C，底座更统一，前期整理更多。

**跳源 verify:** `.kiro/specs/engine-mvp0-tracing-observability/design.md:32`

### 6.2 Q-T-P1-4: V2.1 callback 接回走 node wrapper 还是框架回调

**现在 engine 怎么跑**

今天 V2.1 runner 明确丢弃 callbacks。

所以 graph 跑起来时，外面看不到稳定的 phase start/end。

也看不到模型调用和工具调用的完整生命周期。

人话：

> 今天流水线在黑箱里跑，最后只把成品交出来，中间摄像头没接上主电路。

**候选 A**

候选 A 是在 node wrapper 里显式发事件。

LOGIC 启动前发 NODE_START，结束后发 NODE_END。

SKILL 调模型前后发 LLM_CALL_START / END。

工具调用前后发 TOOL_CALL_START / END。

SUBGRAPH 和 subagent 也发进入退出。

现实表现：

- 事件和业务含义最准。
- 能直接拿 Block 2 StateMapper 产出的 phase_input / phase_output。
- 需要改 graph 装配核心。
- 强依赖 Block 2 先把输入输出切片做出来。

候选 A 更像：

> 在每个工位门口装摄像头，材料进门和成品出门都拍下来。

**候选 B**

候选 B 是走框架原生回调树。

现实表现：

- 少一点手工插桩。
- 但事件里的业务切片可能不够准。
- 需要从框架回调里反推哪个字段是这个 phase 真正输入输出。

候选 B 更像：

> 接入大楼总监控，但要从监控日志里猜每个工位实际拿了什么材料。

**a2 推荐**

a2 在 research 里把候选 A 作为更准确的事件入口。

Block 4 tasks 也按候选 A 拆了主路径。

**PM 你拍的影响**

拍 A，trace 更贴近 engine 真正执行点，但必须等 Block 2/3 关键能力。

拍 B，框架整合更强，但可能牺牲业务语义准确性。

**跳源 verify:** `.kiro/specs/engine-mvp0-tracing-observability/research.md:63`

### 6.3 Q-T-STREAM: 流式 token 是否落盘

**现在 engine 怎么跑**

今天 V2.1 主线没有完整流式 token trace。

未来 Studio 想看大模型打字机效果，就需要 token 事件。

但 token 很多。

如果全部写入 trace 文件，长任务会把文件撑大。

人话：

> 模型一个字一个字说话时，Studio 想实时看，但不一定要把每个字都永久记进黑匣子。

**候选 A**

候选 A 是 token 全量进入事件总线并落盘。

现实表现：

- 回放最完整。
- Studio 可以精确复现打字过程。
- 文件会很大。
- 长轮次、批量测试、daemon 运行都会有磁盘压力。

候选 A 更像：

> 每个字都录像并永久存档。

**候选 B**

候选 B 是 token 在线推送，但不默认写入 trace 文件。

现实表现：

- 前端仍能实时显示。
- trace 文件只保留更高价值的节点、模型完成、工具、异常事件。
- 回放时看不到逐字过程，只看到聚合结果。
- 文件体积更可控。

候选 B 更像：

> 直播时能看到每个字，但黑匣子只保存完整发言段落。

**a2 推荐**

a2 推荐候选 B。

a2 的理由是：MVP0 要避免 trace 文件被高频 token 撑爆。

**PM 你拍的影响**

拍 A，回放能力最细，但磁盘和队列压力大。

拍 B，实时体验保留，长期日志更轻。

**跳源 verify:** `.kiro/specs/engine-mvp0-tracing-observability/design.md:64`

### 6.4 Q-T-PAYLOAD: 大 payload 怎么防爆

**现在 engine 怎么跑**

Predict 侧已经有一套把大字段截断、过滤 usage/cost 的经验。

普通 V2.1 主线还没有统一的 AgentTraceEvent payload 防爆。

如果未来 NODE_START 直接记录整块 data，或者工具返回巨大文本，trace 文件可能快速膨胀。

人话：

> 飞行记录仪要记关键事实，不能把整仓库材料都塞进每一条记录里。

**候选 A**

候选 A 是复用现有的清洗/截断思路。

长文本截断。

大对象只保留摘要。

敏感或低价值字段过滤。

现实表现：

- 实现简单。
- 文件可控。
- 记录里会标明哪些字段被截断。
- 但如果调试需要完整原文，就得另找方式。

候选 A 更像：

> 黑匣子只记摘要和关键字段，超长内容贴“已截断”。

**候选 B**

候选 B 是长内容写到附属 blob 文件。

主事件只保留引用。

现实表现：

- 可以保留全量大内容。
- 但文件管理复杂。
- blob 丢失、清理、权限、关联都要处理。
- 对 MVP0 来说偏重。

候选 B 更像：

> 黑匣子里放索引卡，完整货物另存仓库。

**a2 推荐**

a2 推荐候选 A。

a2 的理由是：MVP0 先保证 trace 不爆，不提前引入复杂 blob 系统。

**PM 你拍的影响**

拍 A，trace 简单可控，但不是全量原文档案。

拍 B，保留更多细节，但实现和运维复杂度更高。

**跳源 verify:** `.kiro/specs/engine-mvp0-tracing-observability/research.md:58`

## 7. 最终全景图

18 个 Q 都拍完并实施后，engine 跑起来可以按下面理解。

用户提交任务。

↓

输入先过入口漏斗。

只放行根输入说明书里声明过的字段。

未知字段、缺字段、错类型，在开跑前就被拦住或清洗。

↓

编译器读 GRAPH.md 和所有 phase。

每个 phase 不只是“在图纸上的节点”，还会逐步有自己的读写说明。

编译器能检查：

- phase 是否存在。
- phase 顺序是否合法。
- phase 要读的 key 前面有没有来源。
- 编译错误能不能带文件、行、phase、字段。

↓

运行时建立初始黑板。

黑板不再只是一个谁都能随便看的大 dict。

它会逐步分成：

- 入场输入区。
- 每个 phase 的输出区。
- 控制用 flow。
- 大模型 messages。

↓

StateMapper 像配料员。

每个 phase 开始前，它从黑板切出这个 phase 该看的 phase_input。

每个 phase 结束后，它把 phase_output 包好放回对应位置。

↓

LOGIC phase：

拿局部输入。

算结果。

交 delta。

delta 合回它自己的输出格。

↓

SKILL phase：

拿局部输入。

找真实模型。

临时拼交卷规则，不污染历史消息。

调工具或 subagent。

最后用 finish_task 交卷。

结果进入当前 phase 的输出格。

↓

SUBGRAPH / subagent：

不再默认拿父图整块 data。

只能拿明确给它的输入。

子图结果按约定回到父图，或作为工具结果回到父 LLM。

↓

错误：

不只是自由文本。

会带错误码和定位信息。

Studio 可以稳定识别“缺模型”“深度超限”“工具参数错”“输入缺字段”。

↓

Trace：

每个节点开始、结束、模型调用、工具调用、subagent 进入退出、异常，都会发结构化事件。

事件 payload 来自 phase_input / phase_output，而不是重复塞整块全局黑板。

token 可以实时给前端看，但默认不把每个字都写进长期 trace。

大 payload 会被截断或摘要化，避免 trace 文件爆掉。

↓

最终返回。

调用方拿到更干净的最终 context。

Studio 拿到能回放的过程记录。

## 10. 最容易误解的 12 件事

### 1. 18 个 Q 不是 18 个孤立开关

很多 Q 有前后依赖。

例如 Block 2 的沙箱，依赖 Block 1 的 phase 读写说明。

Block 4 的 node trace，依赖 Block 2 的 phase 输入输出切片。

### 2. Q-A7 不是只影响文档格式

它决定每个 phase 是否必须先说清楚自己读写什么。

没有这个基础，后面很多“按授权拿材料”的设计都没有依据。

### 3. Q-A8 不是要把所有类型问题一次性解决

a2 推荐先查 key 是否接上。

这更像先保证“材料名字能传到”，不是马上证明“材料规格完全正确”。

### 4. Q-S-P0-3 不是放弃并行冲突保护

智能合并不是让所有覆盖都合法。

它只是区分“后一步更新前一步”和“并行分支同时抢同一格”。

### 5. Input Funnel 不是 phase 输入切片

入口漏斗管的是外部输入进不进整张图。

phase 输入切片管的是某个节点能看黑板上的哪些字段。

### 6. StateMapper 不是业务逻辑

它不决定分析结果是什么。

它只负责按规则把材料分给节点、把节点成果收回来。

### 7. 子图隔离不是不让子图拿数据

它是不让子图偷偷拿父图全集。

需要的数据可以通过明确输入传。

### 8. subagent 轻量化不是把 subagent 变成普通工具

轻量 subagent 仍然是 agent 调用的子能力。

只是它可以用单文件表达，再由 engine 包成最小可运行单元。

### 9. call_subgraph 和 SUBGRAPH phase 不是同一个东西

SUBGRAPH phase 是图纸固定流程。

call_subgraph 是大模型在 SKILL phase 里按需调用登记过的完整子图。

### 10. ErrorCode 不是为了让错误好看

它是为了让 Studio 不再截字符串。

前端可以按错误码定位、过滤、展示。

### 11. Trace 不应该记录整块 data

如果每个 NODE_START 都塞全局黑板，trace 会重复、巨大、难读。

正确方向是记录这个 phase 真正看到的 phase_input。

### 12. token 直播和 token 落盘是两件事

前端实时看见模型逐字输出，不等于要把每个字都写进长期 trace 文件。

## 11. 每个 Block 改完后的实际体感

### Block 1 改完

PM 写 skill 时，会更早被提醒：

- 这个 phase 没写读写说明。
- 这个 phase 要读的字段没人产出。
- 这个编译错误在某个文件某一行。

engine 体感：

- 开跑前验图纸更严格。
- 错误更可定位。
- 编译阶段更像真正的“图纸验收”。

### Block 2 改完

PM 运行 skill 时，黑板不再像公共大白板。

engine 体感：

- 外部输入先过漏斗。
- 每个 phase 拿局部输入。
- phase 输出更有归属。
- 子图边界更干净。
- 顺序覆盖不会被误伤成并行冲突。

### Block 3 改完

PM 跑 SKILL phase 时，模型、消息、子代理、子图调用、错误会更像一套完整运行系统。

engine 体感：

- 不再只靠 mock 才能跑模型节点。
- subagent 深度进入 child flow。
- exit contract 不再污染 messages。
- 轻量 subagent 配置更省。
- LLM 可调用预注册完整子图。
- 错误带稳定 code。

### Block 4 改完

PM 在 Studio 看运行过程时，不再只看最终结果。

engine 体感：

- 节点开始/结束有事件。
- 模型调用有事件。
- 工具调用有事件。
- subagent 进入退出有事件。
- 异常有事件。
- trace 文件不会因为 token 或大 payload 无限制膨胀。

## 12. 一句话收尾

这 18 个 Q 合起来，不是在给 engine 加一堆零散功能。

它们是在把当前“共享黑板 + 自觉读写 + 事后看日志”的 V2.1，推进到“图纸先讲清、输入先过漏斗、节点按授权拿材料、子图按边界交接、错误有码、过程可回放”的 MVP0。

PM 要拍的不是代码细节，而是这些边界要硬到什么程度、兼容旧资产到什么程度、Studio 需要拿到多完整的运行记录。
