## 工单复核

### M6 判据作废并改写

原 M6 写的守卫是：

&gt; `judge.py:278-279` 的 404 分支在 `transform_applied != none` 时降级为 `url_plan_suspect`

**这条接不住 A 案，作废。** A 案的 `transform_applied` 恰恰**就是 `none`** —— 病因是该变换而没变换。以「有无变换」为判据，等于把最该拦的那个放过去。

**改写后的 M6（对 A、B 同时成立）：**

1. **judge 侧收窄 `protocol_unsupported` 的成立条件**：只在 provider **正面说了话**时才判它 —— 即 `code == 405`、命中 `_PROTOCOL_MISMATCH_MARKERS`（`judge.py:185-195`）、或命中 `_has_foreign_protocol_error`（`judge.py:219-227`）。这三者都是「主机告诉我们它不说这个协议」。
2. **新增 `url_plan_suspect`**：`404 + 无 provider 错误信封`（空体或非 JSON 或无 `error` 成员）→ **一律 `url_plan_suspect`**，不再判 `protocol_unsupported`。理由是这种回包在信息论上**无法区分**「我们地址拼错了」与「主机不说这协议」，而两者的正确处置完全相反。删掉 `judge.py:278-279` 现有分支。
3. **`url_plan_suspect` 携 `actionable=False`**：消费侧一律禁止据此销毁数据、禁止进半衰期门。落到 `llm.py:1087-1114` 与 `:804-830`。
4. **保留 `protocol_unsupported` 也不删数据**（M0 已覆盖）—— 即使 provider 正面说了话，销毁用户手工录入的 route 仍然不是任何 verdict 该被授予的权限。

### M4 上位为两案共同根治

`UrlPlan` 单 owner 化不再只是「清理 9 个 owner」的整洁性工单，它是 A、B 两案唯一的共同根治：A 需要 `UrlPlan` 知道 openai 协议的版本根是 `/v1`（dialect 层已经知道，见 `dialect/request.py:84-89`），B 需要 `UrlPlan` 知道 anthropic 面的 `/anthropic` 不得带进 openai wire。M6 的 `url_plan_suspect` 只是止损网，M0 只是止血带 —— **修好 URL 才是修好**。
