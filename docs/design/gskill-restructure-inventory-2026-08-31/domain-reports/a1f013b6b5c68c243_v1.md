## 1. 模块(Module)体系

### 1.1 Module 是什么

`Module` 本身是一个 **OntologyType**,具体的 `OntologySystem`、`ActionSystem` 都是这个类型的具体 Ontology。`OntologySystem@r9` 是同一个 Module Ontology 的一个 Revision,**不是第二个 Module identity**。进程、容器、副本属于 Implementation/deployment,不产生第二个 Module。

&gt; 出处:`D:\coding\zeroth\repository\docs\project_knowledge\owner_rulings\2026-08-23-active-module-link-naming-baseline.md` §3

配套原则(`governance_universe\knowledge-base-system\principles\domain-cohesion\DomainCohesion.principle.zce`):

&gt; "Form a Module around one cohesive responsibility and its shared invariants rather than one file, one OntologyType, or one implementation package."
&gt; boundary plurality: "One Module may govern multiple OntologyTypes when they share coherent governance and operational logic."

### 1.3 完整治理义务(八项)——「一个片段能不能当 Module」的正向清单

`D:\coding\zeroth\repository\docs\project_knowledge\owner_rulings\2026-08-24-module-atomicity-and-reference-cases.md` §3.1:

1. **purpose**:为何存在,拥有哪一项内聚语义责任
2. **owned facts**:哪些事实只由它维护
3. **public capabilities**:外部可以请求什么,输入输出是什么
4. **dependencies**:直接使用哪些外部 Module 或祖先平台公开能力
5. **Rules 与 Actions**:哪些判断约束适用,哪些动作可改变状态
6. **Effects 与 Failures**:成功承诺什么结果,失败如何显式暴露
7. **Evidence 与 Assurance obligations**:哪些动作后观察支持或反驳结果
8. **lifecycle 与 Revision**:怎样形成候选、运行、失败、取代、重开和修订

关键定义(同文件 §2):

&gt; `Module atom`:还能独立拥有一项完整受治理保证的最小语义责任。
&gt; `Module membrane`:向外公开能力、依赖、失败和生命周期的合同边界。
&gt; **膜与原子性是两个维度**(§3.3):"一个膜写得清楚,不证明膜内只有一个不可再分的责任;一个原子已经最小,也不证明其公共合同完整。"
&gt; `causal oracle`:动作完成后能观察什么结果,据此判断责任是否真实达成,而不是只看命令已发出或函数已返回。

### 1.4 split-first 发现流程(拆分方法论,§3.2)

1. 尽量把责任拆成单独片段,**不先沿用当前文件、函数、package、进程或历史目录**
2. 对每个片段执行 §3.1 完整保证检查
3. 通过的保留为 Module candidate
4. 不通过的**改判**为 Rule / Action / Definition / Link / Port / Adapter 或内部机制(「改判不是降级,是恢复正确语义类型」)
5. 只有出现**正向合并证据**才重新合并

**正向合并证据只允许三类**:
- 分开会让同一不可分割的 authority 或语义事实出现重复 owner,破坏唯一事实源
- 必须保持一个不可分割的状态转换,而跨 Module 合同无法在不产生 partial state 的情况下保持原子性
- 某片段没有独立 Effect,也没有可独立验证的 causal oracle

**明确不是合并证据**:同一作者、相邻代码、共同 provider、调用频繁、同一进程、行数少、名称相似。拆分增加治理工作也不能推翻语义边界。

**§3.4 不使用通用物理阈值**:不采用行数、token、文件数、函数数、package 数、目录深度、进程数阈值。"物理映射必须服从语义结论,不能反向成为结论的 owner。"

## 2. Ontology(本体)概念

### 2.1 Ontology 是什么 + 资格判据

公理 `governance_universe\knowledge-base-system\axioms\semantic-ontology-governance\SemanticOntologyGovernance.axiom.zce`:

&gt; invariant qualification: **"A semantic node is an Ontology when removing, merging, or further simplifying it destroys a necessary distinction in the system's operational logic."**
&gt; invariant consequence: "Identity, OntologyType, Revision, governor, Admission, and lifecycle are assigned **after** semantic qualification and never substitute for it."

这是全套体系的地基判据:**先证明「删掉/合并/再拆会毁掉一个必要的行为区分」,才配拥有身份**。

### 2.2 Ontology 的结构 schema

核心 semantics/invariant(同文件):

- `semantics whole` — **"One Ontology Revision is its declaration and exact constituent and dependency closure."**(这就是「闭包」的原始定义)
- `semantics path-non-authority` — "A path or filename creates no identity, type, governance, Link, Revision, or Admission."
- `invariant explicit-governance` — "Every declaration names exactly one governing Module and Capability."
- `invariant constituent-membership` — "Every behavior-affecting material belongs to exactly one constituent role."
- `invariant declaration-exclusion` — ZCE 声明本身不列为自己的 constituent
- `invariant direct-dependency-truth` — 每个直接消费的外部合同有且仅有一份精确依赖声明
- `invariant current-identity-unique` — 一个 accepted-state scope 内,每个 OntologyIdentity 至多一个 current Revision

## 4. scs(spec-coding-system)模块+文档治理研究

### 4.1 第一性推导:为什么模块治理与文档治理是同一系统(§1.2)

&gt; 模块治理要成立,模块必须有可信的公开契约;契约要可信,必须与实现机械同步;而「契约文档与实现机械同步」正是文档治理的核心命题。反向同理:文档治理要成立,每个事实必须有唯一 owner;工程仓中最重要的事实(边界、依赖、不变量)的天然 owner 恰是模块。

三条物理绑定:
- **模块即文档**:每个原子模块恰好一个同目录权威 README 作为唯一局部公开契约
- **依赖即图谱**:代码 import 是图谱 `depends-on` 边的物理投影,双向一致机械可核验
- **绑定即门禁**:契约、实现、测试通过双向指纹互锁,单边修改被拒

**负向推论**:"把模块开发与文档维护拆成两个平行流程时,文档不再承载契约职责,沦为可延期的装饰;在交付压力下装饰最先被牺牲。"

### 4.4 结构模型六条不变量(§8)

1. 每项重要事实和重要状态只有一个权威 owner
2. 模块边界显式声明输入、输出、owner、生命周期、允许依赖、失败行为和验收证据
3. **实体自身的属性只保存标量或小型值;跨实体事实由关系类型表达。存放多个路径的数组不能代替关系**
4. 结构变化通过已声明的操作类型发生,绑定确定的策略版本,以操作后可观察结果和因果证据判定成功
5. **操作与记录分别建模**。记录只在操作显式声明持久输出及其语义角色时产生
6. 受控操作只在规范写路径上预防;扫描器和门禁负责发现旁路修改

**操作类型九项声明(§8.1)**——这是最完整的 Action schema:

| 声明项 | 必须回答的问题 |
|---|---|
| 执行者资格 | 哪类主体可以请求、批准和执行,资格怎样核验 |
| 输入 | 针对哪些实体、关系和参数,如何定址与验证 |
| 前置条件 | 执行前必须成立哪些事实,用哪个策略版本判定 |
| 效果 | 成功后哪些实体、属性或关系发生何种变化 |
| 持久输出 | 哪些产物需要落盘,每个承担什么语义角色 |
| 外部副作用与补偿 | 哪些效果越过本地事务边界,失败后怎样补偿或隔离 |
| 幂等策略 | 重试怎样识别同一请求 |
| 后置条件 | 执行后必须观察到哪些状态,哪些结果构成失败 |
| 证据 | 哪些事后材料能把请求、执行和后置状态连成因果链 |

**实体类型七项声明**、**关系类型七项声明**同节可直接抄。

**记录的五种角色必须区分**(§8.1):实体 / 领域记录 / 操作日志 / 执行收据 / 版本提交。"版本提交存在不等于领域事实已经成立;操作日志没有报错不等于后置条件成立。"

### 4.5 文档类型学四轴(§7.2)——由 agent 四大失败模式反推

| 失败模式 | 反推出的轴 | 取值 |

## 6. 总结:哪些能迁移到「桌面 app 按功能模块做垂直闭包拆分」

**高迁移价值(直接可抄,与 zeroth 的形式化机器无关)**

最值钱的是**拆分方法论本身**:split-first(先拆后验)+ 八项完整治理义务 + 三类正向合并证据 + 「不使用通用物理阈值」。它给了一个可执行的循环:先按可疑边界把状态 owner / policy / Effect / Failure / lifecycle / causal oracle 各自拆开,逐片段过八项检查,过不了的**改判**为 Rule/Action/Port/Adapter 或内部机制而不是"降级",只有出现三类正向证据之一才允许合并。对 agent-harness 这种「一堆职责挤在几个大文件里」的桌面项目,这套流程比任何行数/文件数指标都管用。第二值钱的是 `OntologyQualification` 的**三向反事实判据**(删掉/并入/拆成≥2 个孩子,是否毁掉一个 baseline 行为区分),它把「这该不该是个模块」从口头辩论变成了可比较的行为集合对称差。第三是**膜与原子性是两个维度**这条:一个模块接口写得干净不证明里面只有一个责任,反过来也一样,盘点时必须分别过两遍。第四是**唯一 owner 的四层落法**:公理(单一事实源 + 术语唯一定义)→ 登记表(登记即"那份定义是 current",不做第二份注册表)→ 机械 Rule(identity unique / governor explicit / constituent closure)→ 资格 gate。第五是**依赖必须是显式独立对象**:`ModuleDependencyLinkContract` 的三角色(dependent / dependency / **contract=具体 Capability**)比一根 `A → B` 的边信息量高一个量级,并且天然对上 scs 的「代码 import ↔ 边注册表双向机械核验」。第六是 scs 的**十四项机制清单 + 机械/语义三象限 + 完成语义分级**,这三张表可以原样当作 agent-harness 的治理机制盘点表和验收判据地基。第七是两条反 agent 退化的机制:`claim-non-seed`(README/注释里的自我承诺不能当推理前提,只能当比对目标)和 `gap-remediation-grounded`(每个缺口必须带精确事实源 + change-route),以及 `AgentCorpusGravity` 这条 Law(可见的过时材料会把后来的 agent 拉回旧概念,哪怕上面写着"历史")。第八是**派生视图无权威**这条纪律和它的推论:模块地图、参数总表、索引都应该是从各模块契约机械汇聚出来的生成物,手工地图必须退出在岗——scs 自己就是这么翻案的(裁决 #19)。第九是 `semantic_preflight.py` 的**收据模式**(输入路径 + SHA-256 + ready/blocked + HEAD 变化即失效),这个是纯 Python 单文件,可以直接搬。

**低迁移价值 / zeroth 特有,搬不动**

`zce` 语言本身、`OntologyTypeCatalog` 的 digest 链、`RevisionEnvelope` 三重摘要、`AcceptedStateSnapshot` 的 history/current 双索引、`Admission` 终结准入路径、`AuthorityIdentity` 的 grant/scope/separation、`Evidence`/`Assurance` 双系统、`NorthStar contribution` 闭包 —— 这些是「自治系统需要证明自己没撒谎」才需要的机器,桌面 app 没有这个需求,照抄只会产生巨额治理开销。同理,`ModuleSemanticCompositionContract` 那 368 行的 12 个 operator、17 个 clause dimension、13 种 gap kind 是给形式化求解器用的,人和 agent 手工维护不了;可以借它的**思想**(推导 vs claim 分离、最小 gap、不透明递归)但不要借它的枚举。`governance_universe/` 那套 18 个 Module root 全部物理平级、identity-first resolution、路径完全无语义的布局,前提是有 resolver 和 compiler;没有 resolver 的项目里强行"路径无语义"只会让人找不到文件——桌面 app 应该反过来,让目录结构**就是**模块边界的物理投影(这正是 scs §1.2「模块即文档」的做法),然后用门禁保证投影一致。另外 zeroth 的 `human-apex-only` / confidence-routed autonomy / PM Task + 终端回调那套会话纪律是给「多 agent 长期自治重构」设计的,单人开发桌面 app 用 scs §4 的三级强度模型里的 L1 档就够了。最后,`ZAD-0xx` 编号 + Owner Ruling + 后继通知 + 台账这套供应链,价值在于**「最新裁决在其声明范围内取代旧文,旧文必须挂显著后继通知」**这条规则本身(`ExplicitSupersession` 原则),而不在于那 37 篇文档的具体组织形式;agent-harness 抄这条规则就够了,不必抄整套 Owner Ruling 体裁。
