## 0. 这份方法论解决什么 / 最终产物长什么样

### 0.1 它解决什么

我们要写的是一份 **Studio MVP1 前端实施说明书**。它有两个北极星，缺一不可：

1. **零黑盒**：详细到能让一个**没有对话上下文**的实施 agent，照着它把前端 100% 实现出来——每个操作怎么设计、对接哪条后端接口、现状差在哪、怎么测，都写死，不留「你懂的」。
2. **人类可审核**：逻辑边界清晰到一个人类 reviewer 扫一遍就能判断对错，且实施 agent 不会因为表述含糊而乱发挥。

**范围是前端**。后端（gateway 后端 / engine 后端 / Studio Rust 后端，定义见 §4.4）由别人实现；我们只写**前端要对接的后端契约**，并标注每条契约的**后端实现状态**（已实现 / 未实现 / 契约要改）。

> 写之前先认清：这份手册**不修后端、不改后端**。后端只以「契约 + 实现状态标注」的形式出现。把后端内部实现细节（原子写、0600 权限、落盘在哪）写进手册 = 越界 = 错（详见 §2 规则 6）。

### 0.2 最终产物长什么样

一个**自包含的静态 HTML 手册**（样板成品：`temp/studio-mvp1-template-slice.html`），由一个 Python 生成器（`build_template_slice.py`，把数据 JSON 渲染成 HTML 的脚本）+ 若干**数据 JSON**（每页一份，如 `tpl-apikeys-design.json` 是设计页数据、`tpl-mech-cred.json` 是机制页数据）驱动。

- **数据与渲染分离**：内容写在 JSON 里（这是「写页面」的主战场），样式/结构写在生成器里（这是「定组件」的主战场）。改内容只动 JSON，改观感只动生成器。
- **左导航 + 右单列阅读**：sticky 侧栏导航 + 阅读进度 + hash 路由分页，不做营销式 hero。读者一次只看一页。
- **每个工作流节点（N0 Settings 起，共 7 个节点）按同一套页面铺开**。样板先用 N0 的一个切片（API Keys）跑通全套页型，认可后铺满。

## 1. 页面体系：两级总览 + 五类节点页

整本手册分**两级**，和「后端实施手册」的 S0 总章对齐（先交代环境 / 波次 / routine，再进具体节点）：

- **手册总览（S0）**：全局一张，是**阅读坐标**——边界、要对接的三后端、**实施环境 / 实施顺序（波次）/ 实施 routine / 方法论三原则**、7 个节点的入口。
- **每个工作流节点**：由**一张节点主页 + 五类节点页**组成；五类页**按本质分类，不按体积**（铁律，见 §2 规则 3）——分的是「这页回答哪种问题」，不是「这块内容大不大」。

| 页型 | 层级 | 回答的问题 | 一句话定位 |
|---|---|---|---|
| **手册总览 S0** | 手册级 | 整本怎么读、对接哪几个后端、在什么环境 / 顺序 / routine 下推进 | 阅读坐标：环境 / 波次 / routine / 方法论 + 7 节点入口 |
| **节点主页** | 节点级 | 这个节点是什么、拆成哪几页、整体两轴状态 | 节点入口：N 页导航 + 状态汇总 |
| **设计页**（每个 surface 一张） | 节点级 | 这个页面 / 壳层上**每个操作应该怎么设计** | 稳定的「正确设计」，不写动态进度 |
| **后端接口契约页**（机制页） | 节点级 | 本节点依赖的后端机制 / 接口契约**应该**长什么样 | 契约设计 + 后端实现状态（实现不归我们）|
| **前端复用模块页** | 节点级 | 本节点内被多操作 / 多页面复用的前端组件登记处 | 一处登记，各操作 chip 链进来复用 |
| **实施页** | 节点级 | 前端**现状**、和设计**差**在哪、按依赖**先做什么** | 动态的现状 / 差距 / 计划 |
| **测试页** | 节点级 | 怎么验证「实现 == 设计」，两层测试 | 业务逻辑静态测试 + e2e 真实测试 |

> 「设计页」和「实施页」必须分开。否则读者会把「当前现状」误当成「正确设计」。设计页只讲应该怎样（稳定），实施页只讲现在怎样、要改什么（动态）。这是从后端方法论继承下来的硬规则。

> **导航铁律**：左侧导航**照搬原手册结构**（S0 总览 + 7 个节点组，每组 = 可点 parent + child-list + 状态点），**不自造**新结构。子页标签**逐字等于该页正文标题**（如「N0.1 Settings 壳层 · 操作设计」）——导航和标题不一致，读者就对不上号。整本手册生成进**一个固定文件 / 一个固定 URL**（`temp/index.html`，局域网根路径），每次重建覆盖同一处，不另起文件名。

### 1.0 一个关键的二分：操作设计页 vs 大机制设计页

「设计」有两种粒度，对应**设计页里的原子卡**和**单独的机制页**：

- **操作设计**：一个用户操作（如「进 API Keys 页看到自己存过的 key」）的前端设计，是设计页里的**一张原子卡**。
- **大机制设计**：当一个操作背后牵涉一整块复杂后端机制（如「凭证录入 → 落盘 → 取明文 → 6 态投影」整条链），这块机制单独开一张**机制页**详讲，操作卡只「引用」它（一条指针），不把机制塞进操作卡。

判据：**它是「一个操作的前端逻辑」还是「一块能被多个操作共享的后端机制」？** 前者进设计页原子卡，后者开机制页。

### 1.1 手册总览 S0 · 固定骨架

S0 是整本的阅读坐标，对齐后端手册的总章。固定区块（缺一不可）：

1. **边界 + 读法**：这本只管**前端**、按 7 节点组织；后端实现不归我们、只写契约。一句「先看环境 / 顺序 / routine / 方法论，再进节点页」。
2. **架构基础**：前端要对接**哪几个后端**（见 §4.4 三后端口径），每个后端 = 什么、管什么。**用卡 / 紧凑表，不用长散文**。
3. **实施环境**：Worktree、Branch、**本手册怎么重建**（生成器 → 固定文件 / URL）、权威 spec 路径、后端进度手册链接。让接手的人一眼知道自己在哪、改完怎么看。
4. **实施顺序（波次）**：当前进度（哪些节点已铺开 / 待深化）+ 推进顺序（按工作流 N0 → N6）+ **后端先于前端**铁律。
5. **实施 routine**：每页怎么落地的固定循环（读设计 → 写两层测试先红 → 按契约实现 → 跑 focused gate → 真机验收 + 收口）。见 §5。
6. **实施落地方法论**（精简 4 条，讲前端怎么正确落地、不是怎么写本手册）：先认契约与设计本体 / 前端只投影不自存 / 证据闭环验收 / 复用不自造撞墙不空转。（本文件本身是「怎么写手册」的编写方法论，与 S0 上的「怎么落地」方法论是两回事。）
7. **7 节点入口**：每节点一张卡（状态徽章 + 该节点页面链接）。

### 1.1b 节点主页 · 固定骨架

每个节点一张**主页**（父节点可点进来的落地页，如 `n0_overview`），是该节点的目录入口。固定区块：

1. **节点 intent**：这个节点解决什么、覆盖哪几个 surface（壳层 + 哪些页 / tab）。**一句话** + 一行边界。
2. **本节点 N 页导航**：每张子页一张卡（标题可点 + 一句「这页讲什么」），覆盖 5 设计 + 契约 + 复用模块 + 实施 + 测试。
3. **两轴状态汇总**（见 §4.2）：前端实施轴（N 符合 / N 偏差 / N 未实施）+ 后端契约轴（就绪 / 缺口）。**数字独立可扫读**，不糊成一段散文。

### 1.2 设计页 · 固定骨架

**一个 surface 一张设计页**（壳层一张 + 每个设置页 / tab 各一张），这些页**并列、非递进**——不要用「stage / 第 N 步」这类递进措辞，它们之间没有先后依赖。标题取「N{节点}.{序} {页面名} · 操作设计」（如「N0.1 Settings 壳层 · 操作设计」「N0.2 General 设置页 · 操作设计」），**与左侧导航逐字一致**（见 §1 导航铁律）；看标题就知道这页讲的是那个页面上的全部操作。

设计页是**一串原子卡**（每个用户操作 = 一个「设计原子」= 一张卡），外加页末的「本页前端模块分类」。每张原子卡固定字段：

| 字段 | 内容 | 对应数据 key |
|---|---|---|
| 操作名 + 两个状态徽章 | 操作叫什么；右上：前端实施状态 + 后端契约状态 | `func` / `fe_status` / `be_status` |
| 触发动作 | 用户怎么触发（点哪、自动触发还是按钮） | `action` |
| 前端设计 | 这个操作前端**应该**怎么走（数据流用箭头串清楚） | `fe_design` |
| 前端模块 | 用到哪些可复用前端模块（chip 指针，指向模块页/机制页） | `fe_modules` |
| 后端契约 | 对接哪条后端接口（端点 + 一句用途，指针指向机制页接口表） | `be_contract` |
| 现状偏差 | 一句话差距 + 指向实施页的指针 | `gap_brief` / `impl_ref` |

页末固定一块**「本页前端模块分类」**：按本质分两类——① 可复用前端模块（进模块页登记处）② 后端机制的前端侧（登记在机制页）。**用分类卡，不用裸 `<ul>` 堆长句**（见 §2 规则 4）。

### 1.3 机制页 · 固定骨架

机制页详讲一块**大后端机制的前端侧 + 后端实现状态**。固定区块：

1. **overview**：这块机制是什么、为什么单独成页、代码主要落在哪个后端。
2. **子模块**：把机制拆成几个子模块，每个一张卡（它是什么 / 职责 / 偏差）。**子模块的「功能」是卡内字段，不另起并列卡**（见 §2 规则 5）。
3. **数据文件**：从**前端视角**写——前端通过哪条 API 读/写，schema 有哪些字段。**不写后端怎么落盘**（见 §2 规则 6）。
4. **接口（契约）**：所有 HTTP 接口，**分类 + 结构化**（见 §2 规则 7）：数据 CRUD 接口 vs 触发真实调用的动作接口分开；每条用结构化字段（用途 / 请求 / 响应 / 实现）。
5. **边界**：这块机制做什么 / 不做什么（做/不做二元对照）。
6. **状态与错误**：状态枚举（如 6 态）、状态合成规则、错误码。「条件 → 结果」一律用同一种画法（见 §3 与 §2 规则 4）。
7. **后端实现状态**：每条后端能力的实现进度（已实现 / partial / 契约要改），**引后端实施手册标注**（见 §4.3）。

### 1.4 实施页 · 固定骨架

1. **逐功能现状卡**：每个设计原子一张卡，固定字段——**现状**（current，带证据，按名引用见 §2 规则 8）/ **差距**（gap）/ **后端依赖**（be_dep）/ 指回设计页的指针。
2. **实施计划**：按**依赖排序**的步骤；每步标「前端独立」还是「等后端」；步骤颗粒度要让「谁阻塞谁」一眼看清（别把多件不同依赖的后端事打包成一步）。

### 1.5 测试页 · 固定骨架（两层测试，见 §2 规则 9）

逐功能一张测试卡，每卡两层：

1. **layer1 · 业务逻辑静态测试**：mock 掉外部依赖，RED→GREEN 用例（断言数据流、调用次数、字段值）。
2. **layer2 · e2e 真实测试**：鼠标点界面、看状态流转、截图。**涉及真连通的，必须用真 key 真模型真跑一次**（『测试通过 ⟺ 真能用』）。
3. **预期截图**：每条一行占位（`📷 说明` + `截图待贴` chip），未来贴真图。
4. **覆盖检查**：每个测试**对应到设计原子**（atoms 字段），页面给一个「N 个原子各有两层测试」的全覆盖检查。

## 2. 内容编写规则（10 条，每条带正例/反例）

这 10 条是审查报告里反复挑出的问题沉淀。写完每个字段，对照检查。

### 规则 1 · 术语必带解释，禁用内部代号

每个**函数 / 类 / 文件 / 功能名**，第一次出现要紧跟一个括号，一句话说清它**具体干什么**。读者看不到代码，光给名字 = 逼他去翻文件。同一份文档里反复出现的，首次解释即可。

- **禁用无解释的内部代号**：`③a`/`③b`/`D6`/`12D`/`维度 6`/`femod-x` 这种代称，第一次出现必须展开成「它是什么」。
- ✅ 正例：「`hydrateEndpointSecrets`（api/llm.ts 里把掩码 key 换回明文的函数）会对每个掩码 endpoint 各发一次 secret 请求」
- ❌ 反例：「`hydrateEndpointSecrets` 会处理 endpoint」（没解释它干什么）
- ❌ 反例：「draft 蓝态真探（其维度 6 仍 partial）」——「维度 6」是后端手册的内部代号，没展开。
- ✅ 修正：「draft 蓝态真探（后端 D6『六态投影/证据库』维度里这一子项仍 partial）」
- ❌ 反例：常量截短成 `CURATED_PROVIDER_KIND`，真名是 `CURATED_PROVIDER_KIND_BY_ENDPOINT_ID`，照名搜不到。**名字要写全**。

### 规则 2 · 从文档自身视角写，不从对话上下文写

正式说明书里**不能出现只有看过聊天才懂的表述**：「你最初让我参照的那本」「为什么不并进 X」「就是你最初让我做的那个」。第一次读这份文档的人不知道「你」是谁、「最初」指哪次对话。

- ❌ 反例：「『后端实施手册』就是**你最初让我**参照的那本后端优化手册。」
- ✅ 正例：「『后端实施手册』指《Studio MVP1 后端 12 维度修复框架》，本手册引用它来标注每条后端契约的实现进度。」
- **不要用「为什么不是 Y」来解释分类**。靠「按本质分类」让区分**不言自明**——读者看到分类轴就懂为什么 A 在这、B 在那，而不是靠你回答「为什么 A 没并进 B」。

### 规则 3 · 按本质分类，不按体积

分类轴是「**它是哪种东西**」，不是「简单/复杂、大件/小件」。

- **坏轴**（禁）：「这个模块小，放一起；那个大，单独开页」。
- **好轴**：纯逻辑工具集 / UI 组件 / 后端机制的前端侧 / 绑定某操作的业务逻辑——按**职责归属**分。
- **可复用的进登记处**（模块页）；**绑死某一个操作的不算「模块」**，它只是那个操作卡内的逻辑。
- ✅ 例：`provider-utils`（一组无状态纯函数）= 「纯逻辑工具集」；`RoleNameDialog`（跨节点复用的命名弹框组件）= 「共享 UI 组件」；`凭证 hydration`（后端取明文机制的前端调用侧）= 「后端机制的前端侧」，登记在机制页。

### 规则 4 · 结构化优先，prose 不塞表格

- **表格只放「每格都简练」的数据**（owner 矩阵、状态码、接口字段名）。带说明、超过两句的因果解释，**不许塞进单元格**。
- 带说明的内容用**卡 + 字段 / 列表**；逻辑链用**箭头 / 序号**，不糊成一段散文。
- ❌ 反例：架构表第三列单元格写整句强调说明（「模型调用：凭证、协议探测、路由、6 态、materialize。设置页主要对接它。」）——逼近 prose 塞表格红线。
- ✅ 修正：表格列压成短词组（「凭证/探测/路由/6态」），展开解释挪到表下一句正文；或整体换成 3 张卡（每个后端一张，卡内两行字段）。
- ❌ 反例：状态汇总写成一句话散文「16 个操作 = X 符合 / Y 偏差…」——有结构的数据糊成散文，读者要从句子里抠数字。
- ✅ 修正：拆成计数 chip，前端轴三个数、后端轴两行，独立可扫读。
- ❌ 反例：「本页前端模块分类」用裸 `<ul>` 列两条塞满 xlink 的长句。✅ 修正：做成两张轻量分类卡。

### 规则 5 · 一个对象 = 一张卡，属性 = 卡内字段

一个对象（模块、操作、接口）= 一张卡；它的子部分（模块的「功能」、操作的「触发动作」）是**卡内字段**，**不另起一张并列卡**。

- ✅ 正例：模块卡里「功能（3 条）」是卡内一个 `spec-row`，value 是有序列表。模块的功能没有被拆成和模块卡并列的另一张卡。这是层级正确的标杆。
- ❌ 反例：把模块的每条功能拆成和模块卡平级的独立卡——层级错乱，读者分不清谁从属谁。

### 规则 6 · 数据文件从前端视角写

后端给读写 API 就到此为止。**落盘在哪、怎么落（原子写、0600 权限、迁移函数）是后端实现细节，前端不关心**。

- 讲清「**前端 ↔ 后端 API**」的逻辑关系：前端通过哪条接口读、哪条写、拿到的 schema 长什么样。
- ❌ 反例：在数据文件页罗列后端的原子写、文件权限、v3→v4 迁移内部逻辑。
- ✅ 正例：「前端通过 `GET /api/llm/registry`（拉全量打码快照）读、`PUT …/endpoints`（写 endpoint）写；schema 顶层是 `LLMCredentialsFile`（凭证文件根对象），含 endpoints / routes 两组。」schema 字段用标签云列，敏感字段（api_key）高亮置顶。

### 规则 7 · 接口要分类、要结构化、不重复

- **分类**：数据 CRUD（读写数据，幂等）vs 触发真实调用的动作（点 Test 真发模型请求、真探测）——**两组分开**。
- **结构化**：每条接口用固定字段——**用途 / 请求 / 响应 / 实现**。不写成一段话。
- **不重复**：数据文件卡**不重列接口**，用指针指向接口表那条；接口表是接口的唯一真相源。
- ❌ 反例（来自审查）：用分组颜色给「动作类」接口染上琥珀警告色——琥珀在本手册=偏差/警告，会让读者误以为这组接口有问题。分组靠**标题**区分，不靠语义色（见 §3 一色一义）。

### 规则 8 · 不写行号，按「文件名 + 函数/对象名」引用

行号会漂（审查实测：`api/llm.ts` 整体漂移约 +22 行，因为文件前部插了行没回填），嵌套路径也容易错。

- **引用格式**：`文件名 + 函数/对象名`，让实施 agent 直接 grep 名字定位。
- ✅ 正例：「`api/llm.ts` 的 `hydrateEndpointSecrets`（把掩码换明文的函数）」
- ❌ 反例：「`api/llm.ts:1147`」——一旦文件前部增删行，1147 就指错地方。
- **路径要写全且分类校准**：审查实测前端 settings/api-keys 系列文件真实路径在 `components/studio/` 下（如 `components/studio/api-keys/ProviderCard.tsx`），而 `api/` 系列在 `src/api/`——**不是一刀切加前缀**。要么逐类把完整相对路径写对，要么显式声明每一类的 base。照错的 base 去找 = 一个文件都找不到 = 零黑盒目标直接破功。
- **后端引用别张冠李戴**：引证据时确认这个函数真在你说的那条调用链上。审查实测：`models/test` 的官/三分叉在 `test_endpoint_models` 里，却被错引成 role-test 路径的 `_ensure_official_role_test_verified_profile`——结论对、证据指错函数，会误导后端去改错地方。

### 规则 9 · 测试两层，对应设计原子，全覆盖

- **layer1（业务逻辑静态测试）**：mock 外部依赖，RED→GREEN。断言数据流、调用次数、字段值。偏差项的 layer1 是 RED（未实现），待转 GREEN。
- **layer2（e2e 真实测试）**：鼠标点界面、截图页面/标签/toast 状态。**涉及真连通必须真 key 真模型真跑一次**——『测试通过 ⟺ 真能用』，不接受「能开机」式 smoke 降级（见 §2 规则……即降级=偷换目标）。
- **每个测试对应到设计原子**（atoms 字段），并给**全覆盖检查**（N 个原子各有两层测试）。
- **截图用一行占位**（未来贴真图），不留空。
- ❌ 措辞反例：「16/16 全覆盖」——「全覆盖」易被读成「全通过」，但偏差项 layer1 还是 RED、layer2 还是「截图待贴」。✅ 修正：「16 个设计原子各配两层测试**方案**；偏差项为 RED 待转 GREEN，截图待真跑回贴」。**避免「全/只/都」这类绝对词**（覆盖≠通过）。
- ❌ 时点反例：对偏差项（功能还没实现成目标形态）的 layer2 写「真跑」，没区分「现在真跑的是旧路径」vs「目标路径待实现后再真跑」。✅ 修正：注明「目标形态落地前先对现状路径真跑取证，落地后重跑」。

### 规则 10 · 大段叙述拆成结构化 list，不糊成一团

任何**超过 2~3 句**的字段值，都不能是一坨连续文字。先判断它的内在结构，再选拆法：

- 是一连串**有先后的步骤**（A 然后 B 然后 C）→ 编号列表 / `flow`。
- 是一组**并列要点**（无先后）→ 项目符号列表。
- 是**结论 + 证据/细节** → 结论先行（第一项就是结论），细节逐条 bullet。

一条 list item = **一个原子点 / 一步**，别把 5 句塞进一个 bullet。判据：读者能不能**扫着 bullet** 找到他要的那一点？能 → 拆对了；还得**通读整段**才找到 → 没拆够。

- ✅ 正例：实施页「现状」从『进页走 `getCredentials` → 先 `getRegistry` 拿打码快照 → 再 `hydrateEndpointSecrets` 换明文 → 写本地缓存 → 下次命中缓存不重发』五步，拆成 5 个 bullet，一眼看出有几步、每步干啥。
- ❌ 反例：同样内容写成一个 120 字、句号连成的段落，读者要从头读到尾才知道有几步。
- **工程上**：内容数据里这类字段，要么直接写成数组（一项一步），要么在渲染层按句号 / 分号切成 list（样板生成器的 `listify()` 就是干这个——单句保持 prose，多句自动拆 list）。但**切分点要落在语义边界**（句号、分号、「→」串起的步骤），不是机械按字数断。

### 规则补 · 降级 = 偷换目标（禁）

把「验证真能用」偷换成「能开机」、把「完整实现」偷换成「最小切片」、把「真跑真 key」偷换成「mock 一下」= 拿便利压目标 = 作废。**需求/设计写什么做什么**。验证用真资源，别拿「没凭证/不能碰」当挡箭牌（真 key 在 `.env` / 真凭证库里就用）。

### 规则补 · 可自查的事别留「待确认」

「待确认 / 待验证」常是把一个**打开文件就能查证的事实**留成了悬置。审查实测：「需确认 registry DTO 是否已内嵌 ui_state」——这是打开响应模型就能查死的。**核实优先于留悬置**：能自己查的查死，写「已内嵌 / 未内嵌」，别在交付文档里留「待确认」。否则会出现「徽章标 ok 却 note 说没确认」的两轴不自洽。

## 3. UI 展示规则（组件决策表 + 一色一义）

> 本节是 `temp/ui-component-logic.md`（已定稿的 UI 契约）的浓缩。核心洞察：**手册里绝大多数「卡」都是同一个东西**——一个标题 + 右上角最多一个标签 + 若干字段。它们不该是 8 个 class，而是 **1 个主组件 `card`**，靠数据参数化。

### 3.1 唯一主组件：`card`

```
┌─────────────────────────────────────────────┐
│  标题（左）                    [标签]（右上，可选，≤1）│
├─────────────────────────────────────────────┤
│  字段标签 ： 字段值（值可为 prose / 列表 / 标签 / 子网格）│
│  …                                            │
└─────────────────────────────────────────────┘
```

`card(title, fields[], tag=None, accent=None)`。下面这些「看起来不同的卡」**全部塌成 `card`**：模块卡、数据文件卡、接口卡、后端契约引用、实施步骤、后端实现状态、6 态定义、模块登记卡、导航卡、reason_code。一个 `card` 样式，视觉一致、维护一处。

> 这正面回应了审查里最系统性的病：`.contract` 一个 class 被复用成 3 种结构完全不同的东西（真接口卡 / 设计页契约引用 / reason_code 卡），共 31 处。**同组件必须表达同一种展示**；不同功能不许共用同一组件。

### 3.2 7 种「不是 card」的场景 → 组件决策表

只有下面这些**不是**「标题+字段」，才用专门辅件。写新内容先问：**它是「标题+几个字段」吗？** 是 → `card`。不是 → 在此表对号入座。再不行才考虑新组件（极少）。

| # | 场景（它是哪种东西） | 用组件 | 为什么不能是 card |
|---|---|---|---|
| 1 | 多张 card 并排布局（6 态网格、做/不做两栏） | `card-grid`（N 列包裹器） | 它是**布局**，里面装的还是 card |
| 2 | 线性有序步骤 / 数据流（录入→落盘→…） | `flow`（编号圆点 + 连线） | 强调「顺序 + 串联」，靠连线 |
| 3 | **条件 → 结果**的判定行（6 态合成、错误码短路、reason_code 释义） | `rule`（条件 ┃→┃ 结果） | 强调「→」，横向二元，不是字段表 |
| 4 | 数据结构 schema（字段名+类型+含义一堆） | `tags`（field/struct 标签云） | 一簇小标签，不是几行字段 |
| 5 | 形态变换图（1→N、A→B） | `diagram` | 要「看图」才懂 |
| 6 | 提示 / 边界声明 / 导读 | `callout`（蓝/琥珀/绿） | 无标题的整块提示 |
| 7 | 真·表格（每格都简练） / 有序要点 / 截图占位 / 行内标签 | `table` / `list` / `shot` / `badge` | 二维数据 / 字段的值 / 一图一行 / 就是右上那个标签 |

> 全清单：`card` + `card-grid` + `flow` + `rule` + `tags` + `diagram` + `callout` + `table` + `list` + `shot` + `badge`。一个主组件 + 10 个各司其职的辅件，**没有重复**。
>
> **关键收敛**：所有「X → Y」映射（状态合成规则、reason_code→含义、错误码→是否短路）**统一用 `rule`**，不要一处用三列网格、一处用单格卡、一处用 callout 里的 `<ul>`（审查里这是「同一类映射三种画法」的系统病）。

### 3.3 两个特殊展示：数据结构 schema · 形态变换图（表里第 4、5 行的展开）

这两种内容**最容易被写糊**，单独立规矩。

**A. 数据结构 schema → 字段标签云（`tags`），不是 prose、不是大表**

一份数据结构（如 `llm_credentials.json` 的 schema）= 一组「字段名 + 类型 + 一句含义」。展示成**标签卡**：每个字段一张小标签（`field`），标签内 = 字段名（mono）+ 类型（小胶囊）+ 含义（小字）；同一个子结构（如 `ProviderEndpoint`）的字段归到一个 `struct` 盒里。

- **敏感字段高亮置顶**：密钥类（`api_key`）加 🔒 + 红框，排在最前——读者一眼看到「哪个字段是机密」。
- ❌ 反例：把 30 个字段写成一段「`schema_version` 是版本号，`provider_endpoints` 是端点表，`provider_routes` 是……」的话——读者数不清有几个字段、找不到某一个。
- ❌ 反例：30 个字段塞进一张 30 行的表格，每行含义又是一句话——回到「prose 塞表格」红线。
- ✅ 正例：标签云，按 struct 分组，扫一眼就知道「这个结构有哪些字段、哪个敏感」。

**B. 形态变换图（`diagram`）→ 仅当「文字讲不清形态变化」时才画**

图示是**高成本组件**，不是装饰。判据：这块内容是不是一个「形态变换」（一个东西**变成**另一个东西，且形状/数量变了），且**文字讲不清**？是 → 画图（左边输入、箭头、右边输出）；否 → 别画，用文字/列表。

- ✅ 该画：「一把 key + 多个 URL」→（拆分 + 逐协议探通）→「平铺的 endpoint 列表」，其中「一个 URL 通两协议 → 两个 endpoint」这种 1→N 关系，纯文字绕。
- **公式只出现一次**：变换的定义公式（`endpoint =（base_url × 协议）`）写在卡里的「核心定义」字段**一处**，**不要**在图里再重复一遍（审查实测：同一公式图里图外各一份 = 冗余）。
- **图里用中性色，不蹭语义色**：图里的框/标签用中性或与代码一致的青色，**不要用语义绿/红**（绿在本手册=ready/成功，拿来给图框上色会误导）。

### 3.4 配色：一色一义（铁律）

| 色 | **唯一**语义 | 用在 |
|---|---|---|
| 🟢 绿 | 好/通过：成功 · ready · 符合设计 · 前端独立 · 「做」 | card 状态标签、ready 态、做/不做的「做」、前端独立步 |
| 🔴 红 | 坏/否：失败 · 不做 · 未实施 | failed 态、「不做」、未实施标签 |
| 🟡 琥珀 | 未决/警示：偏差 · 等后端 · partial · 注意 | 偏差标签、等后端、警示 callout |
| 🔵 蓝 | 中性信息/强调/装饰：链接 · 覆盖 · 归属 · 信息 | 链接、覆盖 chip、归属标签、信息 callout |
| ⚫ 灰 | 中立/停用：off · 禁用 · 类型标签 | off 态、「东西类型」类标签 |

铁律：**一色一义**。装饰性的绿（如「已覆盖」chip）降级为蓝，绿只留「成功/符合/做」。同一个语义的绿，用同一个 CSS 变量，别并存多个相近绿值。

**踩过的坑（必避）**：
- **每个 badge 变体必须在 CSS 有定义**。审查实测 `badge.ob`/`badge.ofe` 没定义 → 渲染成透明无底色裸徽章，和别处有底色徽章风格割裂。这是事实 bug，不是观感偏好。
- **别借语义组件再 inline 改色**。审查实测：测试页拿「做/不做」的 `bound-col.dont`（红框红字，语义=「不做」）装「①静态测试/②e2e」，再用 inline style 把红硬改成绿——组件选错 + 配色 hack。两层测试不是「做/不做」语义，应改用中性两栏或竖线分节小标题。
- **同一概念同一页只用一套画法**。审查实测「两层测试」在顶部用两栏卡、在逐卡用竖线小节——同概念两套骨架，认知不连贯。统一成一套。
- **窄屏要有断点**。三列网格（`rule`/状态网格/接口网格）在窄屏会挤爆，统一补 `@media` 降为单列/两列。

## 4. 引用与溯源规则

### 4.1 按名引用，不写行号

见 §2 规则 8。复述要点：函数/对象/文件**按名引用**让 agent grep；路径写全且分类校准；后端证据别张冠李戴。

### 4.2 两轴状态（解决「全绿却标黄」的不自洽）

每个操作/能力同时挂**两个独立状态轴**，分别回答两个不同问题：

| 轴 | 回答 | 取值 | 来源 |
|---|---|---|---|
| **前端实施状态** | 前端代码和设计一致吗 | 符合 / 偏差 / 未实施 | 读前端代码对照设计 |
| **后端契约状态** | 这条后端契约后端实现了吗 | 已实现 / 未实现 / 契约要改 | 据后端实施手册 |

前端实施状态汇总成**页面色**（如这页大部分符合 → 绿）。两轴分开才能表达「前端这块写对了（前端轴=符合），但它依赖的后端契约还没实现（后端轴=未实现）」——避免「前端全绿却因为后端没好而被迫整页标黄」的不自洽。

> 自洽性检查：徽章和 note 别打架。别出现「徽章 ok」配「note 说待确认」。能查死的查死（见 §2「可自查的事别留待确认」）。

### 4.3 引后端实施手册标注后端状态

后端能力的实现进度，**引用后端实施手册**（《Studio MVP1 后端 12 维度修复框架》，`temp/studio-mvp1-12d-repair-framework-2026-06-15.html`）标注，不自己拍。引用时：

- **客观陈述它是什么**（见 §2 规则 2），不写「你最初让我参照的那本」。
- 引它的某个维度时，**展开维度含义**（见 §2 规则 1），不写裸的「D6」「维度 6」。
- 注意它是 JS 动态渲染的单页，锚点（如 `#d6_overview`）运行时才生成——链接能解析但静态看 HTML 时锚点不存在，属可接受的脆弱性，知道即可。

### 4.4 架构口径（易错，必须统一）

**前端只对接 Python sidecar 暴露的 HTTP API。** 前端认**三个后端**：

| 前端要对接的后端 | = 什么 |
|---|---|
| **gateway 后端** | gateway SDK + Python sidecar 暴露的 gateway API（凭证、协议探测、路由、6 态、materialize）。设置页主要对接它。 |
| **engine 后端** | 运行/编排相关的 engine API。 |
| **Studio Rust 后端** | `apps/studio/tauri`（桌面 shell 侧）。 |

**铁律：不存在独立的「Studio 后端」层这种表述。** `apps/studio/backend`（Python sidecar）是「gateway 后端」的 HTTP 壳/承载层——**全手册统一这么叫**。审查实测的坑：同一份 `services/llm_credentials.py` 在总览叫「gateway 后端」、在机制页叫「studio-backend」，口径两页不一致，读者误以为有第四层。凡写到 sidecar 侧代码，统一括注「（即 gateway 后端的 sidecar 侧）」，不引入第四层。

## 5. 工作流：计划 → 审计 → 实施 → 审计

每个页面单元（或一批不冲突的页面），强制走四步，一步不跳：

1. **实施前计划（Plan）**：动手前写出方案——这页改哪个 JSON、加哪些字段、数据流怎么走、对接哪些契约。计划落进文档，不靠对话记忆。
2. **实施前独立审计（Pre-audit）**：派一个 **subagent 独立审计**该计划是否符合 **MVP1 + 三类页设计**（本方法论 + spec 是最高裁判）。审计 subagent 拿到：计划全文 + 相关设计文档路径 + 现状。判定 conform / deviate；deviate 要指出偏了哪条。没过 → 先改计划，不带着已知偏差往下做。
3. **实施（Implement，可并行）**：规划**不冲突**的页面任务（不改同一 JSON、不踩同一契约），派不同 subagent 同时做；冲突的串行。
4. **实施后独立审计（Post-audit）**：再派 subagent 独立审计已落地内容是否符合设计。通过 + 门禁绿（DOM 渲染 / 禁词 / 导航 / 截图检查）→ 才算这页「处理过一遍」。

**后端先于前端**：后端契约（gateway/engine API 形态）没定下来，别先写依赖它的前端页——否则返工。本手册里体现为：先把「后端契约 + 后端实现状态」写清，前端设计/实施再对齐这个契约。

**子 agent 用法**：
- subagent 只产**草稿 / 审查 finding**，**不直接改最终产物**（HTML/生成器/数据 JSON 由唯一整合者改）。
- 主线程是 gatekeeper：subagent 自述「符合设计/测试通过」一律**自己独立复核**（重跑门禁、读 diff），不信转述。
- 多人不许同时改同一份 HTML/JSON。

**沿用已有 UI 组件**：前端真实 UI 改动用已有组件和风格（能用 shadcn 就用 shadcn），不自造组件。手册侧组件用 §3 那套 `card` + 10 辅件，不新增。

## 6. 自检清单（写完一页 / 一个区块前逐条过）

**内容（对照 §2）**
- [ ] 每个函数/类/文件/功能名第一次出现都带括号解释了吗？有没有裸的内部代号（D6/③a/femod-x）？
- [ ] 有没有对话视角表述（「你最初让我」「为什么不并进 X」）？
- [ ] 分类是按本质（哪种东西）还是按体积（大小/简单复杂）？
- [ ] prose 有没有塞进表格单元格？带说明的内容是不是该用卡/列表？
- [ ] 超过 2~3 句的字段拆成 list 了吗？还是糊成一坨？list 一项一个原子点了吗？
- [ ] 一个对象一张卡了吗？属性是卡内字段、还是被错拆成并列卡？
- [ ] 数据文件是从前端视角（前端↔API）写的吗？有没有混进后端落盘内部细节？
- [ ] 接口分类了吗（CRUD vs 动作）？每条结构化（用途/请求/响应/实现）了吗？文件卡有没有重列接口？
- [ ] 引用是「文件名+名字」还是行号？路径前缀分类校准了吗？后端证据有没有张冠李戴？
- [ ] 测试两层都有吗？每个测试对应到设计原子了吗？全覆盖检查在吗？涉及真连通的有没有要求真 key 真跑？截图一行占位了吗？
- [ ] 有没有「全/只/都」绝对词？有没有把可自查的事留成「待确认」？有没有把目标降级成 smoke/最小切片？

**UI（对照 §3）**
- [ ] 这块是「标题+字段」吗？是 → 用 `card`，没用别的同义 class 吗？
- [ ] 同一场景全手册用了同一个组件吗（没有「接口卡/契约引用/reason_code 共用一个 class」这种）？
- [ ] 所有「X→Y」映射都用 `rule` 了吗（没有三套画法）？
- [ ] 配色一色一义吗？绿只表「成功/符合/做」吗？装饰性绿降蓝了吗？
- [ ] 用到的每个 badge 变体在 CSS 都有定义吗（没有透明裸徽章）？
- [ ] 有没有借语义组件再 inline 改色的 hack？
- [ ] 三列/两栏网格补窄屏断点了吗？

**溯源 / 两轴（对照 §4）**
- [ ] 两轴状态都标了吗？徽章和 note 自洽吗（没有 ok 配「待确认」）？
- [ ] 后端状态引后端实施手册了吗？引用客观、维度展开了吗？
- [ ] 架构口径统一吗（三后端、没有第四层「Studio 后端」、sidecar 统一叫 gateway 后端的承载层）？

**流程（对照 §5）**
- [ ] 走了 计划→pre-audit→实施→post-audit 吗？门禁（DOM/禁词/导航/截图）绿吗？

## 7. 高频坑 Top 10（两份审查里反复出现，最该警惕）

把两份审查报告里**反复出现的问题类型**归纳如下，按出现频率/严重度排序。这是最该先扫的清单。

| # | 坑（问题类型） | 来源 | 一句话避坑 |
|---|---|---|---|
| 1 | **同一 class 被复用成多种结构不同的东西**（`.contract` = 真接口卡 / 契约引用 / reason_code，共 31 处） | UI 审查 U1/D1/M3/M5 | 不同功能不共用组件；都是「标题+字段」就统一 `card`，否则各起专名 |
| 2 | **路径/行号漂移失准**（前端缺 `components/studio/` 前缀照着找不到；`api/llm.ts` 行号整体漂 +22） | 内容审查 系统性#1/#2 | 不写行号、按名引用；路径写全且分类校准 base |
| 3 | **「X→Y」映射多套画法**（投影规则三列网格 / reason_code 单格卡 / 错误码 callout-ul） | UI 审查 U2/M5/M6 | 所有条件→结果统一用 `rule` |
| 4 | **未定义的 badge 渲染成透明裸徽章**（`badge.ob`/`badge.ofe`） | UI 审查 U3/M1/F1 | 每个 badge 变体在 CSS 必须有定义 |
| 5 | **架构口径页间不统一**（同一 sidecar 代码一会叫 gateway 后端、一会叫 studio-backend，疑似第四层） | 内容审查 F1.2/F3.3 | 三后端口径全手册统一；sidecar = gateway 后端承载层，无第四层 |
| 6 | **借语义组件再 inline 改色的 hack**（拿红色「不做」组件装两层测试再强改绿） | UI 审查 U5/T1 | 选对语义组件，绝不 inline 覆盖语义色 |
| 7 | **绿色语义过载**（绿同时表 成功/符合/前端/做/已覆盖，多个相近绿值并存） | UI 审查 I2/T5/规则 | 一色一义；装饰绿降蓝，绿值统一成一个变量 |
| 8 | **对话视角 / 内部代号无解释**（「你最初让我参照的那本」「维度 6」「femod-x」） | 内容审查 F1.1/F1.3 | 客观陈述 + 术语第一次出现就展开 |
| 9 | **后端证据张冠李戴 / 名称截断**（models/test 分叉引到 role-test 函数；常量名截短搜不到） | 内容审查 系统性#3/F3.2 | 引证据先确认在该调用链上；名字写全 |
| 10 | **现状/目标同段未切分 + 绝对词 + 可自查留「待确认」**（「全覆盖」被读成全通过；「拉到目录即判通过」混现状与目标；DTO 是否内嵌写「待确认」） | 内容审查 F5.3/F5.4/F6.1 | 现状归实施页、目标归设计页；避绝对词；可查的查死 |
