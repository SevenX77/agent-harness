# 一、系统是什么

我们在做一个 "graph skill"(图技能)系统:
- 一个技能 = 一个有向无环图(DAG),由一个 `GRAPH.md` 文件定义。
- 图里有若干 phase 节点,节点分三类:**agent**(调用 LLM 的智能节点)、**logic**(纯 Python 确定性计算)、**subgraph**(整个节点其实是调用另一个子图技能)。
- 引擎接收"图 + 一份输入",按拓扑顺序把这个 DAG 跑一遍,产出最终结果。
- 图有一对端点:`input`(整图入口)、`output`(整图出口),它们和节点之间的依赖关系是分开的概念。
- 节点之间通过一块共享的"黑板"(blackboard / 状态机)传数据:上游节点把输出字段写进黑板,下游节点按自己声明的输入字段从黑板里取。

# 二、要加什么:声明式的 batch / loop 迭代

现在"迭代"是**手写 Python 硬编码**的(例:在一个 logic 节点里手写 `for` 循环、硬编码批大小=10、手动把每批结果攒进一个累积变量、手动调子技能)。我们要把它换成**声明式、可在节点或图上配置**的机制。

**batch 和 loop 是两个不同的机制:**
- **batch(并发 · 独立)**:对一组输入项并发跑,每项互不依赖、各跑各的。
- **loop(串行 · 累积)**:一项一项串行跑,**每次的输出进入下一次的输入**(带累积)。

**配置作用在两个层级(scope):**

1. **图级**(写在 GRAPH.md):**整个图**作为一个迭代单元。
   - 例:图有 3 个节点,图输入有 10 项,图设了 batch/loop 范围 3-6:
     - **batch**:并发跑第 3、4、5、6 项,每个并发进程**各自完整走一遍这 3 个节点**(4 个独立的整图运行)。
     - **loop**:第 3 项输入 → 走完 3 个节点 → 输出;第 4 项拿"第 3 项的输出 + 第 4 项的输入" → 走完 3 个节点 → …… 一直串到最后。

2. **节点级**(写在某个节点上):只有**那个节点**迭代。
   - 例:图没设,但第 2 个节点设了 batch/loop 范围 1-2:那就是第 2 个节点自己把第 1、2 项 batch/loop 跑掉,然后流程继续往下走第 3 个节点。

3. **嵌套**:图级和节点级都设 → 嵌套。每个图级进程走到第 2 个节点时,第 2 个节点先把自己的 batch/loop 跑完,再继续往下。父图设 10 次 × 子节点设 10 次 = 总共 100 次。

**另外**:子图节点(subgraph)上也能设 batch/loop,子图会"继承"这个参数但不写进子图自己的 GRAPH.md(即:父图用 batch/loop 调子图,子图本身只跑 1 次;若子图自己的 GRAPH.md 也设了,则嵌套)。

# 三、一个真实的复杂案例(说明为什么这事不简单)

一个"小说解构"技能,图输入 100 章小说:
- **节点1 分段**:每章独立、不依赖上一章 → batch 并发跑 100 章。
- **节点2 事件时间线**:第一步 batch 并发把每章合并成"事件";第二步把 100 章的事件合起来整合成**一条总时间线**(在章节断层处要判断是否需要合并)——这一步**必须 loop 一章一章往上拼,不能并发**。
- **节点3 解构分析**:里面是多个并行子节点(情绪节奏 / 时空元素 / 伏笔埋收 / 角色资产分析……,复杂的子节点本身又是一个子图);而且**迭代的粒度变了**——不再是"按最初的 100 章",而是"按事件"或别的字段来切。这里还有两种 loop 模式:
  - 模式①:各并行子节点**互不相关,各自独立** loop n 次;
  - 模式②:各子节点**相关,整体** loop n 次——每一轮里 7 个子节点全部跑完,下一轮每个子节点都要吃"上一轮全部 7 个子节点的结果"。

# 四、引擎现状(已核实)

- 引擎**能"并发跑一组"**:底层有 `asyncio.gather` 形式的 fan-out(目前用于并行子任务),所以"并发 fan-out"做得到。
- 但引擎**没有声明式的图级/节点级迭代**;loop 的累积现在完全靠手写 Python。
- 引擎现在的执行模型是"**把一个 DAG 跑一遍**",没有"把整图或某节点跑 N 遍并把状态串起来"的原生能力。

# 五、我没想通的难点(请重点设计)

1. **loop 累积态的结构、传递与持久化**:loop 时"下一次输入 = 上一次输出 + 当前项的原始输入"。但"上一次输出"具体该取什么(整个最终黑板?某个指定字段?)、怎么和"当前项输入"合并后喂给下一次?承载 loop 的那个单元(图或节点)的输入声明,怎么同时容纳"累积态"和"当前项"两部分?而且累积态要能**持久化**,以支持"从第 49 章已有的数据接着跑第 50 章"这种断点续跑——按什么粒度做 checkpoint、存成什么结构?

2. **迭代粒度沿着图在变**:图是按"章"进入的(范围 3-6 章),但深层节点是按"事件"迭代的(不再是章)。顶层这个"章范围"怎么传到一个按"事件"迭代的深层节点?不同 scope 的范围(图按章、节点按事件)怎么共存与复合?迭代的线索字段(到底按哪个字段切)是否应该让每个节点从它自己的输入数组里自动探测?

3. **图级 loop vs 节点级 loop 的执行与嵌套**:图级 = 整图当迭代单元(每轮跑完所有节点),节点级 = 单节点迭代。上面模式②"整体 loop,下一轮每个节点吃上一轮全部节点的结果"——这种跨节点的"全量结果回灌"怎么建模?batch×batch、loop×loop、batch×loop 嵌套时,状态怎么穿、次数怎么算?

4. **怎么落到"只会把 DAG 跑一遍"的现有引擎上**:图级迭代 = 把编译好的图跑 N 遍(并行,或串行带累积);节点级 = 把一个 phase 跑 N 遍。这个"迭代执行层"该怎么和现有的 DAG runner 集成?loop 的串行累积怎么嵌进现有的 phase 执行 + 黑板状态机里?
