## 0. 术语与本文的权威范围

### 0.1 术语(首次出现即用平白话解释)

| 术语 | 平白话解释 |
|---|---|
| **gskill** | 本项目的技能包格式与其内容:一个目录,里面用文档描述"这个流程有哪些相位(phase)、相位之间怎么连、每个相位读写什么数据"。用户写的就是它,引擎读的也是它。 |
| **相位(phase)** | 流程里的一个步骤节点。一个 gskill 由若干相位和相位之间的连边组成。 |
| **engine(引擎)** | 把一个 gskill 目录编译成可运行的图、并按图执行的纯软件开发工具包(SDK,即被别的程序调用的代码库,自己不开 HTTP 服务)。本仓内的位置是 `packages/graph-agent`。 |
| **gateway(网关)** | 掌管大语言模型(LLM)凭据、路由、注册表这些"配置真相"并把它们落成可用角色的纯 SDK。本仓内的位置是 `packages/graph-agent-gateway`。 |
| **studio** | 桌面应用外壳:一个 FastAPI 后端(`apps/studio/backend`)加一套 React 前端(`apps/studio/frontend`),把 engine 与 gateway 包成人可以点的界面。 |
| **AST** | 抽象语法树(Abstract Syntax Tree):把用户写的 gskill 文本解析成的结构化中间表示。它是编译期一切校验与生成的依据。 |
| **langgraph** | 一个把"多步骤 LLM 流程"表达成图并执行的开源框架,engine 用它作为图执行底座。 |
| **ReAct agent** | 一种让模型自己边想边挑工具、下一步做什么由模型临场决定的用法。它灵活但每次跑的路径可能不同。 |
| **tracing(追踪)** | 运行时把"每个相位收到什么、模型被怎么提问、返回什么、写回了什么"逐条记录下来,供事后逐步复核。 |
| **Effect(域级/模块级承诺)** | 一个域或一个模块**对用户或调用方承诺的可观察结果**:做成功时外部能观察到什么、失败时外部能观察到什么。它不是内部实现描述。 |
| **膜(membrane)** | 一个模块对外的那层契约边界,类比细胞膜:膜内实现怎么写是它自己的自由,膜外只能通过膜上声明的公开能力与它交互。膜上必须写清职责、输入输出、依赖、失败语义、生命周期。 |
| **Port / Adapter** | Port 是"稳定的抽象接口"(领域逻辑只依赖它),Adapter 是"针对某个具体外部环境的实现"(某个模型厂商、某个操作系统、某个进程管理器)。差异关在 Adapter 里,不渗进核心。 |
| **executor(执行者)** | 真正去"跑一个 AGENT 相位"的那一方。AGENT 相位需要一个能自主用工具的 agent 来完成,executor 就是提供这个 agent 的实现。 |
| **monorepo** | 一个代码仓库里放多个可独立发布的包。包边界与仓库边界是两件事。 |
| **原因码** | 一个稳定的、可被程序断言的失败标识字符串(例如 `[F-v3-graph-phase-node-missing]`),而不是一句给人看的自由文本。 |
| **门禁(gate)** | 在持续集成(CI)里必须通过、不通过就挡住合并的自动检查。 |
| **TDD** | 测试先行开发:先写出会失败的测试复现缺陷或定义新行为,再写生产代码让它变绿。 |
| **打包版** | 走完整发布打包链装出来的应用,而不是开发模式下临时拼起来的那一份。 |

## 1. 北极星(五条,2026-08-31 定稿)

**"北极星"指最高层的目的判据**:任何设计取舍、任何功能增删,最终都要回答"它服务哪条北极星、服务到什么程度"。五条并列,不排优先级;当两条在具体场景里互相拉扯,按 §2 的权威链逐层往下裁。

### 北极星-1 · 流程可靠、可重现

**要什么**:用 langgraph 把流程**钉成一张图**,跑一百次就是同样的一百次。这是本项目区别于纯 ReAct agent 的立身之处:纯 ReAct 每次的路径由模型临场决定,可靠性无法承诺;gskill 把"走哪些相位、按什么顺序、每步读写什么"固定在图里,模型只在每个相位内部发挥。

**判据**:同一个 gskill、同一份输入,应当走出同一条相位序列;差异只允许出现在相位内部的模型输出,不允许出现在流程结构上。

### 北极星-2 · 比直接写 langgraph 更简单、更不跑偏、更快

**要什么**:用户用**文档**描述流程即可,不必手写框架代码。三个可度量的好处:**写得少**(同一个流程,gskill 的篇幅显著小于等价的 langgraph 代码)、**偏移空间小**(用自然语言加结构化声明描述,让"随口写代码"式的自由发挥没有落脚处)、**上手快**(不必先学框架的类与回调体系)。

**反向判据(这条北极星的否决权)**:任何功能,如果它让用户**比裸写 langgraph 还累**,那这个功能就是错的——不论它多"完备"。新增配置项、新增必填字段、新增需要记住的约定,都要先过这一问。

### 北极星-3 · engine 与 gskill 的 AST 是核心,其余都是提效辅助

**要什么**:核心资产只有两样——engine(编译与执行)和 gskill 的 AST(格式与它的结构化表示)。gateway 与 studio,**包括** studio 的角色兜底(role fallback)与 copilot 面板,**全部是帮开发者提效的辅助设施**。

**判据(设计歧义时的权重)**:engine 与 AST 权重最高;**studio 迁就 engine,不许反向**。当"studio 用起来更顺"与"engine 的模型更干净"冲突,选后者,并把 studio 那侧改成能配合的形状。

### 北极星-4 · 本地开发的 gskill 原样复用于服务端

**要什么**:开发者在本地(桌面应用里)做出来的那个 gskill,**原样**就能在服务端跑,靠的是"锁定版本的 engine SDK"加"锁定版本的 gskill 格式"来编译。

**现状(如实标注)**:**未实现**。它的前提条件是 engine 拆成独立库并且**完全稳定**——只有 engine 的公开接口与 gskill 格式都不再频繁变动,"锁定版本"才有意义。因此这一条今天的作用是**约束设计**(见 §5-a:执行者永不写进可移植源),而不是宣称能力已具备。

### 北极星-5 · 去黑盒

**要什么**:开发者必须能看清 gskill 运行的**每一个细节**。tracing 信息要**完整**(不缺环节)、**准确**(记的就是实际发生的)、**高效**(采集与查看的代价不压垮运行本身)。

**判据**:凡是"发生了但外部看不见"的环节,都是缺陷候选;修法是把它暴露出来,不是解释它为什么不必看见。

### 明确排除项(降级为通用工程底线,不占北极星席位)

以下两条**是要求,但不是北极星**:

1. **界面状态必须真实**(界面显示的状态就是系统的真实状态,失败态要钉到真实原因码);
2. **失败时对用户数据零副作用**(操作失败不得留下半截产物或损坏既有数据)。

它们属于任何严肃工程都必须做到的底线,不构成本项目的独特目的。落点在 §8 的第⑪条,由验收清单逐模块强制,而不是靠北极星层反复宣讲。

## 2. 权威链与裁决规则

### 2.1 四层权威链(自上而下)

```
北极星(§1,五条)
  └─ 域级 Effect:每个域对用户承诺的可观察结果
       ├─ 必须声明:本域贡献哪条北极星
       └─ 或者显式声明:本域不贡献任何北极星(并写明它为何仍然存在)
        └─ 模块级 Effect:每个公开能力的成功承诺 + 失败暴露
             └─ 膜契约与实现(签名、字段、原因码、生命周期)
```

**"域"指一组围绕同一批不变量组织的能力**(例如"编译与诊断"、"运行与追踪"、"凭据与路由真相")。域的划分方法见 §7,不由现有目录形状决定。

**每一层都必须向上挂钩**:域级 Effect 写不出它贡献哪条北极星,就必须显式写"不贡献",并解释它为什么还留着。模块级 Effect 必须成对写清两件事——**成功时承诺什么可观察结果**、**失败时向外暴露什么**(哪个原因码、哪个位置、外部能据此做什么)。

### 2.2 设计歧义的裁决方向

设计出现歧义时**自上而下裁**:先问上一层的 Effect 是什么,再看哪种读法服务它。

**两种读法都不服务 Effect 链时,结论是"设定本身错了"**,处置方式是回到 §3-② 的"审设定早于审实现":先改设定(格式、契约、规则),而不是在两种都错的读法里挑一个实现。

### 2.3 事实争议的裁决:三道检验

"当初到底裁过什么"属于**事实争议**,不是设计取舍,按固定顺序的三道检验判定,三道同向才动手:

1. **日期**:比较两侧的最后修改时间(`git log -1` 两边各看一次)。文档明显更旧,大概率是文档滞后。
2. **原话**:找权威文档的修订记录、引入该实现的提交信息(`git log -S <字符串>` 找到那次提交)、或用户本人的原话。**不认自己写的旧摘要**——用摘要证明摘要是循环论证。
3. **第一性原理**:回到目标与不可变约束推一遍。常见形状是同一份文档里两半话,一半带理由、一半不带,而不带理由的那半与代码冲突——那半多半是举错了例子。

三道检验指向"文档滞后"时,**改文档**,并在文档里保留"原设计是什么、被什么实证推翻"的修订记录。

### 2.4 claim-non-seed 纪律(自我声明不作种子)

**Effect 是待证明的承诺,不是已达成的证据。** 任何文档里的"已完成"、任何代码注释里的"已支持"、任何报告里的"已验证",**都不构成该目标已达成的证据**。达成要由**动作之后的可观察结果与因果证据**证明:测试在真实执行的环境里绿、真机行为被逐项观察到、产物落盘可查。

这条纪律对本文同样生效:本文写下的每一条 Effect,都还只是承诺。

## 3. 行为原则(八条,约束本文之后的全部工作)

这八条约束**怎么做事**,与 §8 的验收清单(约束**做成什么样**)分工不同。

1. **原则高于载体。** 文档、代码、以及任何被"锁定"的设定,都只是**当下的权威读数**,不代表它正确。发现读数与原则冲突时,改读数。
2. **修缺陷的第一问是"既有设定是否本来就错"。** 先审设定(格式、契约、默认值、规则),再审实现。跳过这一问直接改实现,会把错的设定固化下来。
3. **根因要定性到原则,并当场做同族全量排查。** 一个缺陷修完,要说出它违反了哪条原则;然后立刻在**同一族**(同一原则约束下的全部同类位置)做一遍全量排查,而不是只修被报出来的那一处。
4. **规则与门禁量化在封闭域上,不写事故实例补丁。** 门禁要针对"这一类的全体"(一个可枚举的封闭集合)来断言,不针对某个具体事故实例打一条特判。实例补丁只挡住已发生的那一次。
5. **约束一律下沉为机器强制。** 能做成 CI 门禁的就做成门禁,不能做门禁的就做成交付物里的**必填栏**(不填就交不出)。只写在文档里靠人记得的约束,已被本仓实证证明不成立。
6. **证据环境 = 发货环境。** 验收证据必须出自打包版环境;开发模式下的绿只是参考信号,不是验收证据。
7. **一个概念一处实现一个 owner。** 同一个概念不得有两处实现、两个真相源、两个负责人。
8. **覆盖按域计量,不按步计量。** 计"这个域的能力被覆盖了多少",不计"跑了多少步"。**覆盖不到的格子必须显式标注"未覆盖 + 原因"**,不允许留白让读者误以为已覆盖。

## 4. 结构决定:引擎归属收敛与整体搬仓

### 4.1 背景事实(2026-08-31 勘察结论)

以下是勘察得到的**事实**,不是本节的决定;它们是决定的依据:

- 本机工作副本 `D:/coding/graph-skill-runtime`(远端仓库 `SevenX77/graph-skill-runtime`)是本仓 `packages/graph-agent` 经 `git filter-repo`(把一个子目录的历史抽成独立仓库的工具)抽取后、再加 9 个原创提交(2026-08-27 与 2026-08-28)演进出来的仓库。
- 该仓已具备:**可移植 gSkill v1 格式**(`SKILL.md` + `graph.yaml` + `AGENT.md`,子图注册表为扁平的 `graphs/` 目录)、**Port/Adapter 六边形外壳**、**8 个工具的 MCP server**(MCP 即 Model Context Protocol,让外部 agent 以工具形式调用本项目能力的协议)。
- 分叉时间只有 4 天,engine 侧的漂移是 **1 个提交**。
- 该新仓**已复活**本仓 #1072 刚刚删除的 `DEFAULT_LLM_ROLE` 兜底缺陷(即"未设置 LLM 角色时悄悄套一个默认角色",本仓已裁定为缺陷:未设置就应当编译报错)。

### 4.2 决定 a:engine 的唯一 owner 立即收敛到 graph-skill-runtime

`graph-skill-runtime` 即刻起是 engine 的**唯一 owner**。本仓 `packages/graph-agent` **冻结为只读镜像**,只接受"从新仓回灌"这一个方向的变更,不再作为 engine 变更的落点。

**理由**:两处同时演进就是两个真相源,违反 §3-⑦(一个概念一处实现一个 owner);而分叉仅 4 天、漂移仅 1 个提交,正是合并代价最低的时刻。

### 4.3 决定 b:gateway 与 studio 整体迁入 graph-skill-runtime

gateway 与 studio **整体搬入** `graph-skill-runtime`,该仓成为 monorepo,内部分工:

- **runtime 包**:保持精瘦、可独立发布的身份(它就是"锁定版本的 engine SDK"这一北极星-4 前提的载体);
- **gateway**:独立包;
- **studio**:应用(app),不是库。

**包边界不等于仓边界**:同一个仓库里各包仍各自守住自己的膜,搬仓不放松任何模块边界。

**搬家在模块化重整之前**,理由是**就地重整一次到位**:先搬后整,只需在最终的目录形状上重整一次;先整后搬,等于在旧形状上整一遍、搬完再对齐一遍。

**过渡安排(显式迁移,带退出条件)**:把**冻结的旧 engine 包(v0.3)随迁**,供 studio 在切换完成前继续使用;**Studio 切换门禁(§4.5)全部通过后,整包删除**。这不违反"不做向后兼容"——它是一次**显式声明、带明确退出条件**的迁移,不是长期并存的双读路径。

`agent-harness`(本仓)在迁移完成后**归档为只读**。

### 4.4 决定 c:搬家的前置条件(顺序固定,不可颠倒)

1. **新仓 113 个未提交文件先落 main。** 未提交的工作树内容不构成可被引用的基线,搬家前必须先让它成为仓库事实。
2. **包名裁决。** `gskill` 与 G.SKILL 商标撞名;`graph-skill` 在 npm 与 GitHub 上均已有同名占用。**发布前必须了断**——包名是发布身份,改名的代价随发布时间单调上升。
3. **复刻 CI / 分支保护 / 门禁。** 目标仓必须先具备与本仓等强度的门禁(必过检查、`main` 只能通过绿色 PR 进入),否则搬进去的代码立刻失去约束。
4. **整体迁移。** 前三步齐备后执行。

### 4.5 决定 d:Studio 正式切到新引擎的五条门禁(缺一不放行)

1. **`embedded` 恢复为第一执行路径,且 `ModelResolver` Port 契约定稿(由 gateway 包实现)。** Studio 跑 AGENT 相位走 runtime 自建的 agent 环路,"角色 → 模型"的解析经该 Port 交给 gateway(详见 §5.3)。

## 5. 双场景统一执行模型

**要解决的问题**:AGENT 相位(必须由一个能自主使用工具的 agent 才能完成的相位)**由谁来执行**?本产品的主场景是**本地开发 → 服务端复现**:开发者在本地把 gskill 做出来,同一份 gskill 要能在服务端原样跑出同一条流程(北极星-4)。

**总原则:分叉点唯一。** 差异**只**落在新仓已有的 `AgentExecutor` Port 上,**不新增任何机制**。

### 5.1 裁决理由:为什么没有"交给当前宿主执行"这一档

曾经设想过一个名为 `host-native` 的执行者:AGENT 相位挂起,由**当前宿主**(开发者此刻正在用的那个交互式 agent,例如 Claude Code 或 codex)起一个子 agent 去做,做完回写结果续跑。**它经用户裁决删除,在本设计里不存在。** 四条理由:

1. **宿主的模型、版本与上下文钉不死。** 把相位交给"当前宿主",等于让相位的实际执行者随开发者手边装的是哪个工具、哪个版本、当时上下文里有什么而变。这与**北极星-1(流程可靠、可重现)**直接冲突:同一个 gskill 在两台机器上会被两个不同的 agent 执行,跑一百次不再是同样的一百次。
2. **服务端没有"宿主"可言。** 服务端跑 gskill 时,不存在一个正陪着开发者的交互式 agent。**北极星-4** 要求本地做出来的 gskill 原样在服务端复现,而 `host-native` 恰恰是唯一在服务端无法成立的执行者。
3. **宿主的角色是驾驶员,不是执行者。** Claude Code 与 codex 在本产品里的位置是**驾驶员**:经 MCP 或命令行调用 compile / predict / run / inspect,读回结果,改源文件。它开车,不当发动机——**它永远不是相位执行者**。
4. **单独使用 Claude Code / codex 的场景不构成例外。** 那种场景同样走 `embedded` 或 `ah`:驾驶员是宿主,执行者仍然是这两者之一。

### 5.2 决定 a:executor 是运行时配置,永不进可移植源

**执行者不写进可移植源**:`AGENT.md` 与 `graph.yaml` 里**不出现**执行者信息。理由直接来自北极星-4:同一个 gskill 必须能被任何宿主拿去跑,一旦源文件里写死"用哪个执行者",它就绑死了宿主。

**解析链(两级,后者覆盖前者)**:

1. `RunRequest.executor` —— 本次运行的**全局默认执行者**;
2. `RunPreset.node_overrides[<相位>].executor` —— **相位级覆盖**。

**闭集(只有这两个值)**:`embedded`、`ah`。

### 5.3 决定 b:缺省 = embedded;ah = 显式选择

**`embedded`(缺省执行者)**
runtime **自建 agent 环路**(由 runtime 自己驱动"提问模型 → 模型挑工具 → 执行工具 → 回灌结果"这个循环),其中"角色 → 模型"的解析经 **`ModelResolver` Port** 完成,**gateway 包是该 Port 的权威实现**:凭据、路由、角色与角色兜底(fallback)**全部归 gateway**,engine 只知道"有一个能把角色解析成可调用模型的 Port",不知道任何厂商细节。

**当某个 AGENT 相位没有可用角色供给时,在 compile / preflight 阶段报错并引导用户去配置**——与既有的空角色裁决(交付台账 J-X.10:未设置 LLM 角色即编译报错,原因码 `[F-v3-agent-llm-role-missing]`)**同构**;**不静默**:不悄悄套一个默认角色,也不悄悄跳过该相位。

**`ah`(显式选择)**
经 **agent-hypervisor(ah)** 起厂商命令行(vendor CLI)的**受监督进程**:建会话 → 注入任务 → 收结构化结果 → 回收。**该命令行工具自持登录**(凭据由它自己管,不经本产品);**进程监督、沙箱、崩溃恢复全部归 ah**,engine 不重造这一层。它作为**可选附加依赖(optional extra)**提供,不进默认依赖闭包。

### 5.4 决定 c:preflight 兼容检查(起跑前拒绝,不中途炸)

在 `resolve_run` 阶段(解析运行请求、确定这次要怎么跑的那一步)**逐相位核对**:每个 AGENT 相位声明的能力需求——工具(tools)、子 agent(subagents)、上下文访问(context_access)、迭代与并行形状——与所选执行者的支持面是否匹配。

- **不支持就在起跑前以原因码拒绝**;
- **绝不中途炸**(跑到一半才发现执行者做不到,用户已经付出了前半段的时间与调用成本);
- **绝不静默换执行者**:**没有自动 executor fallback**。选择执行者是用户的显式配置,系统替他换掉就是隐式行为,违反"显式优于隐式"。

### 5.5 决定 d:失败语义

执行者失败,以 **`GSKILL_*` 类型化错误**归因到**具体相位**,并进入 trace。**没有跨执行者重试**:换一个执行者重跑是另一次运行的决定,不是失败处理的一部分(否则失败原因会被后一次成功掩盖,违反北极星-5)。

### 5.6 决定 e:删除清单(新仓,按"不做向后兼容",同一次变更删净)

1. **`host-native` executor** 本体;
2. **durable handoff 的存储 `agent-handoffs.sqlite3`**(durable handoff 指"把该做什么、有哪些约束、要交回什么落成可持久化的交接件",它只为把相位交给宿主而存在);
3. **`submit_agent_result` MCP 工具**(宿主子 agent 回写结果的入口);
4. **`checkpoint_ref` handoff 形状**;
5. **Phase 3b backlog 整体**。理由:那批覆盖缺口(注册表子图的 AGENT 相位、iterate 循环中的 AGENT 相位、类型化恢复 typed resume、宿主确认)是 `host-native` 带来的;**`embedded` 本来就是支持全部形状的原引擎路径**,缺口随 `host-native` 一起消失,不需要单独补。

### 5.7 决定 f:设计后果 —— run 成为长任务,需异步任务模型

MCP / 命令行场景下,run 不再是"调一次、等它返回"的短请求,而是**长任务**:**起跑 → 查状态 / 收事件**。因此需要一个**异步任务模型**,并且**它与实时事件订阅并为同一个 Port**——做成两套,"跑到哪了"这个问题就会有两个答案。

### 5.8 决定 g:被接受的代价(显式记录)

删掉 `host-native` 之后**没有零配置路径**:独立使用者要么配一个 API key 走 `embedded`,要么装 ah 走 `ah`。这与**北极星-2**(比裸写 langgraph 更省事)存在张力。**用户已知悉并接受这一代价**:可重现性(北极星-1)与本地即服务端(北极星-4)优先于首次上手的零配置便利。

### 5.9 决定 h:实施顺序(固定)

1. **executor Port 收口(两个成员)+ 参数链 + preflight**;
2. **gateway `ModelResolver` Port 对接**;
3. **`ah` adapter + 删除六个直连厂商命令行 adapter**(同一次变更删净,不留双路径);
4. **删除清单(§5.6)执行 + 异步 run 任务模型落地**。

## 6. 格式载体:裁决前的事实与依据留底(**结论已出,见 §11.1**)

> **本节的状态**:本节写于裁决**之前**,记录的是待裁问题、已核验的事实、需要先钉的场景权重与裁决窗口。**2026-08-31 用户已裁:维持新仓 `graph.yaml`,不回 markdown 正文 XML**——裁决正文、用户原话、四条理由与机械后果全部在 **§11.1**。本节**原样保留不改结论**:它是裁决依据的留底,不是仍然待办的事项。**引用本节前先读 §11.1**,不要把这里的"待裁"字样当成当前状态。

### 6.1 领头待裁项(已裁):拓扑的载体形式

**当时的待裁问题**:gskill 的**拓扑**(哪些相位、怎么连)写在**markdown 正文里的 XML 标签**(旧格式的 `<phase>`),还是写在**独立的 YAML 文件**(新格式的 `graph.yaml`)?**结论见 §11.1(维持 `graph.yaml`)。**

### 6.2 已核验的事实(裁决的依据)

**旧格式真正的病是"相位 id 集合被写了三遍"**:

1. `GRAPH.md` frontmatter 的 `phases:` 列表;
2. 正文里每个 `<phase>` 标签;
3. `phases/<相位 id>/` 目录名。

三者由三个原因码机器强制一致:`[F-v3-graph-phase-name-mismatch]`(明写"body `<phase>` name / frontmatter `phases` 注册名 / 物理目录名三者不一致",见 `docs/engine/mvp1/01-contract/03-compile-rules/mvp1-alignment.md:250`)、`[F-v3-graph-phases-dir-missing]`(同文件 `:247`)、`[F-v3-graph-phase-node-missing]`(同文件 `:257`)。因此**重命名一个相位要同步改三处**——权威表述见 `docs/engine/mvp1/01-contract/02-skill-syntax/mvp1-alignment.md` §3.2:「Studio 做 rename 时必须同步目录名、`GRAPH.md phases` 注册表和 body `<phase>` 引用」。

**其中 frontmatter 的 `phases:` 列表是零增量冗余**:正文已经规定每个相位都必须出现一次 `<phase>` 标签,那份列表没有携带任何正文之外的信息。

**结论(事实层)**:**治这个病不必换载体。** 把正文的 `<phase>` 定为**唯一注册表**、删掉 frontmatter 里的 `phases:` 列表,就能在 markdown 内部把病治好。

**新格式的对与未论证之处**:把"注册表与边"并成一条**是对的**(它消掉的正是上面那份冗余);但**换成 YAML 是一个独立的决定,尚未被单独论证**——它没有随"消冗余"这个理由自动成立。

**用户的保留意见(当时已记录,未转成结论)**:对"全 YAML 牺牲人类编辑体验"持保留意见,参照物是 Agent Skills 的 `SKILL.md` 那种"给人读、给人改"的设计取向。**这条保留意见在 §11.1 被正面处理**:理由①(散文密集的载体保持 markdown 不变,拓扑里没有散文)与理由②(Agent Skills 自身就是"散文归 markdown、结构归独立文件")即针对它。

### 6.3 裁决前需要先钉的事实(已钉,见 §11.1 与盘点 §8-1)

**各场景里,谁在徒手读写拓扑?** 需要分三种场景分别落实:

1. **Studio 画布**:拓扑由界面生成与改写,人不徒手编辑;
2. **agent 直接使用**:agent 读写文本,不需要人类友好的排版;
3. **人工评审 diff**:人要在代码评审里看懂"这次拓扑改了什么"。

这三种场景对载体的要求不同,裁决取决于它们各自的真实权重。**权重已在全局盘点里钉死**(盘点 §8-1):徒手读写只发生在 Monaco 编辑器与 agent 两个场景,**两者都不依赖 XML 标签**;人工评审看到的只有 git 文本 diff。

### 6.4 裁决窗口(已用)

新格式规范当时的状态是 `audited-ready`(语义已过审计、尚未上机器哈希锁),**还没有 FROZEN**。这就是这项裁决的窗口:在它被冻结之前裁,成本最低。**窗口已按期使用**:2026-08-31 裁决落定(§11.1),规范随后可进入上锁流程(§11.1 机械后果第 1 条,落点批B)。

## 7. 全局盘点方法(先于一切实施)

**"盘点"指在动手改任何代码之前,先把"这个系统有哪些域、每个域有哪些模块、每个模块 own 什么"完整列出来。** 盘点的产物是后续所有实施任务的依据。

### 7.1 三层,由上而下

1. **系统层**:北极星(§1)+ 系统必须支撑的旅程(用户从头到尾走完一件事的完整路径);
2. **域层**:按不变量聚类出的域;
3. **模块闭包层**:每个域内部的模块及其闭包(这个模块 own 的全部事实与能力)。

**物理形状不作判据**:现有文件与目录怎么摆,**不构成**域与模块该怎么划的依据。今天的目录形状是历史演进的结果,把它当判据等于把历史固化成设计。

### 7.2 拆分方法论(取自 zeroth/gas 现行本体)

- **split-first**(先假设该拆):默认倾向是拆开,由证据把它们合回去,而不是默认混在一起、等出问题再拆。
- **八项治理义务**(每个模块必须答全的八问):①为何存在;②own 哪些事实;③公开能力有哪些;④依赖谁;⑤规则动作(它按什么规则做什么动作);⑥成功承诺与失败暴露;⑦事后可观察证据(怎么证明它做到了);⑧生命周期(何时创建、何时销毁、状态归谁)。
- **三类正向合并证据**:要把两个候选模块合成一个,必须给出正向证据,而不是"看起来差不多"。
- **三向反事实资格判据**:对每个候选边界做三个反事实追问——**删掉**它、**并进**别处、**拆得更细**,分别是否**毁掉某个行为区分**?毁掉了,说明这条边界有资格存在;没毁掉,说明它不该单独存在。
- **膜与原子性分开各审**:"对外契约是否完整"(膜)与"内部操作是否要么全做要么全不做"(原子性)是两件事,各审一遍,不合并成一次评审。

### 7.3 三轴对账

- **轴①旅程**:定功能责任(这条旅程要求谁负责什么);
- **轴②实扫**:对**实然代码**做实际扫描(代码里现在真的有什么);
- **轴③设计单元**:交叉审计(设计单元之间是否重叠、是否有真空)。

### 7.4 模块地图是生成物

**模块地图 = 从各模块契约机械汇聚出来的生成物,不手工维护一张总表。** 手工总表必然与契约漂开,而漂开的总表比没有总表更坏(它会被当成真相引用)。

### 7.5 执行顺序的推导

**执行顺序从树的依赖序推导**:被依赖的先做。**问题密度只用于同层平票裁决**——同一层里几个模块依赖序上不分先后时,先做问题多的那个。

### 7.6 功能验收的推导链(三步,顺序固定)

1. **第一性推导应然**:从**产品本体事实**与**北极星**推出每个域**必须支撑**的能力、旅程与失败路径。既有的 33 条旅程地图**仅作对照物**——用来检查有没有漏,不作为推导的来源。
2. **对照实然代码逐条标状态**:每条应然能力,在代码里找到它的实现或确认它缺失,逐条标状态。
3. **文档只当证词**:文档说的话是**证词**,不是事实;**引用之前必须先对代码或真机行为验证**。

**这条链的关键是"文档不作来源"**:应然从北极星与产品本体推,不从"文档里写过什么"抄。

## 8. 规范验收清单(全局封闭集,每模块必过)

**每一条都必须落成一个机械门禁,或落成一次指名到人的语义审查**——不允许只是一条口号。

| # | 条目 | 要求 | 强制方式 |
|---|---|---|---|
| ① | **概念唯一 owner** | 模块 own 的概念列成词表,每个概念在全仓**只有一份实现** | 唯一性上门禁 |
| ② | **膜完整** | 膜上写清:职责、输入输出、依赖(**指名到对方的具体公开能力**)、失败语义、生命周期 | 依赖声明与实际 `import` **双向**机械核验 |
| ③ | **边界 fail-fast** | 非法输入在**膜上**就拒绝;错误走**统一信封**(含跨域请求所需的 CORS 头);原因码入册 | 门禁 + 原因码注册表 |
| ④ | **非法状态不可表示** | 约束编码进类型与 schema(用判别式联合类型),不靠散落的运行时 if | 类型检查 + schema 校验 |
| ⑤ | **SSOT 读取** | 服务端真相**单一读取面**;禁止组件挂载(mount)、窗口聚焦(focus)、定时轮询触发重新取数 | 门禁 |
| ⑥ | **契约零手抄** | 跨边界类型**全部是生成物**,不手写第二份 | CI 漂移门禁 |
| ⑦ | **无平行实现、无死代码** | 不留第二套实现;死代码删除**前**按"先查裁决"纪律确认:它是不是当初被**主动下线**的(用 `git log -S` 找移除性提交、看守卫测试里钉的提交哈希),而不是忘记接线 | 语义审查 + 覆盖扫描 |
| ⑧ | **纯逻辑与 IO 分层** | 业务逻辑**不驻留**在路由层与 UI 层 | 语义审查 |
| ⑨ | **业务逻辑 TDD** | 先写失败测试再写实现;测试必须跑在 **CI 实际执行的 job 里**;证据出自**打包环境** | 门禁 + job 归属核验 |
| ⑩ | **完成语义三级分别举证** | "代码收口" ≠ "真跑验证" ≠ "目标达成",三级各自给证据,不得用前一级冒充后一级 | 交付物必填栏 |
| ⑪ | **界面状态必须真实 + 失败零副作用** | 界面显示的状态就是真实状态,失败态**钉到真实原因码**;失败时对用户数据**零副作用** | 门禁 + 真机点验断言 |

第⑪条是从北极星降级而来的通用工程底线(见 §1 的明确排除项),降级只改变它的层级,不降低它的强制力。

## 9. 逐模块流水线与完成定义

### 9.1 六步流水线

1. **盘闭包**:先立**应然**(这个模块按 §7.6 应该有哪些能力),再进下一步;
2. **代码审查**:应然对**实然**,每条结论给 `文件:行号` 证据;
3. **重构 + 修复**:TDD;不做向后兼容;**旧路径同改同删**;
4. **过原则清单**:§3 与 §8 **逐条填证据**,作为交付物的**必填栏**(不填交不出);
5. **交叉审核**:由 codex(GPT-5.6-sol,extra-high)按**同一份事先声明的清单**审核;发现逐条裁决(采纳或驳回都要写明理由);
6. **真机点验收口**:**打包版**;覆盖**按域计量**;断言**原因码**(不是断言界面文案)。

第 5 步"同一份事先声明的清单"是关键:审核方与被审方用的是同一份、且在动手前就写定的清单,否则审核会变成"审核者临时想到什么就查什么"。

### 9.2 完成定义(五把锁,缺一不关)

1. **事先声明的功能切片全绿**,证据出自**打包版**;
2. **规范清单(§8)全绿**;
3. **codex 的全部发现都已裁决**;
4. **膜落盘 + 漂移门禁上锁**——此后**改膜必须走显式契约修订**;
5. **膜与原子性分开各审一遍**。

### 9.3 "95% 不返工"的保障来自哪里

三件事:**依赖序执行**(不在地基未定时盖上层)、**契约锁**(膜一旦落盘就由门禁挡住静默漂移)、**事先声明的验收**(验收判据在动手前写定,不在交付时临时协商)。

### 11.1 拓扑的载体形式:维持 `graph.yaml`

**待裁问题(§6.1 原题)**:gskill 的**拓扑**(有哪些相位、相位之间怎么连)写在 **markdown 正文里的 XML 标签**(旧格式 `GRAPH.md` 的 `<phase>`),还是写在**独立的 YAML 文件**(新格式 `graph.yaml`)?

**用户原话**:

> 「对于机器,只要把grammar写清楚,compiler严谨,对于机器有什么区别?你得再找个用yaml的真正理由」

**裁决**:**维持新仓的 `graph.yaml`,不回 markdown 正文 XML。**

**先认账:用户的挑战成立。** 语法写清楚、编译器严谨之后,两种载体**对机器没有区别**——"机器更好读 YAML"、"解析更容易"这一类论据**全部作废**,盘点 §8-1 中凡属这一类的证据不再被本裁决引用。以下四条理由**没有一条依赖机器偏好**。

**理由①(对象拆分):人类编辑体验之争的对象是散文,而拓扑里没有散文。**
"给人读、给人改"这个诉求成立的地方是**散文**。gskill 里散文密集的载体是 `SKILL.md` 与相位文件(`AGENT.md` / `LOGIC.md`),**两种方案下它们都保持 markdown 不变**——本裁决不动它们。拓扑本身是纯结构数据。实物证据是本仓一份真实的 `GRAPH.md`(`packages/graph-agent/tests/fixtures/fake_canvas_fanout/GRAPH.md`,全文 10 行,以下为前 8 行):

```markdown
---
schema_version: "2.1"
name: fake-canvas-fanout
---
<input src="io/inputs.json" />
<output src="io/outputs.json" />
<phase id="prepare" src="phases/prepare" depends_on="" />
<phase id="branch_a" src="phases/branch_a" depends_on="prepare" />
```

通篇是 YAML frontmatter 加 XML 标签,**一句散文都没有**。把纯数据写进 markdown,得到的不是"`SKILL.md` 那样给人读的文档",而是**在一个散文容器里手写数据标签**:既拿不到 markdown 的可读性收益,又要付出理由③的代价。

**理由②(参照系反向适用):Agent Skills 的形状本身就是"散文归 markdown、结构归独立文件"。**
用户援引的参照物是 Agent Skills 规范的 `SKILL.md`。那份规范**自己的形状**是:`SKILL.md` 承载**散文说明**,机器可读结构只放**最小 frontmatter**,其余结构化资源(`scripts/`、`references/`)**独立成文件**。`graph.yaml` 独立成文件与这个形状**同构**;把大块机器拓扑塞回 markdown 正文,反而是**偏离**该参照系。

**理由③(一文件一契约):markdown 里的 XML 岛让同一个文件有两个消费者,病根长在这里。**
`GRAPH.md` 这种形状里,同一个文件被两方消费:**人与宿主读散文,编译器读标签**。因此写回器必须**对散文字节保真**——它不能重排、不能规范化,只能在原文里精确挖补。代价是实测到的:写侧自建了一整套影子 parser(`packages/graph-agent/src/graph_agent/core/graph_serializer.py:113,156,160`;域报告 `aad870f45bd77060f_v1.md:48-50` 记为「XML/markdown 载体直接产出了第二个格式 parser」),而「`<phase>` 标签长什么样」这份知识**散在五处、无共享常量**——1 个读正则(`packages/graph-agent/src/graph_agent/core/loader.py:1837`)、1 个写正则(`graph_serializer.py:156`)、3 个生成点(`graph_serializer.py:104`、`:106`、`:152`),证据见域报告 `aad870f45bd77060f_v2.md:9-13`。
**用户的挑战在这里同样成立**:唯一 parser 加严谨 compiler 确实能治标——把读写收进同一个 tokenizer,五处知识能并成一处。但**唯一文件唯一契约让这个病根无处生长**:`graph.yaml` 只有编译器一个消费者,没有"保真散文"的义务,也就长不出第二个 parser。这与本仓编码规范的「**让非法状态不可表示**」同构:能用结构消除的错误,不留给纪律去防。

**理由④(既成事实;次要,仅顺水推舟,不单独构成理由)**:新仓已按 `graph.yaml` 实装,格式规范 `D:\coding\graph-skill-runtime\docs\skill-spec\01-PORTABLE-GSKILL-V1.md` 状态为 `audited-ready`(语义已过审校、尚未上哈希锁),发布链已具备"一次 build + 三平台验收 + 受信发布"的形状(该仓 `docs/design/v1-alignment.md` §2.1)。**这一条只在前三条已经指向 YAML 时用来说明代价更低**;按 §3-① 原则高于载体,既成实现本身不证明它正确。

**§6.2 的事实层结论继续有效,且与本裁决不冲突**:§6.2 证明了"要消掉相位 id 三重冗余,**不必**换载体"——那是**对的**。它否掉的是"消冗余"这条**理由**,不是 YAML 这个**结论**。本裁决用的是理由③(一文件一契约),与消冗余无关。

**用户保留否决权**:若推翻本裁决、改回 XML 载体,则按域报告 F-T9(`aad870f45bd77060f_v1.md:173`)的另一半执行——**必须同批消灭 writer 影子 parser,让 reader 与 writer 共用同一个 tokenizer**;并按 §6.2 把正文 `<phase>` 定为唯一注册表、删掉 frontmatter 的 `phases:` 列表。

**本裁决的机械后果(排入后续批次)**:

1. **格式规范可进入上锁流程**:`01-PORTABLE-GSKILL-V1.md` 由 `audited-ready` 建 SHA-256 哈希锁转 `FROZEN`(域报告 F-T3)。它是「engine 唯一 owner 交接」的门,**落点批B(交接门)**。
2. **「三名一致」规则必须降为「两名一致」**:现行 MoirAI 资产仍要求相位 id 在三处一致——`apps/studio/backend/app/agents/skills/graph-design/SKILL.md:25-28`(要求 `phases/` 目录名、`GRAPH.md` frontmatter 的 `phases` 注册名、正文 `<phase id="name">` 标签三者绝对一致)与 `apps/studio/backend/app/agents/knowledge/KB-01-skill-anatomy.md:48-53`(「Three-Name Consistency Rule」)。`graph.yaml` 下只剩两处(相位目录名 + `graph.yaml` 注册项),**不同步改写就会让 agent 按已作废的规则改 skill**(域报告 F-T9)。这两份是 MoirAI 资产,其单一 owner 按 §4.6-2 定到新仓,故改写**落点为批B′(MoirAI 单 owner 迁移)**,不在本仓另改一份。
