## 三、按「功能模块垂直闭包」重整时，前端先动的三个域

**① `run` 域（run 生命周期 + 诊断 + history + compare + trace）**
先动它，因为它是唯一一个**同时踩中全部四类问题**的域：真相被 `Workspace.tsx:584/586/588/590/595/597/627/637/790/835` 十来个 useState 割裂；`RunMetadata` 是已实测的契约漂移点（`auto_commit`/`paused_at` 缺失、`artifact_ref` 类型方向相反）；`statusVariant` 在 `BatchSummary`/`RunHistoryRow` 复制；`BatchSummary.tsx` 整个是死面。而它的边界是全前端**最清晰**的——`RunStatus` 六态在 `api/types.ts:329` 和 `runs.py:101` 两侧词表已经对齐，`useRunHistory.ts` 已按 SSOT 原则写好（`:242` 注释明确拒绝 mount/focus 重取），`useRunStream`/`useRunDeltas` 事件通道也在。把 run 抽成 `features/run/`（类型从后端生成、一个 store、一套 badge 映射、一套 drawer）能一次性从 `Workspace.tsx` 里剥掉约 800-1000 行，且不碰画布和 Settings 这两个高冲突面。这是投入产出比最高的第一刀。

**② `llm-config` 域（credentials / roles / registry / model groups / provider test）**
第二动，因为它是**底座一违规最深、爆炸半径最大**的域：`api/llm.ts`(2139) + `SettingsPage.tsx`(1477) + `ProviderCard.tsx`(2662) + `CopilotTab.tsx`(1297) + `role-utils.ts`(811) + `LlmRolesTab` + `AvailableModelsSidebar`(809) ≈ **9000+ 行生产代码，另有约 9500 行测试**，而同一份 roles/credentials 真相在其中有三个读取面（`llm.ts:658` 模块缓存 / `SettingsPage.tsx:504` useState / `SettingsPage.tsx:511` useSyncExternalStore），P0-3 的两处 SSOT 读取原则违规和 P0-4 的「本地覆盖服务端」都在这里。不先把读取面收敛成一个，任何 Settings 相关改动都会继续在三份副本间打地鼠。放第二不是因为它不严重，而是因为它需要先有 ① 验证过的 store 范式再套用——直接上手容易变成第七套手写 store。

**③ `graph-authoring` 域（canvas + properties + phase frontmatter）**
第三动，`GraphCanvas.tsx`(2818) + `PropertiesPanel.tsx`(4433) + `canvas-authoring.ts`(711) + `subgraph-expansion.ts`(658) + `phase-frontmatter.ts`(573) ≈ 9200 行，是体量最大的域。放最后有三个理由：一是它的**纯逻辑/IO 分层已经开了头**（`canvas-authoring.ts`、`subgraph-expansion.ts` 存在即证明方向已定），补完比重构便宜；二是它对 ① 有依赖——`PropertiesPanel.tsx:3207-3818` 那整块 LLM compare 子系统其实属于 run/compare 域，得等 ① 落地才有地方搬；三是画布是 UI 冲突面最集中的文件，并行改动风险最高，应该在前两个域验证过拆分范式后再动。第一刀不是拆 `GraphCanvas()` 本体，而是把 `:266-692` 那批纯函数（语义 diff、展开代数、连线写回、MiniMap）搬进已有的两个 `.ts`，让 2000 行的 `GraphCanvas()` 先降到可读的量级。
