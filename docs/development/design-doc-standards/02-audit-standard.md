# 设计文档审计规范

> 审计**怎么审**。配套:文档怎么写见 [`01-writing-standard.md`](./01-writing-standard.md);三轴心智见 [`00-three-axes.md`](./00-three-axes.md);符合标准的范例见 [`example/`](./example/)。
> **通用 + 自包含**:本规范**不引用规则文件夹外的任何文件**。项目专属的 scope / 范例,由"项目自己的 README + INDEX + 本规范判据"实例化,不写进本规范。

## 审计落在三轴的哪里(见 `00-three-axes.md`)
- **主审 轴② 能力模块**:逐模块审它的 `baseline`(对代码)+ `alignment`(对决策)。
- **轴③ 设计单元索引(INDEX)做交叉检验**:跨模块一致、双向引用、去重。
- **轴① workflow 保覆盖**:按决策脊柱过一遍,确保每个决策点牵动的单元都审到、不漏。

---

## 一、硬规范(违反即 FAIL)

### R0 内容正确
文档内无自相矛盾 / 逻辑漏洞 / not-make-sense;跨文档对同一事实无冲突。

### R1 唯一真理(不把弃用文档当 SSOT)
当前 milestone 文档是唯一权威;已弃用 / `superseded` 旧版**不得作 SSOT 引用**。内容自写完整;缺的 🚨 真空报警,不靠链旧文档充数。

### R2 baseline 对照代码(不对照任何 spec)
baseline 真实性 = 和当前代码一致(挂真实 `文件:符号名`),**与决策无关**;不得拿任何 spec(尤其旧 spec)冒充现状。

### R3 alignment 对照最新决策(无 stale)
alignment 反映最新拍板决策;过时 / 被推翻的目标 = FAIL。`FROZEN` ≠ 最新有效。

### R4 baseline / alignment 职责分清 + 测试锚点
baseline = 现状(对代码)、alignment = 目标(对决策),不混;baseline 必有「测试锚点」差异表(现状 vs 目标)。

### R5 引用拓扑(轴②内双向 + 跨轴走 INDEX)
- **轴② 内直接双向**:`代码↔baseline`(代码注释标 baseline;baseline 用 `文件:符号名` 为主、行号辅)· `baseline↔alignment`(frontmatter `binds_*` 互标 + 交叉引用互指)· 能力模块间实现引用双向。
- **跨轴(workflow / 设计单元 ↔ 能力模块)走 INDEX 枢纽、不两两互引**;能力模块自包含(含就近决策原话),不跳 workflow 取决策。详见 `00` 引用拓扑 / `01 §2`。

### R6 引用纪律
不引 `.kiro/` / `temp/` / 工作日志(临时会删);跨模块引当前 milestone 内部 + 双向链。

### R7 锁状态合规(状态机)
`status` 符合 `01 §1` 状态机;**未通过审计不得标 `FROZEN`**;`FROZEN` 哈希入锁表;`superseded` / `deprecated` 符合"被取代 / 新版零引用"前提。

### R8 设计单元索引登记(轴③ = 横跨 / 锁 / 追溯枢纽)
每个**横切设计单元**(横跨多能力模块的 feature)在项目 `INDEX` 登记一行:**单元 | 源 workflow/atom action | 横跨的「模块 × 切面」(每切面标 owner 模块) | `binds_code` | 锁状态**。
- **`spans` 精确到 模块 × 切面**(例:子图 = 语法切面→skill-syntax · 布局切面→physical-layout · 解析切面→resolver)。
- **去重判据**:每个切面只一个 owner 模块写实现;别的模块写了同切面 = 重复违规(扫 INDEX 的「切面 × owner」照出)。
- 跨模块一致(Q3)、单元级锁(R7)、对外对接,全挂 INDEX;INDEX **不重述实现 / 决策**,只记映射。

## 二、质量要点(弱项标 ⚠️)

### Q1 深度 / 颗粒度对照范例
不只设计方向、**必须含设计细节**;颗粒度对照 [`example/`](./example/) 的 baseline / alignment 范例。明显薄(只方向 / 缺 `文件:符号名` / 缺测试锚点)= ⚠️。

### Q2 决策留底 + 原话
关键决策有**原话引用** + 决策表(决策 + 动机);讲清"**为什么 / 约束**",不只"做什么"。

### Q3 跨模块一致 + 变更连带改齐(用 INDEX 交叉检验)
同一设计单元在它 `spans` 的各模块说法一致;反转 / 变更牵动的连带都改齐——**顺 INDEX 的 spans 逐处查**(缺一即 ⚠️)。

### Q4 gap 报警 / 实施边界
缺的、待设计的 🚨 报警;**实施层面**(代码改 / 接口签名 / 实施顺序)归实施层,不混进设计文档。

### Q5 scope 对照项目 README「做什么 / 不做什么」
scope 边界由**项目 README 的 non-goals** 界定;文档出现 scope 外内容(通用引擎塞领域 / 业务代码)= 违规。README **没有 / 没确认** scope → 先第一性原理分析定 + 项目 owner 确认盖章,再据此审。

## 三、配套:代码诊断(双轨)
"审计" = **双轨**,缺一不可:
- **文档轨(本规范)**:审 `baseline` / `alignment` **文档**质量(R0–R8 / Q1–Q5)。对象 = 文档。
- **代码轨**:对**源代码**跑工程体检——5 维:
  - **极简度**:无为兼容 / 过渡而堆的临时适配器、冗余包装;
  - **类型安全度**:无 `cast(Any)` / `type: ignore` 逃避、无隐式 Any;
  - **死代码干净度**:无物理残留的废弃方法 / 不可达逻辑 / 历史包袱;
  - **测试活性度**:非假 Mock、有真实端到端校验、无脆弱 skip;
  - **接口与依赖清晰度**:不越权引私有(`_` 模块)、不绕统一 `Settings` 随处 `os.getenv`、无循环导入。
  每条缺陷标**严重度**(critical / major / minor)+ `文件:符号名` 证据。对象 = 代码。
- **连接点 = baseline 的 `binds_code`**:审一份 baseline 时,顺它绑定的代码符号跑代码诊断,一次同时验「文档说的代码现状对不对(R2)」+「那段代码本身干不干净(5 维)」。
- **执行**:靠项目配套的代码诊断套件;本规范只定**代码轨查什么**(上述 5 维 + 严重度),不绑定具体实现工具。

## 四、输出格式
逐份文档:
```
### <文档相对路径>
- R0–R8: PASS | FAIL — 证据(文件:符号名 / 引用)
- Q1–Q5: PASS | ⚠️ | N/A — 证据
- 🚨 本档真空 / 债:缺什么、待迁什么
- 修复建议:具体
```
全局汇总:① FAIL 总清单(优先级);② 🚨 去-旧版债总账;③ 双向引用缺口(代码 / baseline / alignment 哪层没绑);④ 跨模块 drift;⑤ 锁状态清单(各文档 `status` + 可否进 FROZEN);⑥ 设计单元索引覆盖(哪些单元未登记 / 重复 / 真空)。

## 五、判定铁律
- 宁可误报、不可漏报(漏报 = 假装合格)。
- 每条结论必有 `文件:符号名` / 引用证据,不凭印象。
- 拿不准"现状是否被新决策推翻" → 先核实最新决策(`FROZEN` 也可能已废)。
- **审计只产出"文档标注 + 🚨",不产出代码补丁**:代码轨发现的债如实写回对应 baseline + 警告,归 refactor-target;改代码是独立重构任务,不混进审计。

## 六、审计执行方法论(怎么审才不漏)
> §一–§五 定"审什么";本节定"**怎么审才不漏**"。下列 8 条为真实审计执行踩坑后的总结(⊕ = 实证:本规范配套项目执行中真实发生过的漏报/返工)。

### M1 ⊕ 逐模块查穷,不按维度分轮扫
- **反模式**:先扫全部文件的链接、再扫全部的引用、再扫全部的语义——每轮只抓一类,漏的下轮才冒出来,反复返工(用户原话:"为什么来来回回那么多回合")。
- **正解**:固定一个模块,把它的**所有维度**(R0–R8 + Q1–Q5 + 跨小节自洽 + migration 对照)一次查穷、修完,再下一个模块。

### M2 ⊕ 机械可判 → 脚本全量;语义判断 → 逐字读
- **机械可判**(符号是否存在、链接是否解析、frontmatter 字段齐否、锚点是否匹配、单元是否登记)→ **写脚本落在文件系统上全量验**,不靠人眼/转述/计数(数了 30 个锚点 ≠ 30 个都能解析)。
- **语义判断**(内容矛盾、是否反映最新决策、动机真实性)→ **每档逐字读**,不抽样。抽样得来的"语义 PASS"是抽样信心,**不等于**脚本穷举的"0 就是 0";报告须诚实标注覆盖方式。

### M3 ⊕ 跨小节自洽 = 语义审计的核心检查
- 一份 alignment 的:frontmatter `units` / 各 F-section 归属 / §3 接口 Region·Capability links / §5 决策表单元 / §7 涉及 / §8 gaps / INDEX owner —— 必须**互相一致**。
- **实证**:绝大多数语义 FAIL(矛盾型 R0/R3 + 单元映射 Q3)都出在这里——"文档这节说 X、那节说非 X"(如"golden 不在 Properties"却在 links 里列了 `properties`)。审每档必须把它**自己的各节互校**一遍。

### M4 ⊕ 自审报告不可全信,要独立对抗式复核
- 任何审计(含 AI 自审)的结论必须**独立重验**,尤其机械声明(报"链接 PASS"可能只是数了没真解析;"问题清单"可能只覆盖一半)。
- 复核要**对抗式**:假设审计者有错、主动找它的漏;归属/owner 类结论一律以**权威源(INDEX)**裁决,不以审计者写的为准。

### M5 ⊕ "越新越准"是陷阱:派生文档会有损压缩
- 派生/摘要文档(如从原始笔记清理出的 workflow)**不能因为"新"就自动覆盖**承载 PM 原话/🔒 的源(派生时会把"当且仅当 A 失败才 B"精简成"B")。
- **finality 序**:明确 supersede > PM 原话/🔒(在哪都算)> 领域 canonical > 已回写的完整决策 > 派生/摘要 > 旧参考。迁移退役 = **逐条 diff/merge**(拿🔒当校验清单核派生),不是整体搬。

### M6 ⊕ 判"漏"前先查"挪位 / 改名"
- 一个被引用的符号/内容在原处找不到 ≠ 丢了——先查它是否**挪到了更合适的模块**、或**代码改了名**;全树都不在,才是真漏。

### M7 ⊕ 退役 / SSOT 泄漏检查要查"裸名"不只"路径"
- 退役一份文档、或查 SSOT 泄漏,要 grep **路径**(`x/y.md`)**和裸名**(`y`)两种;只查路径会漏掉 "`y:行号`""见 y 批次1" 这类裸文本引用。

### M8 ⊕ 锁需要机器强制,状态标签 ≠ 锁
- `FROZEN`/`locked` 若没有"哈希入锁表 + 触发测试"的机器层,只是自觉标签,挡不住多 session/AI 的**静默漂移**("顺手改一句""对齐实现改一段""格式化带走几行")。
- 没机器就别冒用 `FROZEN`;过渡用 `audited-ready`(语义已审、待机器锁)。`unit-lock=drafted` 时文件级 `FROZEN` 本就不成立(R7)。
