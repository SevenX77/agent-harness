# PR-1 报告：T3 事件记录统一收口

## 1. 设计是什么

这次改动要解决的是运行记录不稳定的问题。旧方式里，事件可能由两个地方各自发出，容易出现重复、漏记，或者同一件事在不同记录里长得不一样；记录文件的名字也不统一，外部想实时接入时还要按一套偏重的写法来配合。

T3 的设计方向是把这件事收敛成一条主线：同一件运行中的事，只从一个地方发出；每次运行都有一个统一的黑匣子记录文件；外部如果想实时看进度，只需要提供一个接收出口，跟着收到同一条事件流。

## 2. 实现是否按设计完成

已经按设计完成。单一事件源已经落地：三类运行环节现在都走同一套记录流程来记录开始和结束，旧的“事后批量补记”方式已经清掉，因此不会再凭空重复发阶段事件。

收尾时还发现并修复了一个静默降级回归：主模型不可用、系统切到备用模型时，那条“已经降级”的告警一度没有被任何接入方收到。现在这条告警会同时进入黑匣子记录文件，也会同步送到实时查看的一侧。这里遵守了黄金原则：没有把已有功能悄悄删掉，而是把该保住的降级告警保住了。

验证也完成了。红灯先行已经做过：先写出能抓住问题的失败测试，确认它确实会失败，再修到通过。两轮实现审查都放行，分别覆盖架构纯净度和 PM 视角可验收性；文档同步也经过 PM 替身审查放行。测试方面，主控独立复跑确认：引擎全套 1128 项全部通过，Studio 后端全套 403 项全部通过，不是只跑了局部子集。

有一处需要如实说明的过渡安排（为避免只报好的一面）：这次主线的事件流已经统一好了，但其中“试跑/预测”这条接入路径目前还是用一个临时的过渡接法对接这套统一事件流，属于已知的、写在下一阶段计划里的过渡方案，会在下一个 PR（PR-2）里完成彻底的原生替换。它不影响本次主线功能的正确性，主线和实时查看看到的都是同一套事实。

## 3. 完成后的功能逻辑

现在运行一个任务时，每发生一件重要的事，都会立刻进入这次运行专属的黑匣子记录文件：开始运行、某个阶段开始、某个阶段结束、请求了一次大模型、调用了一个工具、整次运行结束，都会按同一条事件流记录下来。

如果接入方，比如 Studio 页面，想实时展示这些进度，只要接上一个接收出口，就会同步收到同样的事件流；如果没有接实时展示，也不影响黑匣子照常记录。这样一来，事后排查和实时查看看到的是同一套事实，不再是两套各自维护的记录。
