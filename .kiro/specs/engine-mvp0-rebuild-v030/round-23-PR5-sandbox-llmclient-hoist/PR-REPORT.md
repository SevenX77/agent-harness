# PR-5 完成报告

## ① 问题是什么 + 为什么要改

这次改动解决的是两个引擎底层稳定性问题，目标是让多个 skill 并行加载和长期运行时更可靠。

第一个问题是沙盒模块串台。引擎加载不同 skill 自带的 Python 文件时，如果两个 skill 各有一个同名文件，例如都叫 `schemas.py`，加载过程会临时往 Python 全局注册表里登记。旧实现登记后不撤销，后加载的内容可能覆盖或干扰先加载的内容；更严重的是，如果进程里原本已经合法加载过同名模块，旧的清理方式也可能把它误删。结果就是两个 skill 明明应该互相隔离，却可能互相串台，表现会很诡异，也很难排查。

第二个问题是底层大模型客户端重复创建和连接泄漏。引擎会复用底层大模型客户端，这些客户端内部带着网络连接池。旧实现在高并发下可能出现两个请求同时发现“还没有可复用客户端”，于是各自创建一个，造成重复连接和资源浪费。同时，长期运行的进程，例如命令行监听模式或 Studio，没有统一的关闭入口，网络连接可能只增不减，运行久了就有内存或连接耗尽风险。

## ② 实现是否按设计完成 + 论据

实现已按设计完成，并经过红灯先行验证、源码修复、双重审计和全量回归验证。

验证过程先写了会失败的测试，证明两个问题都是真实存在的：同名 skill 文件加载后会留下全局痕迹；高并发首次请求会重复创建底层客户端；长期运行场景缺少统一释放入口。随后再写实现让这些测试转绿，属于真实的先验失败、后验修复，而不是事后补测试。

最终全量测试结果是 `1011 passed / 0 failed`。这说明本次修复没有只让新增用例通过，也没有破坏现有执行、加载、运行、工具、模型、集成等测试面。

本轮还经过两类审计：工程审和 PM 替身审。两边最终都判定通过。审计过程中，PM 替身审计员发现了一个我在新实现里引入的回归风险：撤销临时登记时写得太粗暴，可能把进程里本来合法存在的同名模块也一起移走。这个问题已经修掉：现在加载前会先拍快照，加载结束时只撤销自己新加的内容；如果原本就有合法内容，则恢复成原样。这个场景也补了防回归测试，防止以后再犯。

另一个审计补强点是连接释放流程。现在释放所有底层客户端时，单个释放失败不会中断后续释放，也不会静默吞掉异常；它会记录日志，并继续释放剩余连接，最后清空整体资源状态。

## ③ 改完之后功能逻辑

沙盒加载现在变成了短时、可恢复、无残留的流程。加载某个 skill 自带文件时，引擎只在加载那一刻临时登记；加载完成后立刻撤销自己新增的登记。如果加载前进程里已经有合法的同名内容，引擎会在结束后恢复原样。这样不同 skill 的同名文件会彻底隔离，不再互相串台，也不会碰坏进程里已有的模块。

这个清理动作发生在必要的解析完成之后，所以不会破坏运行期校验。即使加载过程中出错，也会走收尾清理，避免留下半成品状态。

大模型客户端现在也变成了可控的资源生命周期。高并发首次请求时，“查找是否已有、没有就创建、创建后保存”这三个动作会作为一个完整动作执行，不会被另一个请求插进来。因此同一个配置下首次请求只会创建一个底层客户端，后续请求复用它。

长期运行进程现在有统一关闭入口。命令行、Studio 或服务进程在退出、重载或重置时，可以一次性释放所有底层网络连接。释放时即使某一个连接关闭失败，也不会影响其他连接释放；失败会被记录下来，便于后续排查。这能降低长期运行时连接堆积和内存耗尽风险。
