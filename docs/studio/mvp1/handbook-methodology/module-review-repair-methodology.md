# 模块审查修复优化方法论

本文是一份可复用到任意项目的执行文档，用来指导团队从一个模块的混乱现状，产出一份类似 `temp/studio-mvp1-12d-repair-framework-2026-06-15.html` 的“可读、可修、可验收”的模块审查修复手册。

它不是原则清单，而是一套落地流程：先定义模块本体，再拆语义层和能力层，最后用固定页面结构、固定字段、固定验证门禁，把设计、修复、验收和证据分开呈现。

## 0. 最终产物

完成一次模块审查修复手册后，至少应得到三个产物：

| 产物 | 作用 | 责任人 |
| --- | --- | --- |
| HTML 手册 | 面向主线程和执行者阅读，提供导航、进度、每个父子节点的设计/修复/验收页。 | 主线程或唯一整合者 |
| 子节点审查稿 | subagent 或模块负责人输出的可合并草稿，不能直接改 HTML。 | 各子节点 owner |
| 验证证据 | RED/GREEN 测试、DOM 检查、禁词检查、导航检查、Playwright 截图和人工验收记录。 | 执行者 + reviewer |

交付标准是：另一个人只看手册，就能知道这个模块为什么存在、边界在哪里、当前哪里有问题、先修什么、怎么写测试、如何验收、哪些风险还没消掉。

## 1. 什么时候需要做模块审查修复手册

出现以下任一情况，就应考虑做模块审查修复手册：

| 触发信号 | 典型表现 | 为什么需要手册 |
| --- | --- | --- |
| 模块边界反复失守 | 业务层直接调用内部 SDK、UI 自己推导后端状态、运行时绕过 store。 | 单点修复会复发，必须先把 owner 和访问路径写清。 |
| 多个缺陷共享同一根因 | 看似是接口、UI、测试三个问题，实际都是同一个语义归属不清。 | 需要按父节点聚合问题，而不是按文件名散修。 |
| 旧实现名称误导设计 | 团队把 adapter、hook、bridge 当成架构层，而不是接入方式。 | 必须从第一性原理重新定义模块本体。 |
| 修复牵动多条路径 | API、前端、运行时、存储、测试、桌面 shell 同时受影响。 | 需要父节点页讲设计，修复页讲路径，子节点页讲验收。 |
| subagent 并行后难以合并 | 多个人同时改一份 HTML 或给出互相矛盾的结论。 | 需要统一草稿格式和唯一整合入口。 |
| 状态页已经变成流水账 | 页面充满“当前做了什么”，但读者看不出正确架构。 | 需要分离稳定设计和动态修复状态。 |

不需要做完整手册的情况：

- 只是单个局部 bug，owner 清楚，影响面小，测试能直接覆盖。
- 只是依赖版本升级或样式微调，不涉及模块边界、语义归属或跨层调用。
- 已有同类手册且本次只是补一个子节点，可以直接追加子节点验收页。

## 2. 从第一性原理定义“模块本体”

模块本体不是文件夹名，不是类名，也不是某个 adapter。模块本体是这个模块在系统中独立存在的理由。

定义模块本体时，按下面顺序写，不要跳步：

1. 这个模块解决什么问题。
2. 它拥有哪类事实、状态、规则或执行能力。
3. 它对外承诺什么稳定接口或行为。
4. 它不拥有什么，即哪些事情应该归别的模块。
5. 它如何失败，失败时错误由谁定义、谁展示、谁恢复。
6. 它的生命周期是什么：创建、读取、更新、删除、发布、恢复、过期或封存。
7. 哪些调用方可以使用它，调用方只能带什么输入，不能绕开什么边界。

### 2.1 模块本体卡片模板

每个父节点先写一张本体卡片：

```md
## Mx · <模块名>

### 模块本体

- 解决的问题：
- 拥有的事实/状态/能力：
- 对外承诺：
- 不拥有：
- 主要调用方：
- 主要失败模式：
- 生命周期：

### 一句话边界

<模块> owns <事实/能力>；<调用方> 只能通过 <接口/能力> 消费；<模块> 不负责 <非职责>。
```

示例：

```md
## M3 · RuntimeStateStore

### 模块本体

- 解决的问题：让 resume/checkpoint 的运行态可恢复、可并发控制、可防止旧 worker 覆盖新状态。
- 拥有的事实/状态/能力：lease、heartbeat、snapshot、restore、fencing token。
- 对外承诺：同一 run 同一时刻只有一个有效 writer；旧 token 写入会得到 state.lease_fenced。
- 不拥有：最终运行产物、trace 展示、UI 操作文案。
- 主要调用方：Engine resume path、Studio resume API、运行时 checkpointer bridge。
- 主要失败模式：state.lease_conflict、state.lease_fenced、state.not_found。
- 生命周期：acquire -> restore -> heartbeat/snapshot -> release。

### 一句话边界

RuntimeStateStore owns 可变运行态和并发写入保护；Engine resume 只能通过它恢复和写快照；它不负责 run artifact 的不可变归档。
```

### 2.2 禁止从这些东西开始定义模块

不要用下面方式定义模块：

- “这个模块就是 `xxx.py` 里的那些函数。”
- “这个模块就是 adapter 层。”
- “这个模块是为了修某个测试失败。”
- “这个模块就是前端页面上那个按钮。”
- “现在代码怎么写，它就是什么。”

正确做法是先定义事实和承诺，再映射到代码、接口、UI 和测试。

## 3. 区分语义层、能力层和接入方式

审查手册最容易出错的地方，是把 adapter、bridge、hook、presenter 写成架构层。它们通常不是模块本体，而是某种接入方式。

### 3.1 两类核心层

| 层级 | 定义 | 拥有什么 | 不拥有什么 | 常见测试 |
| --- | --- | --- | --- | --- |
| 语义层 | 定义业务事实、状态、规则、用户意图和一致性。 | 对象模型、状态机、owner 规则、错误语义、生命周期。 | 通用执行细节，例如文件怎么原子写、HTTP 怎么重试、DOM 怎么渲染。 | contract tests、状态机测试、owner boundary guard。 |
| 能力层 | 提供可复用执行能力。 | 安全执行、传输、原子性、并发保护、重试、恢复、封装底层平台。 | 业务字段含义、UI 文案、领域规则、发布决策。 | 能力 contract、错误映射测试、路径/权限/并发测试。 |

判断规则：

- 如果它决定“这个事实是什么意思”，它在语义层。
- 如果它决定“如何安全执行这个操作”，它在能力层。
- 如果它只是把一种调用形式接到另一种调用形式，它是接入方式。

### 3.2 接入方式词典

| 接入方式 | 作用 | 可以做 | 禁止做 | 典型验证 |
| --- | --- | --- | --- | --- |
| adapter | 把调用方接口翻译成 owner 模块接口。 | DTO 转换、transport 切换、ResponseEnvelope 映射。 | 重新制定 owner 业务规则、私自 fallback、私自 materialize。 | adapter contract、静态 guard 禁止业务分支。 |
| bridge | 跨运行时、进程、宿主或平台连接能力。 | Tauri command、native host、LangGraph checkpointer bridge。 | 把平台细节变成业务语义源头。 | 集成测试、权限测试、错误透传测试。 |
| hook | 前端生命周期和状态订阅封装。 | 调 API、管理 loading/error、订阅事件、清理资源。 | 决定后端语义、硬编码 owner 状态机。 | React hook tests、断线重连测试。 |
| presenter | 把 owner 事实渲染为用户可读 UI。 | 状态展示、排序、分组、局部错误展示。 | 自己推断真实状态、吞掉 owner error。 | 组件测试、可见文案测试、截图检查。 |

### 3.3 分类决策树

```text
这个对象是否定义业务事实或状态含义？
  是 -> 语义层
  否 -> 它是否提供通用执行能力？
       是 -> 能力层
       否 -> 它是否翻译两个模块的契约？
            是 -> adapter
            否 -> 它是否跨宿主/进程/平台？
                 是 -> bridge
                 否 -> 它是否封装前端生命周期？
                      是 -> hook
                      否 -> 它是否只负责展示 owner 事实？
                           是 -> presenter
                           否 -> 回到模块本体，重新定义
```

## 4. 页面结构设计

推荐页面顺序固定为：

```text
S0 总章
  M1 父节点设计页
  M1 父节点修复页
  M1.1 子节点验收页
  M1.2 子节点验收页
  ...
  M2 父节点设计页
  M2 父节点修复页
  M2.1 子节点验收页
```

### 4.1 S0 总章

S0 是整本手册的入口，不写单个模块的细节。它负责建立阅读坐标：

1. 这份手册解决什么。
2. 当前 worktree、branch、基线、状态页路径。
3. 整体波次或推进顺序。
4. 每个节点固定 routine。
5. 通用方法论。
6. 全局验证门禁。
7. subagent 分工和合并规则。

### 4.2 父节点设计页

父节点设计页只讲稳定设计，不写动态进度。它回答：

- 这个模块为什么存在。
- 模块本体是什么。
- owner 怎么切。
- 语义层、能力层和接入方式怎么分。
- 对外接口、状态、错误、数据流是什么。
- 调用方如何使用它。
- 哪些事情明确不属于它。

父节点设计页的读者应能在不看修复状态的情况下，理解正确架构。

### 4.3 父节点修复页

父节点修复页只讲动态修复路径。它回答：

- 当前哪里有问题。
- 修复顺序是什么。
- 每个子节点落点是什么。
- 需要哪些 RED/GREEN gate。
- 当前证据和剩余风险是什么。
- 哪些问题已经由本轮精修沉淀成通用规则。

设计页和修复页必须分开。否则读者会把“当前状态”误认为“正确设计”。

### 4.4 子节点验收页

子节点页用于单点修复和验收。它不重新讲父节点大设计，只引用父节点边界，然后落到具体问题：

1. 问题背景。
2. 正确设计。
3. 当前现状。
4. 修复目标。
5. 自动化/静态验证。
6. 手工验收。
7. 放行判据。

禁止写法：

- 不要在 S0 写某个子节点的大段实现细节。
- 不要把波次写成无证据的乐观排期。
- 不要只写“大家按 TDD 做”，必须写 RED/GREEN 的检查命令和证据路径。

```md
| --- | --- | --- | --- |
| 语义层 | <...> | <...> | <...> |

<一句话边界 + 2-4 段解释。>

| --- | --- | --- | --- | --- |
```

禁止写法：

- 不在设计页写“当前还没修完”“本轮已完成”这类进度。
- 不把 adapter 写成所有调用方必经的通用架构层，除非它确实是模块本体。
- 不用“应该、尽量、未来考虑”替代接口和错误契约。

```md
<按依赖关系说明先修什么、再修什么。>

## 本轮问题记录

| 问题 | 处理原则 | 是否已同步到设计页 |
| --- | --- | --- |

| 子节点 | 修复目标 | 验证重点 | 当前状态 |
| --- | --- | --- | --- |

| 门禁 | RED 应如何失败 | GREEN 应如何通过 | 证据 |
| --- | --- | --- | --- |

## 剩余风险

| 风险 | 影响 | 后续 owner | 阻塞放行吗 |
| --- | --- | --- | --- |
```

禁止写法：

- 不在修复页重新解释整套设计，设计页已有的内容只引用。
- 不把“跑过一次”写成“已放行”，必须有命令、截图或人工验收证据。
- 不写无 owner 的风险。

### 5.4 子节点验收页模板

```md
# Mx.y · <子节点名称>

## 状态

- 当前状态：ok / partial / bad / review
- 归属父节点：Mx · <父节点名称>
- 父节点边界：<引用一句话边界>

## 问题背景

<旧问题为什么会出现，它破坏了哪个边界。>

## 正确设计

<这个子节点在正确架构里应是什么样。>

## 当前支线现状

> <当前代码/页面/测试证据，必须具体。>

## 修复目标

<可执行目标，不写抽象愿望。>

## 自动化 / 静态验证

- <测试 1：文件/命令/断言>
- <测试 2：文件/命令/断言>
- <静态 guard：扫描范围/禁止模式/allowlist>

## 手工验收

1. <打开哪里>
2. <点击什么>
3. <应看到什么>
4. <不应看到什么>

## 放行判据

- <所有 RED 已转 GREEN>
- <UI/接口/运行时主路径被覆盖>
- <错误态和取消态被验收>
- <证据已写回父节点修复页>
```

禁止写法：

- 不写“检查一下能不能用”，要写具体入口、动作和预期结果。
- 不把单测替代人工验收，特别是 UI/桌面/浏览器路径。
- 不在子节点页引入新的父节点设计结论；若发现设计变了，先改父节点设计页。

### 5.5 表格使用规则

表格适合承载可扫描信息：

- owner 矩阵。
- 接口字段。
- 状态/错误码。
- 调用方使用矩阵。
- RED/GREEN 门禁。
- subagent 分工。

表格不适合承载长逻辑。超过两句话的内容，**拆成 list 或卡片，不写成大段落**（更新：早期版本说「写成段落」，现已统一为「拆 list/卡」，见 §6）。单元格里不要塞完整文章。

推荐表格列数为 2-5 列。超过 5 列时，拆成两个表或改成卡片。

## 6. UI 展示约定（统一 `card` 体系）

> **本节已更新。** 早期版本这里详列了一套旧组件词汇（`hero-card` / `repair-child-card` / `check-card` / 多种 `info-table` 用法 / `renderS0`·`renderParentDesign` 等渲染函数）。这套**已被取代**：所有手册现统一到**一个主组件 `card` + 少数辅件**，与《前端实施手册页面编写方法论》同一套约定。复刻时**不要**再保留早期那套多卡片词汇。

### 6.1 一个主组件 `card`

手册里绝大多数「块」都是**标题 + 右上≤1 标签 + 若干字段**——模块本体卡、owner 矩阵项、子节点验收卡、状态卡、门禁卡……全部是同一个 `card(标题, 字段[], 标签?)`，不为每种再起一个 class。子部分（如模块的「能力清单」）是**卡内字段**，不另起并列卡。

### 6.2 只有这些不是 card（辅件）

`card-grid`（并排多张卡）· `flow`（顺序流 / 数据流，编号串联）· `rule`（条件 → 结果，如 RED/GREEN 门禁、状态合成、错误码短路）· `tags`（schema 字段标签云）· `diagram`（形态变换图，仅当文字讲不清形态变化时）· `callout`（风险 / 当前状态 / 结论）· `table`（**每格都简练**的真表格，如 owner 矩阵、状态码、调用方矩阵）· `list`（要点，是某字段的值）· `shot`（截图占位行）· `badge`（状态 / 类型标签）。判定：新内容先问「是不是 标题+几个字段？」是 → `card`；不是 → 在辅件里对号入座。

### 6.3 一色一义

🟢 绿=成功 / ok / 「做」 · 🔴 红=失败 / bad / 「不做」 · 🟡 琥珀=partial / 警示 / 等 · 🔵 蓝=信息 / 链接 / 装饰 · ⚫ 灰=停用 / 类型。**每个 badge 变体必须在 CSS 有定义**（别出现透明裸徽章）；装饰性的绿降级为蓝，绿只留「成功 / ok / 做」。

### 6.4 prose 不糊成段；大段叙述拆 list

超过 2~3 句的内容**拆成 list / 卡**，不写成大段落（取代早期『长逻辑用段落』）。先判断它是步骤（编号 / `flow`）、并列要点（项目符号）还是结论+证据（结论先行）；一条 list = 一个原子点。表格只放每格简练的数据。

### 6.5 模板与状态值

复刻仍可从 `module-review-handbook-template.html` 起步，但**组件一律按上面 `card` 体系收敛**，删掉早期 hero / check / repair-child 多套卡。状态值固定 `ok / partial / bad / review`。视觉骨架不变：左 sticky 导航 + 右单列阅读（max-width ~880-960px）+ hash 路由分页，不做营销式 hero；callout 只用于风险 / 状态 / 结论；移动端隐藏 sidebar、补窄屏断点。HTML 由**唯一整合者**改，subagent 只产数据 / 草稿。

## 7. 三类模块如何套用同一方法论

### 7.1 接口模块

接口模块的重点是契约和 owner 边界。

父节点设计页必须写：

- owner 是谁。
- DTO/schema 字段。
- transport 与业务错误如何区分。
- adapter 是否只是翻译层。
- 调用方禁止绕过哪些路径。

子节点常见拆法：

- 唯一入口。
- transport switch。
- 错误族。
- 静态 import guard。
- contract parity。

验证重点：

- contract tests 覆盖成功和错误。
- AST/import guard 禁止业务层直接 import owner 内部实现。
- http/in-process 或本地/远端两种 transport 返回同形 DTO。
- 错误不被吞成 generic 500。

### 7.2 UI / 前端功能模块

UI 模块的重点是用户意图、状态来源和展示职责。

父节点设计页必须写：

- 用户要完成什么任务。
- UI 展示的事实来自哪个 owner。
- hook 做哪些生命周期事情。
- presenter 只渲染哪些事实。
- 哪些状态不能由前端本地猜测。

子节点常见拆法：

- 数据加载和错误态。
- 保存/取消/冲突。
- 空态/禁用态/权限态。
- 事件订阅与重连。
- 可见文案和交互验收。

验证重点：

- 组件测试覆盖 loading、success、error、empty、disabled。
- hook 测试覆盖 API 调用、取消、清理、重连。
- 文案禁词检查禁止旧状态词或调试词进入 UI。
- Playwright 点击主成功路径和明显失败/取消路径。

### 7.3 运行时模块

运行时模块的重点是生命周期、并发、恢复和证据。

父节点设计页必须写：

- 运行态和运行产物是否分离。
- 哪些状态可变，哪些对象 seal 后不可变。
- 并发写入如何防护。
- idempotency、lease、fencing、cursor、checkpoint 如何定义。
- 错误如何进入 trace/event/UI。

子节点常见拆法：

- artifact store。
- runtime state store。
- event stream。
- resume/checkpoint。
- trace/error envelope。

验证重点：

- Spy store contract 断言调用顺序。
- 并发测试覆盖冲突和 fencing。
- seal 后拒写、hash mismatch 可见。
- 断线重连不重复事件，cursor gap 可见。
- UI 不把运行时错误降级成通用网络失败。

## 8. TDD / RED-GREEN 验证流程

每次修改 HTML 手册或其生成逻辑，都按 RED-GREEN 做。不要先改页面再补测试。

### 8.1 RED 阶段

先写会失败的检查：

| 检查 | RED 应失败的原因 |
| --- | --- |
| DOM 渲染检查 | 新页面缺 section、缺 nav、重复 id、active 页面为空。 |
| 文案禁词检查 | 出现旧术语、调试标签、TODO、待补、泛化空话。 |
| 导航检查 | `PAGES` 中有 pageId，但 TOC 或 DOM 找不到。 |
| 页面职责检查 | 设计页出现“当前风险/已完成/本轮修复”，修复页重复长篇设计。 |
| Playwright 截图检查 | 页面空白、导航不可点、分页文案溢出、移动端阅读列破碎。 |

### 8.2 GREEN 阶段

只做让 RED 变绿的最小改动：

1. 补数据字段。
2. 补 render 函数。
3. 调整页面结构。
4. 更新 CSS class 或响应式规则。
5. 重新运行 focused gate。

不要在 GREEN 阶段顺手重构无关模块。

### 8.3 DOM 渲染检查示例

```js
import { chromium } from "playwright";

const url = "file://" + process.cwd() + "/temp/module-review.html";
const browser = await chromium.launch();
const page = await browser.newPage({ viewport: { width: 1440, height: 1000 } });
await page.goto(url);

const sections = await page.locator(".doc-section").count();
if (sections === 0) throw new Error("no doc sections rendered");

const active = await page.locator(".doc-section.active").count();
if (active !== 1) throw new Error("expected exactly one active section");

const missingTargets = await page.evaluate(() => {
  return [...document.querySelectorAll('a[href^="#"]')]
    .map(a => a.getAttribute("href").slice(1))
    .filter(id => !document.getElementById(id));
});
if (missingTargets.length) {
  throw new Error("missing nav targets: " + missingTargets.join(", "));
}

await browser.close();
```

### 8.4 文案禁词检查示例

每个项目先定义自己的 deny list。常见禁词包括：

- `TODO`
- `TBD`
- `待补`
- `临时`
- `随便`
- `应该可以`
- 旧状态词，例如已经废弃的 `needs_setup`
- 调试标签，例如 `open repair page`，如果面向中文读者应替换成中文阅读标签

示例脚本逻辑：

```js
const banned = ["TODO", "TBD", "待补", "临时", "应该可以"];
const text = document.body.innerText;
const hits = banned.filter(word => text.includes(word));
if (hits.length) throw new Error("banned copy: " + hits.join(", "));
```

### 8.5 导航检查示例

```js
const result = await page.evaluate(() => {
  const navIds = [...document.querySelectorAll("[id^='nav-']")]
    .map(el => el.id.replace(/^nav-/, ""));
  const sectionIds = [...document.querySelectorAll(".doc-section")]
    .map(el => el.id);
  return {
    navWithoutSection: navIds.filter(id => !sectionIds.includes(id)),
    sectionWithoutNav: sectionIds.filter(id => !navIds.includes(id) && id !== "s0_overview")
  };
});

if (result.navWithoutSection.length || result.sectionWithoutNav.length) {
  throw new Error(JSON.stringify(result, null, 2));
}
```

### 8.6 Playwright 截图检查

至少保存这些截图：

| 截图 | viewport | 断言 |
| --- | --- | --- |
| S0 总章 | 1440x1000 | 左侧导航、进度、阅读列可见。 |
| 父节点设计页 | 1440x1000 | 首屏能看到模块本体和边界，不混修复状态。 |
| 父节点修复页 | 1440x1000 | 当前风险、子节点 repair cards、门禁可见。 |
| 子节点验收页 | 1440x1000 | 自动化/手工验收并排或合理堆叠。 |
| 移动端 | 390x844 | sidebar 隐藏，正文不溢出，分页按钮可用。 |

截图不是为了好看，而是为了确认页面非空、布局不重叠、长文案不溢出、导航和分页能工作。

## 9. subagent 使用规范

### 9.1 基本原则

多人协作时，只有一个角色可以编辑最终 HTML。其它 subagent 只能产出审查稿、字段草稿、测试建议或 review findings。

禁止多人同时改同一个 HTML。这样会产生三类问题：

- 页面结构互相覆盖。
- 状态口径互相矛盾。
- 主线程无法判断哪个版本是事实源。

### 9.2 推荐分组

| 分组 | 负责内容 | 输出 |
| --- | --- | --- |
| 架构审查组 | 定义父节点本体、owner、语义/能力层。 | `temp/review-mx-architecture.md` |
| 子节点执行组 | 每个子节点的问题、正确设计、修复目标、验证门禁。 | `temp/review-mx-y-child.md` |
| 验证组 | RED/GREEN 测试、DOM、禁词、导航、截图。 | `temp/review-mx-validation.md` |
| UI 手册整合者 | 唯一编辑 HTML，合并字段和页面结构。 | HTML 手册 |
| reviewer | 找真实 bug、遗漏证据、职责混写。 | `temp/review-mx-findings.md` |

### 9.3 subagent 任务书模板

```md
任务：审查 <Mx.y 子节点>

只读输入：
- <HTML 手册路径>
- <相关代码/测试路径>

禁止：
- 不编辑 HTML。
- 不改生产代码。
- 不改其它 subagent 的草稿。

请输出：

## 子节点摘要
- 父节点：
- 子节点：
- 当前状态建议：ok / partial / bad / review

## 问题背景

## 正确设计

## 当前现状证据

## 修复目标

## 自动化 / 静态验证

## 手工验收

## 放行判据

## 需要主线程决策的问题
```

### 9.4 合并协议

1. 主线程先收集所有 subagent 草稿。
2. 按父节点检查是否存在本体冲突。
3. 若子节点草稿和父节点设计冲突，先修父节点设计，不直接把冲突塞进子节点。
4. HTML 整合者只从已确认草稿复制字段。
5. 每次合并后跑 DOM、禁词、导航和截图检查。
6. reviewer 只提真实问题，不要求为了风格统一改动正确内容。

### 9.5 防止多人改同一个 HTML

执行规则：

- HTML 文件有唯一 owner。
- subagent 输出 Markdown 或 JSON 字段，不输出 HTML diff。
- 如果必须让 subagent 提 UI 建议，只允许给 class/section 建议，不允许直接改文件。
- 所有“已完成/ok”状态必须由主线程根据证据改，不由 subagent 自行宣布。

## 11. 主线程补进 HTML 时的重点

如果把本方法论补进现有 HTML，优先补这些内容：

1. S0 增加“什么时候需要做模块审查修复手册”，帮助读者判断适用场景。
2. S0 增加“模块本体卡片”和“语义层/能力层/接入方式词典”，避免以后再把 adapter 抬成通用架构层。
3. 父节点设计页统一收敛为稳定设计页，动态状态下沉到父节点修复页。
4. 父节点修复页增加 RED/GREEN 门禁表，不只列当前风险。
5. 子节点验收页补齐“自动化/静态验证”和“手工验收”的具体入口、动作、预期结果。
6. 增加文案禁词检查，特别是旧状态词、调试标签、TODO/TBD、含糊承诺。
7. 增加 DOM/nav 检查，保证每个 `PAGES` 条目都有 section 和 nav。
8. 增加 Playwright 截图检查，覆盖 S0、父设计页、父修复页、子节点页和移动端。
9. 增加 subagent 协作规则：subagent 只产草稿，HTML 只有唯一整合者修改。
10. 将 “D12 本轮精修问题记录” 抽象成通用“本轮方法论沉淀”，供其它父节点复用。

## 12. 与《前端页面编写方法论》统一的内容约定（本轮沉淀）

> 下面这些是本轮精修沉淀的**跨手册通用内容规则**，前后端手册一致。详细正反例见 `frontend-page-authoring-methodology.md`，这里只列要点，写每个字段时对照。

1. **术语必带解释，禁裸代号**：函数/类/文件/能力名第一次出现紧跟一句话括注「它干什么」；禁用无解释的内部代号（如 `D6`/`③a`/`维度 6`）。
2. **从文档自身视角写，不从对话上下文写**：不写「你最初让我参照的那本」「为什么不并进 X」这类只有看过聊天才懂的表述；靠「按本质分类」让区分不言自明。
3. **按本质分类，不按体积**：分类轴是「它是哪种东西」（语义层/能力层/接入方式；可复用单元/绑定某操作的逻辑），不是「大件/小件、简单/复杂」。
4. **不写行号，按「文件名 + 函数/对象名」引用**：行号会漂、嵌套路径易错；让实施者直接 grep 名字。引证据先确认函数真在该调用链上（别张冠李戴），名字写全别截断。
5. **两轴状态，自洽**：前端实施状态（符合/偏差/未实施）与后端契约状态（已实现/未实现/契约要改）分两轴标，避免「全绿却整页标黄」；徽章和说明别打架（别「ok」配「待确认」），能自查的查死。
6. **数据文件从消费方视角写**：给读写 API 就到此为止；落盘在哪、怎么落（原子写、权限、迁移）是 owner 内部细节，消费方不关心。
7. **大段叙述拆成结构化 list**：超过 2~3 句不糊成段；判断它是步骤（编号/flow）、并列要点（项目符号）还是结论+证据（结论先行），一条 list = 一个原子点。
8. **降级 = 偷换目标（禁）**：把「验证真能用」换成「能开机」、把「真跑」换成「mock 一下」= 作废；验证用真资源真跑。
