### 1.2 AST/schema 层的关键优化点

对 `core/manifest.py` 做逐行 diff（主仓 397 行 vs 新仓 463 行，246 行差异），实质优化是：

1. **拓扑从 Markdown body 搬进 typed YAML**：`phases: list[str]` + body XML → `phases: tuple[GraphPhaseRef,...]`，`GraphPhaseRef` 带 `id: pattern(^[A-Za-z][A-Za-z0-9_-]*$)`、`depends_on: tuple[str,...] min_length=1`、`output: bool`（必填），并有 `_dependencies_are_unique` 校验 `input` sentinel 误用/重复依赖/非法依赖名（新 `manifest.py:45-68`）。
2. **关闭 `metadata: dict[str, Any]` 逃生口**：`GraphManifest` 与 `PhaseNodeBase` 都删掉了 `metadata` 开放字段（旧 `manifest.py:209`、`:242`），schema 真正闭合。同时删掉死代码 `BatchSpec`。
3. **不可变化**：`list` → `tuple`（`phases`、`artifacts`、`fields`），配合 `ConfigDict(extra="forbid", frozen)`。
4. **跨文件系统安全**：phase id 大小写不敏感唯一性校验（`manifest.py:283-295` `_local_identifiers_are_unique`），避免同 bundle 在 Windows/macOS 上解析成不同目录集。
5. **必填性收紧**：`name: str|None` → `name: str = Field(min_length=1)`；`description` 由可空变必填非空。
6. **跨字段一致性**：`IterateSpec` 新增 `_mode_contract_is_complete`——`range[0] &lt;= range[1]`、`loop` 必须有 `accumulate`、`batch` 拒绝 `accumulate`（`manifest.py:258-267`）。
7. **各注册表去重**：`AgentNodeAST._registries_are_unique` 一次性校验 tools/subagents/subgraphs/references/examples/context_access 六个注册表重复（`manifest.py:367-381`）；`LogicNodeAST` 校验 actions 唯一。
8. **聚合诊断表格化**：`01-PORTABLE-GSKILL-V1.md:477-490` 列出 8 类"同轮必须全报"的缺陷（Root inventory / Agent Skills metadata / Graph inventory / Phase inventory / Phase DAG / Graph call / Agent capability / Artifact），禁止 first-error 行为。

**结论**：格式改动是**真实的结构性升级**，且方向正确（人机职责分离、拓扑单一真相源、闭合 schema、扁平复用注册表、artifact 提升为可提交声明）。但它是**主仓 AST 的定向重构，不是新建模型**——`parser.py` 430 行只差 12 行、`graph_assembler.py` 3341 行只差 119 行。

## 2. 执行模型：**不是根本不同，是在同一引擎前面加了一层 executor Port**（务必看清）

### 2.1 三个 executor，LangGraph 仍在底下

`domain/models.py:248-296` 定义闭集：`HostNativeExecutorConfig(kind="host-native")` / `CliExecutorConfig(kind="cli")` / `EmbeddedExecutorConfig(kind="embedded")`；`:352` 默认 `Field(default_factory=HostNativeExecutorConfig)`。

- **`embedded` = 主仓原样的 langchain 调 LLM API 路径**。`v1-alignment.md:313`：「现有 engine 路径已经放到显式 `embedded` executor 后面；provider clients 位于 `graph-skill-runtime[embedded]` optional extra，不在 base dependency 中。它不再是默认 executor。」`adapters/engine.py`(312 行) 是 `CurrentEngineAdapter`。
- **`host-native`（默认）= 把活交回宿主 coding agent**。流程（`v1-alignment.md:252-262`、`README.md:106-112`）：图跑到 AGENT 相位 → LangGraph SQLite checkpoint 持久化 → 在**独立**的 `&lt;state_root&gt;/agent-handoffs.sqlite3` 持久化 `AgentTask` → 返回 `RunResult(status="agent_required")`，公开 `checkpoint_ref = gskill-handoff-v1:&lt;task-id&gt;`（不泄漏 LangGraph 内部 id）→ 当前宿主 root agent 创建**一个 fresh native clean-context child** → child 返回满足 `task.output_schema` 的 JSON → 宿主经 `submit_agent_result`(MCP/SDK/`python -m ... submit`) 提交 → runtime 校验 identity+schema，写回同一 graph state 继续跑。
- **`cli` = runtime 自己起厂商 headless CLI 的新进程**。六个 adapter：claude / codex / copilot / cursor / gemini / opencode（`v1-alignment.md:266-306`）。每个 task 一个新进程 + 新临时 cwd，不传 resume/session id；完整 prompt 只走 stdin 或临时 `agent-task.md`，**不进 argv**；Windows 用 Win32 Job Object（`KILL_ON_JOB_CLOSE`）拥有进程树，POSIX 用 process group + `SIGTERM`→1s→`SIGKILL`，macOS `killpg` `EPERM` 时才走 bounded `ps` 窄回退。

**所以答案是：默认路径确实把活交给宿主 coding agent / 厂商 CLI，但 langchain 路径没删，只是降级为显式 opt-in 的 `embedded`。**

### 2.2 host-native 的适用面目前非常窄（这是最大的成熟度陷阱）

`adapters/host_native.py:39-70` `host_native_agent_phases()` 在执行前直接 raise，**以下形状全部不支持**：

- registry 子图内的 AGENT 相位（`host_native.py:50-61`）
- graph 级 iterate 含 AGENT（`:69-`）
- phase 级 iterate 的 AGENT
- 与其他相位**不可比较的并行分支**里的 AGENT
- 必须 `SqliteCheckpointStoreConfig`

`v1-alignment.md:250` 原文确认：这些「都会在执行前以 `GSKILL_INVALID_REQUEST` 失败，不会落入 embedded 模型路径」。`cli` executor 复用同一批限制，**且额外**在 handoff 创建前以 non-retryable `task-capability-missing` 拒绝声明了 `tools`/`subagents`/`subgraphs`/`context_access` 的 AGENT（`v1-alignment.md:270`）。

换句话说：**新仓的 host-native/cli 只能跑"root DAG 里串行、无子图、无迭代、无工具、无子 agent"的 AGENT 相位**。主仓 Studio 现有 skill 的绝大多数形状（子图 + iterate + tools）在新仓要么落回 `embedded`（= 又回到 langchain 调 API），要么直接失败。

## 6. Studio 转换器与集成设计

### 6.1 converter：转什么、怎么转、单向

**入口**（`01-PORTABLE-GSKILL-V1.md:496-502`）：
```
python -m graph_skill_runtime migrate studio-skill SOURCE DESTINATION [--runtime-config PATH] [--preset-id ID]
```
`SOURCE` = legacy v0.3 Studio skill root；`DESTINATION` = **全新** v1 root；`--runtime-config` 显式指旧 `studio.runtime_config.v2`，省略时读 `SOURCE/.workspace/runtime_config.json`（不存在则只转 portable source）；`--preset-id` 默认 `migrated`。

**实现**：`src/graph_skill_runtime/migration/studio_v030.py`（1,470 行）+ `atomic_publish.py`（88 行，Linux `renameat2(RENAME_NOREPLACE)` / macOS `renamex_np(RENAME_EXCL)` / Windows `os.rename`，**明确拒绝把裸 POSIX `rename` 当 fallback**）。

**执行模型**（`:504`）：只读 preflight → 同 filesystem 临时 sibling 目录生成完整输出 → create-if-absent 发布。**不修改 SOURCE，不覆盖任何 destination 文件，失败不留 partial destination。**

**映射表**（`:508-518`）：

| Legacy | v1 |
|---|---|
| 根 `GRAPH.md` metadata | 根 `SKILL.md` 的 Agent Skills metadata + 根 `graph.yaml` 的 graph metadata |
| `GRAPH.md` phase 注册表 + body `&lt;phase&gt;` edge/output | `graph.yaml.phases[]` 的 `{id, depends_on, output}` |
| `phases/&lt;id&gt;/LOGIC.md` | 同名同位 |
| `phases/&lt;id&gt;/SKILL.md` | `phases/&lt;id&gt;/AGENT.md` |
| `SUBGRAPH.md` 的 path | `SUBGRAPH.md.graph` registry id |
| Agent `subgraphs[].path` | `AGENT.md.subgraphs[].graph` registry id |
| 本地被引用的旧 subskill root | `graphs/&lt;graph_id&gt;/graph.yaml` + 该 graph 的 `phases/` |
| 旧 runtime artifact definitions | 根 `graph.yaml.artifacts` |
| 旧配置里已启用的 artifacts | `gskill.toml` preset 的 `artifact_requests` |

**runtime_config 拆分**（`:526-537`）：`inputs.active.root`→`RunPreset.inputs`；`inputs.active.phases`→`RunPreset.bindings`（地址规范化为 `&lt;graph_id&gt;/&lt;phase_id&gt;/&lt;field&gt;`）；node params→`node_overrides`；compare candidates→`compare_candidates`；breakpoints→`breakpoints`；`{stem,fields,mode,format}`→`graph.yaml.artifacts`；**import manifest / removed / conflict / Studio mirror state → Studio adapter state 或迁移报告，不进 portable/runtime declaration**。

**确定性 artifact id**（`:543-551`）：补默认值→NFC+trim 规范化→`{stem,fields,mode,format}` canonical JSON → SHA-256 → stem 转 kebab 候选 → 冲突时加 `&lt;candidate&gt;-&lt;hash-prefix&gt;`（≥8 hex，延长到全 bundle 唯一）。**数组重排不改 id；完全相同的重复 definition 判失败，不静默合并。**

**迁移报告**（`:555-562`）：`.gskill-migration-report.json`，schema `gskill.migration-report.v1`，含 graph/phase 文件映射、reference→id 映射、artifact index→hash→id 映射、config 字段归属分类、preset id、converter 版本。**不复制 secret value。**

**方向：严格单向**（`:598-602`）：「原子切换后的 runtime core 只读取本文格式。Legacy parser 只能由显式 `migrate studio-skill` adapter 调用；`compile`、`predict`、`run`、SDK 和 MCP **不做格式嗅探，也不在新解析失败时回退 v0.3**。」无反向 converter。

**converter 的硬失败边界**（`:591-596`，这是主仓迁移风险的核心）：
- `SOURCE == DESTINATION`、destination 已存在、destination basename 不是合法 Agent Skills name、destination 在 source 内 → 写入前失败
- 未知 legacy 字段、**未解决的 Studio conflict**、重复 graph/phase/artifact definition、graph id 规范化冲突、无法解析或越界的 graph reference → 失败
- **「Converter 只接受可明确提升为 flat registry 的直接本地 legacy subskills。任何 legacy subskill 内再包含 subskill、依赖物理嵌套推断 parent，或同一内容出现多个不一致 owner 时失败。」**
- Secret value 或不能安全归属的配置项 → 失败并进 diagnostics（不猜、不丢、不复制）

## 7. 我的判断

### 先把三条路的真实代价摊开

**路 A：现在就把新仓当 engine 基础重盘主仓计划**

代价：
- 主仓 Studio 87 处 engine import 要重新对着 77 符号公开面 + 8 个 MCP tool 收口；上表 12 类内部模块必须走"提升为 Port"或"Studio 重写"二选一。
- Gateway 13,469 行 + 477 测试无处安放。新仓 `README.md:20` / `v1-alignment.md:30/447` 三处明确不接。主仓要么继续养一个新仓不认的外部包，要么把它做成新仓的 `AgentExecutor`/model-resolver adapter（**新仓没定义这个 Port**）。
- 立刻撞上 Phase 3b 未实现：HITL、断点、子图 AGENT、iterate AGENT、并行 AGENT、实时事件流、golden create/promote 全缺。Studio 的核心旅程（`DELIVERY_LEDGER.md` 第 3-9 步：compile→predict→run→读 trace→改→复跑→定 golden→publish）**至少 4 步落地不了**。
- 新仓当前状态本身不稳：113 个未提交文件在特性分支、入口身份 2 天翻转 2 次、命名未裁决、未上 PyPI、Phase 4 只有 Codex/Windows 一条实机证据。

收益：格式与架构一次到位，不做二遍功。

**路 B：主仓按自身现状先做完模块化重整再迁**

代价：
- **主仓 `DELIVERY_LEDGER.md` 已经明确否决过这条路**。2026-07-30 用户裁决原文：「本冲刺只做接线，**不做 ontology 改造、不做模块化重构、不做文档系统工程**（三者对闭环零贡献，明确后置）」。再提模块化重整 = 推翻既有裁决。
- 主仓最近 39 个提交（2026-08-27 起）全是 Studio/settings/canvas/ledger 的批示轮工作（R3-1..R3-16），engine 只动了 1 次。**主仓当前的产品节奏在 UI/闭环，不在 engine**。插入重整会中断这条节奏。
- 重整完成后仍要做一次格式切换（GRAPH.md→SKILL.md+graph.yaml），且新仓在此期间会继续跑（它已有 9 个提交的架构差），漂移只会更大。
- 最致命的：**重整的目标形状就是新仓已经做出来的形状**（domain/application/ports/adapters/integrations + typed facade + closed models）。这是纯粹的重复劳动。

收益：不打断当前闭环冲刺。

**路 C：混合——分域对齐**

代价：需要明确的域切分与门禁，管理成本高。风险是切分不清导致"两边都改一半"。

收益：把不可分割的大切换拆成可验收的小切换；每个域独立止损。

### 我倾向 C，且要在两周内启动，具体切法如下

**理由的核心是三个不对称：**

**① 漂移窗口现在几乎为零，但不会一直为零。** 分叉 4 天，engine 侧漂移 = 1 个提交（`#1072`），gateway 侧 = 0。同时那 1 个提交已经是一条**用户裁决过的实证缺陷**（新仓 `manifest.py:422` 的 `DEFAULT_LLM_ROLE` 兜底，主仓已证明会导致"编译全绿、运行必崩"）。两个 owner 各自演化 `core/manifest.py`、`core/runner.py` 的成本会随时间超线性增长。**这一条把"慢慢来"的选项排除掉了——B 的最大风险不是慢，是漂移不可逆。**

**② 但新仓的执行模型现在还接不住 Studio。** §2.2 那份 host-native/cli 拒绝清单（registry 子图 AGENT / iterate AGENT / 并行 AGENT / tools / subagents / context_access）加上 `README.md:112` 的"无实时事件订阅"和 Phase 3b 的"无 HITL resume"，意味着**今天把 Studio 接到新仓，Studio 会立刻降级成一个只能跑串行 LOGIC 图的壳**。`v1-alignment.md:25` 自己把这些标成「drafted；未实现」。**这一条把 A 排除掉了。**

**③ 血缘决定了这不是"融合两套系统"，而是"给一套系统收敛 owner"。** parser 差 12 行、graph_assembler 差 119 行、io/ 目录完全同构。真正的新增全在**外壳**（adapters/application/domain/ports/integrations，约 8,000 行）和**格式层**（manifest.py 的 246 行差 + migration 的 1,567 行）。**这意味着按域切分是物理可行的**——不像两套异构实现那样必须整体切换。

**具体切法（域 → 处置 → 门禁）：**

| 域 | 立刻对齐新仓 | 照旧留主仓 | 判据 |
|---|---|---|---|
| **格式（GRAPH.md → SKILL.md+graph.yaml）** | ✅ **是**，且**只在新仓改** | — | 格式是所有下游的上游。主仓 `docs/engine/graph-skill-runtime/README.md` 的切换条件已写死：「实现完成；迁移与跨宿主验证通过；所有代码、contract maps、示例和文档引用重钉到新契约；旧格式在同一次切换中删除。**切换前不得维护双读格式**」。这条纪律必须保住 |

6. converter 对**真实用户 skill**（不是 fixture）跑通一轮，含嵌套子图场景
