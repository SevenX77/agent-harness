# Round 27 契约冻结 PR 报告

## §1 设计是什么

这个 PR 的设计目标很简单：把“功能和对外能力一个都不能少”从口头原则变成工程基线。过去的问题是，某个能力被外部真实使用了，但没有被清楚写进契约；以后别人改动时，可能以为只是整理，实际却把外部依赖打断了。本 PR 做的“基线冻结”，就是把当前已经被使用的对外能力、核心功能、技能编写规范全部登记成固定基线。以后任何删除、改名、改结构、改文档正文的动作，都不能悄悄发生；如果确实要改，必须有明确理由和 PM 批准。

## §2 实现是否按设计完成

实现已经按设计落地。第一，对外能力已经穷尽冻结为 65 项，其中有 12 项虽然名字上像内部能力，但已经被外部真实使用，所以标为“事实上的契约、后续清理”；另有 6 项只被旧适配层使用，标为“待核实”。第二，核心功能整理为 30 项，每项都绑定到现有自动检查，避免“功能清单写了但没人守”。第三，14 份技能编写规范全部加了“已冻结”和“请勿编辑”标记，正文一个字没改，并用内容指纹锁死，任何字符变化都会被发现。

这套机制一共落了 5 道硬门：对外能力漂移门、规范文档指纹门、功能矩阵精确数量门、例外清单严格格式门、PM 个人审查门。第四轮又补掉了两个审计发现的漏口：之前保护人列表少覆盖了 3 个关键文件；功能矩阵原来是“至少 25 项”，现在改成“必须正好 30 项”。两位审计角色做了交叉复核，主控也用实际检查确认。现有 1048 项自动检查全部通过，没有回归。源码一行没动，符合本 PR 只做契约冻结、不改功能实现的边界。

## §3 完成后功能逻辑

从这个 PR 合并以后，任何人想动这 65 项对外能力、14 份技能规范、30 项核心功能，或者想动这套保护机制本身，都会先被自动门拦住。默认规则是：变了就失败，不能悄悄合入。

如果确实有正当理由要改，就必须走例外流程：在例外清单里写齐 7 件事，包括变更编号、PM 批准说明、理由、影响了哪些对外能力、影响了哪些字段、影响了哪些内容指纹、以及什么时候清理或失效。少写任何一项，整套检查都会失败。例外清单和所有保护门文件都绑定到 PM 个人审查，必须 PM 本人在平台上批准。也就是说，“功能/API 一个都不能少”从今天起不再靠记忆和口头提醒，而是由自动检查加 PM 审批共同兜底。
