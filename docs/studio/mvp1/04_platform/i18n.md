# i18n — 多语言本地化(横切基础设施)

> **Tier**: platform(横切 NFR;文档归 04_platform,治理条目见 [INDEX §11](../../INDEX.md#11-跨切约定-nfr-锁定-2026-06-01))
> **Owns**: studio 全栈多语言的**单一架构权威** —— 前端 react-i18next 词条 + 后端 `error_code`/`details` 契约 + 语言切换。**不** owns 各 region 的具体文案(那是各 region/capability 用 `t(key)` 引用)。
> **Status**: 全 `target-design`(代码未实现);**地基已就绪**:三层 `error_code` 体系 FROZEN `live`,前端 `llm-error-messages.ts` catalog `live` 但仅英文。
> **Related**: [settings region](../03_regions/README.md) · [compile-lint](../02_capabilities/compile-lint/mvp1-alignment.md)(引擎 `[F-v3-*]` 码)· 引擎 `error_registry.py` · 后端 `ErrorResponse` · [INDEX §11](../../INDEX.md)
> **核心决策**: 库 = **react-i18next**;架构 = **Strategy C(前端单权威翻译)**;引擎/网关**语言无关零改动**。默认 `en`,首发加 `zh-CN`,其他语言架构支持、按需加词条。

## 1. 服务职责 / 定义

studio 多语言的唯一架构权威。一句话契约:**后端只产机器码 + 结构化参数,前端用一套 react-i18next 词条把所有 UI 文案和后端错误码翻成当前语言。** 引擎/网关作为可复用库保持语言无关。

- **owns**:i18n 库选型、词条组织、语言切换、前后端翻译契约。
- **不 owns**:具体文案内容(各 region/capability 自己用 key 引用词条)。

## 2. 库选型(决策 + 备选)

**决策:react-i18next**(三件套:`i18next` 核心 + `react-i18next` React 绑定 + `i18next-browser-languagedetector` 语言探测插件)。

| 库 | 机制 | 包体积 | 类型安全 | 生态/便利 | 判定 |
|---|---|---|---|---|---|
| **react-i18next** | 运行时 JSON 词条 | ~8KB | 手写 `.d.ts` 声明合并 | **最大,Vite 零配置** | ✅ 选用 |
| LinguiJS | 编译期宏 + 编译步骤 | ~3KB | 编译期开箱 | 中,机制重 | 次选 |
| Paraglide(inlang) | 编译成类型安全函数 | 按需,可 tree-shake | 最强开箱 | 较新,生态小 | 前沿备选 |

**选 react-i18next 的理由**(针对本栈 React 19 + Vite 8 + TS + Tauri 桌面):
1. **Tauri 抹平唯一短板** —— 桌面应用代码打进二进制,非按访问下载,Lingui/Paraglide 的"小包"卖点在这里无意义;不值得为用不上的优点吃"宏 + 抽取 CLI"的复杂度。
2. **同构现有代码** —— `llm-error-messages.ts` 现在就是 `Record<string,string>`,与 react-i18next 的 JSON 词条结构完全同构,迁移成本最低(Lingui 要改写成组件内联宏 + 编译插件)。
3. **生态最大** —— React i18n 事实标准,文档/AI 覆盖最全;React 19 原生支持。
4. **唯一短板可补** —— 加 `react-i18next.d.ts` 把词条声明成类型,写错 key 当场 TS 报错。

## 3. 架构 — Strategy C(前端单权威)

**数据流**:后端产 `error_code` + `details`(结构化参数)→ 前端按 code 查词条 + 用 details 插值 → 渲染当前语言文案。

| 层 | i18n 职责 | 改动 |
|---|---|---|
| **前端**(React) | **唯一翻译权威**:react-i18next 翻所有 UI 文案 + 后端错误码 | 新建骨架 + 词条 |
| **后端**(studio backend) | 只产 `error_code` + `details`;`message` 降级为开发者 fallback | 契约收敛 + 清理 6 处中文 |
| **引擎 / 网关**(库) | 只产 `[F-v3-*]` 码,**语言无关** | **零改动** |

**为什么不选 Strategy B(后端各自 i18n)**:需两套 i18n 系统 + 两套词条同步、locale 透传到每个后端请求、`graph-agent`/`graph-agent-gateway` 这种可复用库被迫感知语言(污染 API)。Strategy C 单系统、单词条源、库零污染,且现有代码已 80% 这么建。代价:少数无码的动态/透传消息(见 §9)在 zh 下仍英文 —— 可接受(开发者诊断信息)。

## 4. 前端骨架(契约 & 关键设计)

- **初始化**:`src/i18n.ts`,在 app 入口前 init;`languagedetector` 探测 → 落到 `en`/`zh-CN`。
- **词条文件**:`src/locales/{en,zh-CN}.json`,**按功能 namespace 分文件**(`settings` / `canvas` / `copilot` / `errors` / …),避免单文件膨胀(契合 code-style 300 行/单一职责)。
- **错误码词条**:`errors` namespace 收编现有 `llm-error-messages.ts` 的 42 条(正是该文件注释写的"未来 i18n 包住这个 catalog")。
- **类型安全**:`src/@types/react-i18next.d.ts` 把 `en.json` 键声明成 `resources` 类型 → key 自动补全 + 错写报错。
- **插值/复数**:i18next 原生 `{{var}}` 插值;英文复数用内置规则;暂不引 ICU 插件(YAGNI,有复杂复数再加)。
- **切换**:`i18n.changeLanguage()` 运行时即时切换,**无需重启**。
- **错误码 → 文案的唯一出口**:`src/utils/errors.ts:errorMessage`。凡是把后端失败显示给用户的地方(toast、诊断抽屉、banner)都经过它:响应里有 `error_code` 且 `errors` namespace 有这个键 → 用词条 + `details` 插值;没有词条 → 落回后端 `message`(§5 定的开发者 fallback)。**不允许某个界面自己按 code 拼文案** —— 同一个码在两处读出两种话,就是"一个问题两个答案"。
- **"不自己拼文案"包括不自己读 `error.message`。** 一个调用点写 `error instanceof Error ? error.message : '…'` 时,它并没有在拼文案,它是**根本没让 `errorMessage` 看见这次失败**,于是后端那个码永远没机会被翻译。这不是假想:2026-08-21 真机点验发现 Save to Team 就是这么写的,后端已经按契约回了 `error_code=APP_SETTINGS_INCOMPLETE` + `details.field=gitea_host`,用户读到的却是 `Request failed with status code 400`。所以规则的可执行形式是:**捕获到的错误一律交给 `errorMessage(error, fallback)`**,`fallback` 只说"我当时在做什么"(如 `Sync failed`),仅当这次拒绝本身什么可读信息都没带时才登场,永远不覆盖错误自己带的话。
  - **这条由测试守住,不靠自觉**:`src/utils/one-error-exit.test.ts` 扫描 `src/` 全部非测试文件,出现 `instanceof Error ?` 即失败,唯一豁免是 `utils/errors.ts` 自己(它就是那个出口)。理由与「黑板的 `holds` 闸门」同一条:只写在文档里的纪律,在这件事上已经实证失效过一次。

## 5. 后端契约(改什么 / 不改什么)

后端 `ErrorResponse`(`app/models/errors.py:10`)已是 `{error_code, http_status, message, details, retry_strategy}` —— **schema 不改**。

| 项 | 现状 | i18n 后 |
|---|---|---|
| `error_code` | ✅ 机器码(`STANDARD_ERROR_MAP` `exceptions.py:30` + 引擎 `[F-v3-*]`) | 不变,作为前端词条 key |
| `details` | ✅ 部分带参(如 `{field:"user_id"}` `skills.py:179`) | **契约要求**:翻译所需参数必须进 details(供前端插值) |
| `message` | 自由英文文本 | **降级为开发者 fallback**(词条未覆盖该码时显示,方便贴 bug) |
| 残留中文 | ⚠️ **远超 6 处**:`copilot.py` 单文件 ~15 行中文 —— 整个 Copilot 系统提示(`BASE_SYSTEM_PROMPT_TEMPLATE`)+ ~8 条用户可见 `CopilotEventError`(L212/234/371/386/399/496/498/499);另 `skills.py:178/187/261/270/279`、`models/skills.py:ConfigMismatchWarning`。**`skills.py` 那批已清**(见 §9) | **全部改回英文 source**;用户可见错误走错误码,**系统提示走 §5.1 单独机制** |
| 成功/状态提示 | 如 `"Provider test queued."`(`llm.py:388`) | 非错误、无码 → **前端直接持词条**,后端可只发状态 |

### 5.1 Copilot 系统提示 / 模型可见 prompt 的 i18n(Strategy C 的显式 carve-out,PM 2026-06-05)

UI 文案 + 错误码走 §3 Strategy C(前端翻、backend 语言无关)。但 **Copilot 系统提示**(`copilot.py:BASE_SYSTEM_PROMPT_TEMPLATE` / `build_system_prompt`,backend 构造、**发给模型**、前端不渲染)走不通前端翻译 —— 前端根本看不到它。机制:

- **source = 英文**:现状 `BASE_SYSTEM_PROMPT_TEMPLATE` 是中文(= drift,实现时改回英文源)。
- **i18n 维护 EN + ZH 两版系统提示**:放 **backend locale 资源**(非前端 react-i18next 词条 —— 因前端不渲染系统提示)。
- **Copilot 后端按当前 locale 选模板**:`build_options` / `ClaudeSDKClient` 调用前,按前端随请求 / session 传入的 locale 取对应语言系统提示。**这是对"backend 语言无关"的显式 carve-out** —— UI + 错误码 backend 仍语言无关,唯 Copilot 系统提示 backend 需感知 locale。
- **SDK 语言环境随 locale 自动切换**:`claude_agent_sdk` 调用的语言环境跟随当前 locale,让模型用对应语言回应(zh-CN → 中文系统提示 + 中文回应;en → 英文)。
- **用户可见的 `CopilotEventError` 文案**仍走错误码 / 前端翻译(Strategy C);**只有模型可见的系统提示**走本机制。

## 6. 引擎 / 网关:零改动

`graph-agent`(引擎)`error_registry.py`(上百处 `[F-v3-*]` 结构化码)与 `graph-agent-gateway`(`exceptions.py`,3 条 `[F-v3-gateway-*]`)继续**只产码**。工作量在前端:**补齐"会在 UI 出现的那部分码"的中文词条**,纯日志码不翻。这正是 Strategy C 的好处 —— 库不被 locale 污染。

## 7. 语言切换 UX

- **首启**:Tauri 探测 OS locale → 命中 zh 用 `zh-CN`,否则 `en`。
- **手动**:Settings 放语言下拉,切换即时生效。
- **持久化**:选择存入 `app_settings`(后端 metadata store),跨会话/跨窗口记住。

    句子既然跟着语言变,搜索就必须跟着变,所以它改成接收**已渲染好的** headline
    (`headlineOf` 形参),纯投影本身仍然对语言无知。
  - **翻译器在这一批被收窄了类型**:这里近一半的键是**拼出来的**(`fact.${label}`、
    `decision.${decision}`、`settings.${verdict}`),而 i18next 的 `t` 类型只接受字面量键。
    与其为每个描述子写一遍 switch 把名字变回同一个字符串(等于把表写两遍),不如把翻译器
    在 `useTraceCopy` 这一处收窄成 `(key: string, options?) => string`。放弃的是 TS 的键名
    检查,补回来的是 `trace-copy.test.tsx`:它把每一种 headline、每一个路由决策、每一个设置
    裁定、每一个事实标签在**两种语言**下都渲染一遍,断言没有一个回显成自己的键 —— 这比
    编译期检查更接近读者真正会看到的东西。
- **仍未做**:§5.1 Copilot 系统提示 EN/ZH 双版 + locale 切换;`copilot.py` 那批
  `CopilotEventError` 中文;运行列表(Timeline)那一屏 —— 它整屏未翻(`Loading…`、`n/a`、
  各行标签),`utils/run-format.ts` 的 `formatRunTokens`(`"3,889 tokens"` 里的那个词)与
  `formatRunDuration` 属于它的词汇表,由它自己那一批一起收,不在 `trace` 这批里单拎一个词
  出来翻 —— 半翻一屏比整屏未翻更难读。

## 10. 已知缺口 / 风险

- **动态/透传消息**(git stderr、`str(exc)`)无码 → zh 模式仍英文。接受:开发者诊断信息。
- **引擎码海量,只翻 UI 可见子集** —— 需逐步识别哪些码真会到 UI(纯日志码不翻);P2 随接入识别。
- **词条与 UI 同步漂移** —— 加文案要同步加 key;P2 可选配 `i18next-parser` 在 CI 检测漏 key/死 key。
- **复数/语序**:中文无复数,英文有;当前用原生规则,若出现复杂复数/性数再上 ICU 插件。
