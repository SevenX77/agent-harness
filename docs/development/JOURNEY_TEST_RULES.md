# 旅程点验规则(测试阶段)

> 本文件是**旅程点验阶段**的规则源:一次点验要查哪几个维度、判据从哪来、什么算查过了、
> 结论往哪落。它不改变 [AGENTS.md](../../AGENTS.md) 的任何工程规则,只规定"在做点验这件事时"
> 额外生效的纪律。
>
> **适用范围**:对着真机逐项走用户旅程的验证活动。不适用于 worktree 阶段的本地门禁与单测
> (那一阶段的规则在 AGENTS.md「CI Gates」),也不适用于日常功能开发
> (那套在 `apps/studio/frontend/CLAUDE.md`)。
>
> **旅程的模块划分**照 `docs/studio/mvp1/01_workflows/INDEX.md` 的 7 个节点,外加两个横切模块
> (Copilot、失败退路);模块编号与 [DELIVERY_LEDGER.md](DELIVERY_LEDGER.md) 的旅程任务块一致。

## 1. 判据来源纪律

点验的每一条"预期"必须指得到一行权威文字。这一节规定怎么找那一行,以及找错了会发生什么。

### 1.1 先读文档自己声明的权威指针,再引它的正文

设计文档分两类角色,**同一个目录里两者并存**:

- **摘要**:workflow 节点文档(`docs/studio/mvp1/01_workflows/0N_*.md`)。它给旅程的全貌,
  正文里会**声明**细粒度权威在别处。
- **权威**:被摘要指向的那份细则(例如 `00_settings-ux-spec.md`)。它带**修订记录**,
  是决策实际落盘的地方。

`00_settings.md:29` 就明写着「细粒度 UX 规格…见 `00_settings-ux-spec.md`(PM 2026-06-02 口述,
**权威**)」。**引摘要之前必须先看这一行,顺着它读到权威那一份。**

**这条规则来自 2026-08-23 的一次真实误报。** 点验模块一时,报告称"设计说 official 只需
`get-models`、实现却要求真生成探测,两者冲突"。实际上权威那一份
(`00_settings-ux-spec.md:33`)在 **2026-07-01** 就记了修订:

> 原设计为"get-models 连通即 verified、不做逐模型 probe"。实证推翻:Anthropic 账户**欠费**时
> `GET /models` 照常 200,但**所有**生成调用被 `HTTP 400 "credit balance is too low"` 拒绝
> —— role 测试全红、API keys 页却全绿,两页真相矛盾。

冲突七周前就裁完了,滞后的只是摘要。**引了非权威的摘要就下"设计与实现冲突"的结论,
是把自己的检索不足报成了产品缺陷。**

### 1.2 判定"文档 vs 代码谁对"的三道检验,顺序固定

发现文档与代码不一致时,按顺序走完三道,不许跳:

1. **日期**。`git log -1 --format=%ad --date=short -- <文档>` 对
   `git log -1 --format=%ad --date=short -- <代码>`。文档明显更旧 → 大概率是文档滞后。
2. **原话**。找用户的原始裁决。三个地方:权威文档里的**修订记录**段;引入该实现的那个
   **提交信息**(`git log -S "<代码里的特征串>"` 定位);会话历史里的用户消息
   (只认 `type=user` 且 `role=user` 的条目,不认自己旧的摘要——摘要是自己写的,
   拿它当用户原话是循环论证)。
3. **第一性原理**。哪一侧的理由站得住。注意一种常见形状:文档里两半话,一半带理由、
   一半不带,而**不带理由的那半与代码冲突**——此时通常是那半举错了例子。

三道检验指向同一侧才动手。指向文档滞后 → **改文档**,并在改动里保留"原设计是什么、
被什么实证推翻"的修订记录,不许直接抹掉旧说法。

### 1.3 指不到判据时,标出来,不要编

- 判据存在但还没做 → `目标态`。实测确认"确实没做"就是结论,不算失败。
- 设计源里翻不到这一行 → `待定判据`。如实记录现状,再由用户裁它是缺陷还是缺设计。
  **不许自己编一个预期然后拿它判分。**
- 找不到就写"我在 X / Y / Z 都查过,没找到权威依据"。

## 2. 每个模块必查的九个维度

一个模块点验完的定义:下面九项**每项都有结论**(通过 / 不符 / 目标态 / 待定判据 / 无法观测,
并写明为什么)。只测功能通不通,不算点验完。

### D1 · 功能正确性
按模块的步骤表逐条走,每条给操作 / 预期(带判据坐标)/ 实测结果 / 截图。

### D2 · 数据结构与运行架构是否站得住
不止问"跑通了吗",还要问"这么设计合理吗、健壮吗"。每个模块给出:
- 这个模块的**真相源是谁**、有没有第二份并行真值
- 传输与落盘的**数据结构**(把类型定义原样贴出来)、字段是否让非法状态不可表示
- **幂等与冲突**:重复触发会怎样,有没有乐观并发标记,冲突时倒向哪一侧
- **失败行为**:重试几次、有没有上限与退避、失败对用户是否可见、失败的数据会不会丢

### D3 · 性能与响应性
记录该模块每个**阻塞操作**的真实耗时(冷启动、探测、编译、predict、run、发布)。
超过阈值的记为发现,即使功能正确。**理由**:一次点验若不记时间,就分不出"慢但能用"
和"坏了"——而用户体验上这两件事是同一件事。

### D4 · UI/UX 是否符合人的认知习惯
拿**成熟软件的既有做法**当参照,指名道姓(哪个软件、它怎么做、为什么那样做),
再说本仓哪里不合理。禁止"业界一般都这么做"式的无对象论证。
必查:控件说的话和它实际干的事是否一致;不可用的控件是否说明了为什么不可用
(灰按钮不给理由 = 缺陷);错误文案是否既说了出了什么事、也说了怎么办。

### D5 · 可访问性
- **状态不许只用颜色表达**。色相之外必须还有文字 / 图标 / 形状承载同一信息。
- 整条旅程能否**只用键盘**走完;焦点是否可见。
- 屏幕阅读器能拿到的信息是否完整(`aria-label` / `role` / 可及名)。

### D6 · 代码健康度(按模块,不按仓)
- **大文件**:列出该模块超过 800 行的源文件,说明它承担了几个职责。
- **高内聚低耦合**:模块对外的公开边界是什么;有没有伸手进别的单元的私有结构。
- **路径是否模块化**:该模块的代码、测试、翻译资源、文档是否聚在一处,能否整体迁走。
- **健壮性**:边界校验在不在入口;有没有 try/except 把坏状态吞进深处。
- **文档双向链接**:代码能指到它的设计源,设计源能指回代码坐标。

### D7 · i18n
点到哪个模块,就把该模块的 i18n 一起做掉。规则:
- **runtime 在 studio**(统一的加载 / 切换机制),**翻译内容与模块代码放在一起**,
  理由是模块迁移时一起带走。
- **领域专有名词不翻译**:模型 / 协议 / 厂商名、LLM / AI / agent / skill / phase / graph /
  node / endpoint / route / token / golden / trace / predict / compile / checkpoint / SDK /
  MCP,以及本仓专名(agent-harness、Skill Studio、graph-agent、ah)。不许翻译清单见
  i18n 术语表。
- 后端与 Rust 层**直接显示给用户**的文案同样在范围内。

### D8 · 数据破坏与恢复
把该模块的真相文件**弄坏**(删掉 / 截半 / 塞进非法字段),然后:
- 应用是**响亮地失败并指出准确的文件名**,还是静默回退到默认、或给一片空白?
- 有没有恢复路径,路径是否对用户可见?
**理由**:本仓的历史事故里,本地数据损坏的频次高于远端故障——凭据文件装不进新 schema 时
21 个 endpoint 整片消失,而 `healthz` 还是 200。

### D9 · 安全边界
- 密钥**不出现**在日志 / toast / DOM / URL 参数里(机械 grep,不靠肉眼)。
- 该模块的网络监听只绑本机;点验用的调试口在收尾时确认关闭。
- 用户可见的错误文案不回显凭据片段。

## 3. 环境纪律

### 3.1 只在真窗口测
CDP 驱动真 Tauri 窗口,配方见 `.claude/skills/studio-verify/SKILL.md`。浏览器直开 Vite 的
web 模式下 Tauri 原生桥是假的、Recent 在 Rust store 里打不开 skill,**它产出的结论不算数**
(2026-08-14 用户裁决)。web 模式唯一允许的用途是开发途中肉眼扫样式。

### 3.2 dev 构建之外还要验打包版
dev 构建和 NSIS 安装包的 sidecar 解析路径不同。**只在 dev 上验过的旅程,说明不了发布出去的
那个 app**。打包链在 `.github/workflows/package.yml`,按路径触发。

### 3.3 从零环境点验:不共用本机的真配置
带写操作的步骤(新增 provider、改角色映射、删条目)**不在用户真实的凭据库上做**——
这个界面的删除已经真删过一次数据。这类步骤一律在**一次性配置目录**里做:
`STUDIO_CONFIG_DIR` 指到临时目录,凭据从 `/d/coding/.env` 取。

一次性环境同时承担两件别处做不到的事:
- **从零复现整套配置**,验证一个新用户能不能走通;
- **人为制造每一种状态**。本机当前 0 条 failed route,所以 failed 态的原因呈现在真配置上
  物理不可观测;一次性环境里故意配一个坏 key 就有了。

### 3.4 不信被测系统的自我判定
Studio 自己的 Test 说失败时,**不当结论用**。去 provider 的官方 API 文档核对请求形状,
用独立方式(curl / 官方 SDK)自己打一次,比对两边结果。一致才认;不一致则缺陷可能在
Studio 的探测逻辑而不在 provider。

### 3.5 运行时资源先占黑板
点验前 `claim cdp-9222` 与 `main-app`(`scripts/wt-board.sh`,要 `WT_BOARD_AGENT` 身份),
验完 release。收尾必须验证调试口真关了:`curl 9222` 返回 `000`。
「我重启了」不等于「它关了」。

## 4. 报告与销账纪律

- **一条改动 / 一个步骤占一行**,不合并。五列:界面路径 · 操作 · 预期(带判据坐标)·
  实测结果(带截图文件名)· 状态。
- **没实测的行不许标通过。** 凡声称已验证,必须以当轮真机操作的结果为据。
- **无法观测要写明为什么**,并给出补测条件(通常是一次性环境里造出该状态)。
- 报告与截图**发布成 Artifact 页**给用户看,不发本地盘路径(用户常在远端)。
- 发现的问题记进 [PROBLEM_LEDGER.md](PROBLEM_LEDGER.md),编号 `J-<模块号>.<步骤号>`;
  任务进度记进 [DELIVERY_LEDGER.md](DELIVERY_LEDGER.md) 的旅程任务块,**完成一个勾一个**。
- **文档滞后与代码缺陷同等对待**:按仓规 MVP1 设计是真相源,读者会拿过期描述当真相,
  所以滞后的描述要修,修法见 §1.2。

## 5. 顺序纪律

模块 N 的出口物是模块 N+1 的输入,顺序不能打乱。一条 skill 贯穿全程:模块二新建的那个
skill 带到模块十的发布。每个模块另起夹具的话,测的就只剩单点功能,而旅程的价值恰恰在
"上一步的产物是不是下一步真能用"。
