## 一、已完成的工作(3 个 PR + 1 个决策)

> ⚠️ 这 3 个 PR 都在 `wc/round31-api-design` 这条 feature 分支上,**已写完、自审过,但还没合进 main**。

### PR-trace-bug — 引擎默认就记录运行轨迹

- **要做什么**:以前只有 app 端显式要求记录,引擎才记运行轨迹;直接命令行跑(不显式要求)就什么都不记,等于"黑跑"。
- **完成情况**:改成主线即使没人显式要求,也自动把轨迹写到运行目录下。
- **完成后效果**:不管用什么方式跑一个 skill,都有完整可回溯的运行轨迹,不再有"跑了但没记录"的黑洞。

### PR-A — 报错类型从 24 个砍到 5 个

- **要做什么**:引擎对外抛 24 种错误类型,太多,app 接不过来也记不住。
- **完成情况**:收敛成 5 个公开错误大类 + 一个统一的"错误信息包"(细节放在结构化字段里,而不是靠错误类型的数量来表达)。Studio 端和 Gateway 端同步切换适配。
- **完成后效果**:app 只需认 5 个错误大类 + 读信息包里的字段,接入大幅简化。

### PR-B — 运行目录参数规整

- **要做什么**:以前运行目录是可选参数,还另有一个单独的"轨迹目录"参数,职责混乱、产物落点不可预测。
- **完成情况**:把运行根目录改成必传,引擎一律只往 `runs/<本次运行id>/` 子目录写,删掉多余的轨迹目录参数。
- **完成后效果**:每次运行的产物落点统一、可预测,app 端明确知道去哪里找。

### 本 session 额外完成 —— LLM 平台分支评估 + 方向决策(非代码)

- 评估了另一台机器做的「LLM 平台分支」(V2)能否合 main。三方审计(工程实测/架构/PM 替身)收敛结论:**设计扎实、你的黄金原则过关,但它从没跑过 CI 且实测会红,而且跟本机 round-31 在同一块撞车**。
- **你拍的决策**:采纳 V2 作基线;PR-C(把 LLM 配置搬 Gateway)撤掉(V2 用更成熟的模型做掉了同一块);后续基于 V2 重新设计。
- 顺手清理:删掉死的 PR-C 半成品文件 + 14 条已合并到 main 的废弃本地分支。
