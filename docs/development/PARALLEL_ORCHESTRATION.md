# 并发推进 SOP(协调方直驱多 agent 并行交付)

> **本文是什么**:一个交互式会话同时驱动多个实施 agent、并行推进一批工单时的规则源。
> 它规定七件事:席位怎么编、权威正文谁来写、工单什么时候放行、怎么隔离、任务书写什么、
> PR 怎么审怎么合、状态落在哪。
>
> **本文只写编排层增量。** 每张工单自己落地时,走的仍然是
> [AGENTS.md](../../AGENTS.md) 既有的 worktree→PR→CI 管线与门禁清单;那些规则本文
> **只引用、不复制**(依据「文档事实唯一所有权」:同一条规则只允许一个权威定义,
> 复制出来的第二份一定会与本体漂移,而读者无法判断哪一份是现行的)。
> **维护本文时逐句自查**:这一句是本文新立的编排层规则,还是别处已有的工程规则?
> 已有的只许写成指针(「见 AGENTS.md 某节」),不许在这里重新下达一遍。
>
> **适用范围**:由一个协调方会话派发、多个实施 agent 并行执行的程序性交付
> (例:2026-08/09 的 gskill 重整)。单人单任务的日常开发不适用本文,直接走
> AGENTS.md 与 `apps/studio/frontend/CLAUDE.md`。
>
> **多 agent 编排的另一条路线**是 ah 编队(`.ah/README.md`):由 ah 拉起 master
> 与 workers 的常驻编制。本文描述的是协调方直接用会话内后台 agent 派单的轻量形态。
> 两者不互斥,按任务规模选一种,不要在同一个程序里混用两套派单口径。

## 〇、术语(本文的固定指代)

本文正文中,下列名词一律取此处的定义,不另用简称或代词。

| 名词 | 指什么 |
|---|---|
| **程序** | 一次由同一批目标绑在一起的多工单交付活动(例:gskill 重整)。一个程序有自己的决议文档和台账行。 |
| **工单** | 派给单个实施 agent 的一件工作:能独立开出一个 PR,有明确的文件领地和验收判据。 |
| **协调方** | 发起并维护这个程序的那一个交互式会话。它派单、裁定、合并,并落盘 §1.2 授权的那三类直写内容。 |
| **实施席** | 承接一张工单、从写失败测试到开出 PR 全程负责的后台 agent。 |
| **执笔席** | 新建的、未继承协调方会话历史的 agent,按自包含 brief 撰写权威正文(职责见 §1.2)。 |
| **交叉审席** | 对 PR 差异做对抗式审查、给出 approve/rework 与分级发现的外部审查者(当前实例:codex)。 |
| **放行门** | 一张工单的最后一个前置依赖被解除的那个时刻。门一开,这张工单就具备派单条件。 |
| **领地** | 任务书授权某张工单改动的文件集合。领地之外的文件,该工单一律不碰。 |
| **权威正文** | 项目规则、规范、设计、决议这四类文档的正文,以及对它们的实质性修改(定义与边界见 §1.2)。 |

## 一、席位编制与执笔分工

### 1.1 席位表

资源方案的批准记录在
[gskill 重整决议](../design/gskill-restructure-decision-2026-08-31.md) §10「资源与实施方案」
(用户 2026-08-31 逐项批准);本节是它在编排层的操作口径。

| 席位 | 型号 / 推理档位 | 只做什么 | 绝不做什么 |
|---|---|---|---|
| 协调方(主会话) | Fable 5,xhigh | 推导与裁决、拆工单 DAG、写任务书与 brief、核验产出、裁定审查发现、合并、§1.2 列举的三类直写内容的落盘 | 写产线代码;撰写权威正文;与在跑工单碰同一文件 |
| 实施席(后台 agent) | Opus 5,xhigh | 一张工单从失败测试到 PR 的全程;返修回原席继续 | 越出任务书领地;自行合并;代替协调方裁原则问题 |
| 执笔席(后台 agent) | Opus 5,xhigh,干净上下文 | 按自包含 brief 撰写权威正文 | 继承协调方的会话历史;自审自己的产出 |
| 交叉审席 | codex GPT-5.6-sol,xhigh | 对 PR 差异做对抗式审查,给 approve/rework 与分级发现 | 终裁——它的发现须经协调方逐条裁定真伪(见第五节第 5 条) |

交叉审席走 OpenAI 额度,与实施席、执笔席所用的 Claude 额度池零竞争;把对抗审放在
它身上不会挤占实施与推导的额度(依据同上,决议 §10.1 末段)。

交叉审席的调用配方(命令行,只读全盘):

```bash
codex exec --skip-git-repo-check -c model="gpt-5.6-sol" \
  -c model_reasoning_effort="xhigh" \
  -c 'sandbox_permissions=["disk-full-read-access"]' \
  --output-last-message <裁决输出文件> - < <提示词文件>
```

### 1.2 权威正文由干净上下文的执笔席撰写

**什么算权威正文**:项目规则(`AGENTS.md`、各级 `CLAUDE.md`)、规范文档、设计文档、
决议文档的正文,以及对这四类文档的实质性修改(改变规则内容、结构、判据或措辞含义的
修改)。

**正向规则——权威正文一律由执笔席写。** 协调方准备一份**自包含 brief**,交给一个新建的、
未继承本会话历史的 agent 执笔。brief 必须写全七项:目标、范围、术语、已核验的事实与
证据坐标、输出路径、边界(明令不许改什么)、验收判据。执笔席只读 brief 与 brief 指到的
仓内文件,不需要也不应当读会话历史。

**协调方在这件事上做且只做三件事**:

1. 准备 brief;
2. **机械核验**执笔结果里的事实——引用的路径是否存在、行号是否对得上、引文与原话是否
   逐字一致、需求是否逐条覆盖;
3. 把核验发现写成**逐条修订清单**交回执笔席,由执笔席自己改。

**协调方可以直接落盘的,只有下面这三类,穷举,没有第四类。** 每一类都写死了输入是
什么、输出长什么样,**并且各带一组前置条件**(逐类写在表下面);套不进这三类、或者
套得进但前置条件不满足的,一律走执笔席。

| # | 直写类别 | 输入 | 输出 |
|---|---|---|---|
| 1 | 交付台账行的状态标记 | 这一行跟踪的**每一个** PR,各取两个**查得到的当前量**:①`state`,取值 `OPEN` / `MERGED` / `CLOSED`,用 `env -u GITHUB_TOKEN gh pr view <N> --json state` 查;②**最近一次交叉审裁决**,取值 `尚未审` / `approve` / `rework`,按 §五 第 3 条的记录位读——`gh pr view <N> --comments` 里首行匹配 `交叉审 r` 前缀的评论中时间最晚的那一条,一条都没有就是 `尚未审`。②是**可复位量**:新裁决覆盖旧裁决,rework 之后再来 approve 就读回 `approve`;「曾经发出过 rework」是只增不减的历史事实,**不能**拿它当输入 | 按交付台账「状态词汇」几行给出的**优先级全序**取排最前的那一个标记,括号里按闭式列全这一行跟踪的 PR 号(升序、`+` 连接、无空格)。落到三个标记上的规则:`state` 是 `OPEN` 且裁决是 `rework` → `🔁 返修中(…)`;`state` 是 `OPEN` 且裁决是 `尚未审` 或 `approve` → `🚧 进行中(…)`;跟踪的 PR 全部 `MERGED` → `✅ 已合并(…)` |
| 2 | 用户原话的**整条**逐字引文 | **一条完整的**用户消息的原文,加这条消息在会话中的日期 | `> 「原文」(用户,YYYY-MM-DD)`。整条照搬,零改写、零概括、零补充、零省略;日期格式一律 `YYYY-MM-DD` |
| 3 | 指针行 | 一个已经存在的文件路径或小节标题,**外加落点处已有的指针写法** | 照落点已有的写法把该坐标写出来,不附转述、不附评述 |

**判据一句话:前置条件满足时,输出由输入唯一决定,不存在第二种合法写法。**
达到这一条才算直写。
达不到的一律走执笔席,包括:要在几种都说得通的说法里挑一种的、要概括的、要取舍的、
要斟酌措辞的。

**这条判据是有前提的,每一类的前提写在下面三段里。** 前提不满足时,输出就不再由输入
唯一决定——那不是「直写做得马虎一点」,而是根本不属于直写,整格交执笔席。三类的前提
之所以要逐条写出来,是因为前三版都栽在同一个地方:把一个**看起来**机械的动作当成了
机械的,而没去数它在真实数据上会不会分叉。

**第一类的三个前置条件,缺一条就整格交执笔席。**

1. **这一行跟踪的 PR 全都处在 `OPEN` 或 `MERGED`。** 只要有一个是 `CLOSED`(关掉而
   没有合并),那一格要交代的是「为什么关」,那是写出来的字,不是标记。
2. **这一行既没有被外部条件挡住,也没有被主动搁置。** `阻塞(原因)` 与
   `已搁置(重启条件)` 在台账的优先级全序里排在三个标记之前,而它们括号里必须写出
   原因或重启条件——同样是写出来的字。何况「有没有被挡住」本身要判断,不是观察得到的。
3. **括号里能按闭式写完。** 闭式是:PR 号按升序排、用 `+` 连接、`+` 两侧不留空格
   (`#600+#601`)。需要写「哪个 PR 干了什么」「随哪件事一起」「日期」「区间共几条」
   的,都是散文,写不进闭式。

三条都满足时,协调方对这一格只有一个动作:**把标记从全序里的一个值翻到另一个值**。
那一行里除这个标记以外的每一个字,仍然由执笔席写。

**与第一类同族的还有一个动作:把交叉审裁决贴成 PR 评论**(做法见 §五 第 3 条)。它没有
单列成第四类,因为它落的不是仓内文件;但它的形状与第一类一样——输入是裁决原文加轮次
与结论,输出是首行固定、其余原文照贴的那条评论,不概括、不改写。它之所以是必做步骤:
第一类的输入②就从那里读,不贴就没有来源。

**第二类只认整条引用,摘引不算。** 从一条长消息里挑出一句,或者用省略号把两段接起来,
「挑哪一句」「省略哪一段」都是取舍,换个人会挑出别的句子,输出就不由输入唯一决定了。
所以直写只覆盖**整条消息逐字照搬**;要摘引的,连同摘引这个取舍一起交执笔席。交付台账
里已有的引用**多数是摘引**(带 `……` 的那些),它们本来就在执笔席那一侧——这不是例外,
正是这条前提在真实数据上的样子。

**第三类的输出形态由落点决定。** 同一个坐标至少有两种都说得通的写法:裸的仓根相对
路径(`docs/development/PROBLEM_LEDGER.md`),和 markdown 链接
(`[DELIVERY_LEDGER.md](DELIVERY_LEDGER.md)`)——本文两种都在用。所以第三类的输入里
必须带上**落点已有的写法**:同一张表、同一节里既有的指针长什么样,新写的就长什么样。
落点没有既有写法可照(第一次在这里放指针),形态就是一次取舍,归执笔席。

**标记词表、优先级全序、多 PR 的括号写法,owner 都是交付台账,不是本文。** 三者写在
[DELIVERY_LEDGER.md](DELIVERY_LEDGER.md) 开头的「状态词汇」几行。台账那几行改了,
上表跟着改,不在本文另立一套——两处写同一件事,只有一处能是权威(依据「文档事实
唯一所有权」)。

**第 3 条前置条件挡下多少既有行,是数出来的,不是估的。** 2026-09-02 机械扫描交付台账
正文全部 134 处 `✅ 已合并(…)` 实例:122 处括号里是单个 `#数字`,12 处不是。这 12 处按
上面的规则**各有确定去处,一半一半**:

- **6 处进得了闭式**——2 处本来就是闭式(`#600+#601`、`#616+#617+#618`);4 处是纯 PR
  号、只是连接符或空格不同,改写成闭式不丢信息(`#872 + #873`、`#721 + #722 + #723`、
  `#788 + #790` 带空格,`#726/#727/#729/#734/#739` 用斜杠)。这 6 处的号本来就是升序。
- **6 处括号里带着写出来的字,按第 3 条归执笔席**——`#613 状态面板 + #614 安装/配置`、
  `#747 主体 + #754 登录按钮拆链补缺`、`#765 主体 + #769 补缺`、`#698,随 P3 一起`、
  `#928,2026-08-21`,以及 `#653-#667,15 个 PR`(它既用区间又带条数,两样都写不进闭式)。

**所以本文不说「闭式覆盖了全部聚合行」,只说「每一行都有确定的去处」**:6 处进得了闭式,
6 处明确出直写集。历史行一行不改——台账的维护规则是只增写不删史。复核用的扫描:

```bash
# 只数正文行:开头那几行 `>` 引用块是词表定义,里面的写法是例子不是记录
uv run python -c "import re,pathlib;L=pathlib.Path('docs/development/DELIVERY_LEDGER.md').read_text(encoding='utf-8').split(chr(10));b=chr(10).join(l for l in L if not l.startswith('>'));v=re.findall(r'已合并[（(]([^）)]*)[）)]',b);S=re.compile(r'^#[0-9]+$');C=re.compile(r'^#[0-9]+([+]#[0-9]+)*$');W=re.compile(r'^#[0-9]+([ ]*[+/][ ]*#[0-9]+)*$');o=[x for x in v if not S.match(x)];print('total',len(v),'single',len(v)-len(o),'closed-form-able',sum(1 for x in o if W.match(x)),'prose',sum(1 for x in o if not W.match(x)))"
# 2026-09-02 实测输出:total 134 single 122 closed-form-able 6 prose 6
```

**修订记录行不在直写集里。** 它看着像照抄,其实不是:同一份 diff 可以写出好几份都
说得通的修订记录——写哪几条、按什么顺序排、每条追溯到哪个原因,都是取舍,而取舍
没有唯一解。修订记录同时是权威正文的组成部分,它是后来人判断这份文档为什么变成
现在这样的唯一依据。因此修订记录由执笔席随正文一并撰写。

**负向规则**:

- **协调方不充当执笔席。** 一个满载会话历史的会话去写正文,会把只有当事人才懂的代号、
  没有落盘的隐含前提、以及尚未成立的判断一起写进正文,而读者从正文里看不出哪一句缺
  依据。本文初版就是这样产生的:它由协调方自己撰写,交叉审随后查出三类缺陷——免审
  边界不可机械判定、两处依据是查无出处的代号、多处把 AGENTS.md 已有的规则重新下达
  了一遍(具体是哪几处,以文末修订记录逐版列出的为准)。
- **不把多个 agent 的片段拼成正文。** 拼接出来的正文没有任何一方对全篇一致性负责,
  概念漂移和重复定义会从接缝处进来。
- **执笔席不自审。** 它的产出由协调方机械核验;正文若随 PR 落地,再由交叉审席按第五节
  的管线对抗审。

**这条纪律不是本文新立的**,它来自跨项目通用文档写作规范中「权威正文由干净上下文独立
执笔」一条。该规范在本仓之外维护,本文因此把规则本身完整写出,而不给一个仓内坐标——
读者不需要找到那份规范也能照着执行。

## 二、调度:工单 DAG 与放行铁律

1. **先摆 DAG 再开工。** 把全部工作摆成一张带依赖的工单图。依赖只认两种:
   **裁决依赖**(等用户裁决,或等方案批准)与**文件依赖**(与在跑工单碰同一片文件)。
   「概念上有先后」不构成依赖,不得据以排队。

2. **放行铁律:任何放行门一开,立即按下面这个程序扫全 DAG 放行。** 不排队、不等上一批
   收尾。程序是确定的——同一份 DAG、同一批在跑工单、同一个并发上限,谁来跑都得到同一个
   启动集:

   1. **排序。** 取所有「依赖已解除、尚未开工」的工单,按 **(DAG 拓扑深度, 台账行序)**
      升序排成一个序列。拓扑深度相同就比台账行序;两者都相同不可能——台账行序在一份
      台账里互不相同。
   2. **逐张扫描。** 从序列头开始,对每一张工单判断:它的文件领地与
      **「在跑工单 ∪ 本轮已放行工单」** 的领地是否零重叠。零重叠就放行,并**立刻把它
      计入「本轮已放行」**;有重叠就跳过这一张,继续看下一张。
   3. **停止。** 「在跑 + 本轮已放行」的数量达到第 3 条的并发上限时停止扫描。

   **第 2 步里「∪ 本轮已放行」这一项是关键**:少了它,两张互相重叠、但都不与任何在跑
   工单重叠的工单会在同一轮里被同时拉起,当场撞进 rebase 混战。加上它,重叠的两张里
   序在后的那张自然落到下一轮——**「谁等」由排序定死,不靠临场判断**。

   两条依据:

   - **原理**:等待的唯一正当理由是真依赖。两张工单既不碰同一片文件、也不互为裁决
     前提时,让后一张等前一张收尾并不降低任何风险,只是把批次排得整齐,代价是整段
     并行时间。同一判断在程序的决议里已经写成实施策略:
     [gskill 重整决议](../design/gskill-restructure-decision-2026-08-31.md) §10.2
     要求「模块 N 在审核/CI/点验时,模块 N+1 开始盘点」——重叠推进,不按批次对齐。
   - **实证**(2026-09-01):批 B 的放行门在 00:24 打开,协调方却等手头的修缺陷批
     收尾,到约 07:50 才派单,损失约 7 小时并行进度;而那一波工单与在修的缺陷**零
     文件重叠**,本可即刻并行。

3. **并行上限有两层,取更严的那层。**

   - **程序自己的上限优先。** 程序的决议文档若为它的工单定了并发上限,该上限在这个
     程序内高于第 2 条的放行程序所能放行的数量——决议文档是这个程序的授权来源,
     一般调度规则不越过它。现例:
     [gskill 重整决议](../design/gskill-restructure-decision-2026-08-31.md) §10.2
     为 gskill 重整的模块重构单定了「互不相交的模块至多两个 worktree 并行」。
   - **没有程序级上限时,以本机资源实测为准。** 2026-09-01 在本机实测:8 个实施
     agent 并行可行。上限是第 2 条第 3 步的停止条件,两条取更严的那个。瓶颈是 CPU 与磁盘,不是模型额度——多套测试套件同时跑会把毫秒级
     时序测试挤成假红,处理办法见第五节第 6 条。

## 三、隔离:文件领地与运行时资源

1. **worktree 规则本文不下达。** 本仓的 worktree 规则见 AGENTS.md
   「Baseline & Working Environment」(worktrees 一条)与「Workflow Pipeline」
   第 1 步(`scripts/wt-new.sh`)。**编排层增量只有一条**:一个程序常常跨到本仓
   之外的仓(例如 gskill 重整要在新仓上落地),而那些仓没有 `scripts/wt-new.sh`。
   对这类仓,任务书必须写出等价命令
   `git worktree add <独立目录> -b <分支> origin/main`,并**由任务书指名 worktree
   目录**——目录由任务书指名,两张工单才在物理上不可能落进同一棵树;留给实施席
   自己挑,两张工单挑中同一个目录名的概率不为零。

2. **任务书里明令不碰**:别人的 worktree、封存分支、以及与在跑工单重叠的文件区域。
   写成禁令清单,不写成「注意避让」——避让不可核验,禁令清单可以逐条对照 diff。

3. **两张工单必须碰同一文件时,任务书写死两件事**:合并顺序,以及 rebase 责任方
   (谁后合谁负责 rebase)。同时要求双方在报告里各自陈述冲突面属于哪一种——**文本
   邻接**(改动挨着,语义无关)还是**语义重叠**(两边改的是同一条规则或同一个行为)。
   两者的处置不同:文本邻接由责任方 rebase 即可;语义重叠必须回到协调方重新裁定,
   因为它意味着同一件事被两张工单各自决定了一次。

4. **运行时资源**(端口、CDP 调试口、正在跑的主 app)走黑板 `scripts/wt-board.sh`
   占用。规则完整写在 AGENTS.md「并行任务的运行时资源黑板(`scripts/wt-board.sh`)」,
   本文不复述,也不在这里另立口径。

## 四、任务书(brief)标准

**每张任务书必须自包含**——实施席不读会话历史也能干完这张工单。这与第一节第 2 条对
执笔席 brief 的要求是同一条纪律的两个应用面。任务书写全六项:

1. **背景与目标**:这张工单要达到什么,做到什么样算达到;
2. **裁决依据的原文坐标**:文件路径加行号,直接引原文,**不转述**——转述会把裁决的
   边界磨掉,而实施席无从发现自己拿到的是二手版本;
3. **已知连带**:这次改动会触发哪些硬钉断言、登记机关、计数锁;
4. **并行纪律**:worktree 指令、领地边界、以及邻居工单此刻在改什么;
5. **门禁清单**:指向该仓 AGENTS.md 的门禁节(本仓是「CI Gates — run locally
   BEFORE pushing」),**不在任务书里另抄一份**——抄一份就会与门禁本体漂移,而实施席
   会照着过期的那份跑;
6. **报告格式**:要求带第一手证据——先红后绿的两段测试输出、门禁实测输出、PR 号。

**已裁事项直接写进任务书,实施席无权再上升。** 允许实施席上升的只有两类:真正的原则
冲突(两条规则指向相反的做法),以及任务书未覆盖的目标级取舍(做到什么程度算达到)。
其余一律自行推导、自行决定,并在报告里写明按哪条依据得出哪个决定。

**先写失败测试、再写产线代码**这条纪律本身是 AGENTS.md「Developer Workflow Rules」
既有的规则(遵循 `superpowers:test-driven-development`),本文不重新下达。**编排层
增量是证据落在哪**:任务书必须要求报告里贴出先红、后绿的两段测试输出,协调方据此判断
这张工单是否真的走了这条纪律。派单形态下,协调方看不见实施席的过程,不留这两段输出,
纪律就没有可核验的痕迹。

## 五、PR 审合管线

1. **PR 开出即押住。** `env -u GITHUB_TOKEN gh pr merge <N> --disable-auto`,实施席
   不许自合。AGENTS.md「Workflow Pipeline」第 3 步默认武装 auto-merge,第 4 步把
   `--disable-auto` 列为「想先审再合」时的**可选**做法;**编排层增量是把这个可选做法
   变成强制**——并行期同时有多个 PR 在飞,任何一个自行合并都会让「按依赖顺序合并」
   (本节第 7 条)失效,而失效的代价由后合的那张工单以 rebase 混战的形式承担。

2. **攒批送审。** 攒 2–4 个 PR 打包成一次交叉审席调用,降低调用开销与弹窗干扰。
   提示词逐 PR 定制审点,并**显式标注跨 PR 交互面**:两张工单动了同一文件时,一方
   引入的对象会不会让另一方删掉的防线失守。单个 PR 独审看不见这一类缺陷,因为它只
   存在于两份 diff 的交集里。

3. **每一轮交叉审裁决,回来就贴到 PR 评论上——这是「最近一次裁决」的唯一记录位。**
   协调方收到裁决后立即执行:

   ```bash
   env -u GITHUB_TOKEN gh pr comment <N> --body-file <裁决文件>
   ```

   评论正文**首行固定**为 `交叉审 r<轮次>:approve` 或 `交叉审 r<轮次>:rework`,其余是
   裁决原文照贴。**读取方法同样固定**:`env -u GITHUB_TOKEN gh pr view <N> --comments`
   里,首行匹配 `交叉审 r` 前缀的评论中**时间最晚的那一条**就是「最近一次裁决」;一条
   匹配的都没有,就是 `尚未审`。

   **为什么必须有这个记录位**:台账状态标记的输入之一是「最近一次交叉审裁决」
   (§1.2 第一类),而本程序的交叉审走命令行,不落 GitHub review——
   `gh pr view --json reviews` 对一个审过三轮的 PR 照样返回空数组。裁决要是只留在
   协调方的会话里,这个输入就没有任何人能复查的来源,状态标记也就不再是查得到的
   事实,而是协调方的记忆。**贴评论这个动作本身与 §1.2 第一类同族**:输入是裁决原文
   加轮次与结论,输出是那条评论,原文照贴、不概括、不改写,输出由输入定死。

4. **有一类 PR 免送交叉审席,判定按文件路径。** 免审是一道门,门的判据必须机械可判,
   所以判定程序、闭集定义和判定示例独立写在本节末尾的「免审闭集」小节里。

5. **交叉审席的裁决不是终裁。** rework 的每一条发现,由协调方裁定真伪与处方:交叉审席
   也会错,也会开出与仓内设计真相冲突的药方。先例(2026-09-01,gskill 重整审查轮):
   它开出「把 `run_dir` 加进概念词表白名单」的处方(概念词表见
   [gskill 重整决议](../design/gskill-restructure-decision-2026-08-31.md) §8 验收清单
   第 ① 条「概念唯一 owner」),经协调方裁定与仓内设计真相冲突,驳回。
   裁定成立的真缺陷,**打回原实施席返修,不换人**——换人等于让新人从零重建这张工单的
   上下文,而原席已经有了。处方给第一性修法,不许逐条打补丁。

6. **本地测试变红时,先对照 pristine `origin/main` 复跑。** 并行期本地测试失败,先在
   干净的 `origin/main` 检出、同一环境下复跑同一个测试:两边都红 = 环境问题或既有问题
   (记录下来,继续推进本工单);只有本 PR 这边红,才算本 PR 的问题。不做这一步,多套
   测试套件同跑挤出来的假红会被当成本 PR 的缺陷,把工单卡在不存在的问题上。

7. **合并按依赖顺序执行。** 合并后按 AGENTS.md「Workflow Pipeline」第 6 步(根目录
   依赖刷新)与第 7 步(engine/gateway 源码改动后的 vendor 重建)跟进。

### 免审闭集:按文件路径判定,不按内容性质判定

**正向规则。** 一个 PR **免送交叉审席,当且仅当**它的
`git diff --name-only --no-renames origin/main...HEAD` 输出的**每一条**路径都落在
下面这个闭集里。`--no-renames` 不是可省的修饰,理由见本小节的「为什么判定命令必须
带 `--no-renames`」。

**闭集分两层:类判据决定谁够格进,枚举决定判定时认哪几条。**

**① 类判据:归档类记录(将来要扩张,先拿这条量)。** 一份文件够格进这个集合,当且仅当
它同时满足下面三条:

- **它记的是已经发生的事实**——状态、发现、已执行的审查提示与裁决、盘点结果;
- **它不定义任何将来要遵守的规则或契约**,也不被任何程序读取为输入;
- **写错了只需再写一条记录订正**,不会让别处的代码或别人的工单跟着错。

三条缺一条就不进。判据的分界线不是「看起来像不像记录」,而是**这份文件的内容有没有被
将来依赖**:被依赖的,错一句就传导下去,必须过对抗审;只被回看的,错一句下一条记录就
能纠。

**② 显式枚举(判定时只认这一层,四条,逐条列全)。**

1. 路径**恰好等于** `docs/development/DELIVERY_LEDGER.md`(交付台账:在做什么、
   到哪一步);
2. 路径**恰好等于** `docs/development/PROBLEM_LEDGER.md`(问题台账:用户点名问题
   与旅程点验发现的销账落点);
3. 路径匹配 `docs/design/*-inventory-*/domain-reports/**`(域级盘点报告);
4. 路径匹配 `docs/design/*-inventory-*/codex-review/**`(交叉审的提示词与裁决原文)。

**第 3、4 条只收证据包目录里的这两个子目录,不是整个目录。** 证据包**顶层**的文件
——`adjudication-record.md`(裁决)、`inventory-synthesis.md`(设计综合)、`README.md`、
`name-clearance-*.md`、`verification-*.md`——**一律出集送审**:裁决与设计综合定义的是
后续工单要遵守的东西,被将来依赖,过不了类判据第二条。上一版用 `*-inventory-*/**` 一个
通配把整个目录收进来,等于把裁决与综合稿一起免审了,这是本版收窄的原因。

**两层缺一不可。** 只有枚举,每次扩张都成了没有标准的个案裁量;只有类判据,判定又
退回「这个文件算不算记录类」的性质之争,而那正是初版被推翻的原因(见下面「为什么用
路径而不用内容性质」)。所以分工是:**扩张时用类判据论证,判定时只查枚举。**

**问题台账凭什么入集(第 2 条的依据)。** 它的行记的是**别处已经做完的事**:用户在聊天
里点了什么问题、真机点验看见了什么现象、修没修好。这些是已发生事实的记录,不定义任何
将来要遵守的规则,也没有程序去读它。`AGENTS.md`「旅程点验规则」一条把两本台账并列并
指定它是旅程点验发现的落点(「进度在 `DELIVERY_LEDGER.md` 的旅程任务块,发现记进
`PROBLEM_LEDGER.md` 的「旅程点验发现」一节」);它自己开篇也写明与交付台账的分工。

交叉审席提过一个反对:问题台账里有「归属翻译」(把用户的话翻成哪个模块的问题)和
「修复顺序」,这两样带判断。**这个反对不成立,理由在类判据的第三条**:归属翻译与修复
顺序都是**记录内容**,不是别处要遵守的契约——没有任何工单或程序把台账里的归属当输入,
翻错了下一条记录订正即可,不会传导。要是哪天某条归属被用作派单依据,那它就不再只是
记录,该条也就该出集——判据本身已经把这个边界画好了。

**这次扩张与收窄的实测依据。** 口径先说清楚:**完整滚动 30 天窗口**里 `origin/main` 上的
全部 squash 提交,不是 `gh pr list --limit N` 那种会被截断的样本——上一版就是拿 60 条的
截断样本当「近 30 天」,数出来的比例是错的。2026-09-02 实测,窗口内共 **532** 个提交:

| 闭集版本 | 命中提交数 |
|---|---|
| 只收交付台账 + 证据包整目录(第六版) | 41 |
| 加进问题台账(第七版) | 83 |
| 本版:两本台账 + `domain-reports/**` + `codex-review/**` | 82 |

分项:只改交付台账 **40** 个,只改问题台账 **21** 个,两本台账同改 **21** 个。

两个结论,都只说数据支持得住的:

- **纳入问题台账是对的**:命中数从 41 涨到 83,翻了一倍——原来有一半够格免审的记录型
  提交被挡在门外。
- **上一版写的「两台账同改是纯记录型 PR 的主导形状」不成立,已删除。** 实测只改交付
  台账的有 40 个,两本台账同改的 21 个,前者更多。当时得出「主导」是因为样本被
  `--limit 60` 截断,而截断段恰好落在一批两台账同改的提交上。
- 本版收窄证据包目录只让命中数从 83 掉到 82(窗口内只有 1 个提交碰了证据包顶层文件),
  **代价很小,换来的是裁决与设计综合不再被免审**。

复核用的扫描:

```bash
uv run python -c "
import subprocess,re
out=subprocess.run(['git','log','--since=30.days','--no-renames','--name-only','--format=%x00%H','origin/main'],capture_output=True,text=True,encoding='utf-8').stdout
C=[[l for l in c.split(chr(10)) if l.strip()] for c in out.split(chr(0)) if c.strip()]
C=[(x[0],x[1:]) for x in C]
DL='docs/development/DELIVERY_LEDGER.md'; PL='docs/development/PROBLEM_LEDGER.md'
broad=re.compile(r'^docs/design/[^/]*-inventory-[^/]*/.+')
narrow=re.compile(r'^docs/design/[^/]*-inventory-[^/]*/(domain-reports|codex-review)/.+')
hit=lambda fs,S,rx: bool(fs) and all(f in S or rx.match(f) for f in fs)
print('commits',len(C))
print('v6',sum(1 for _,fs in C if hit(fs,{DL},broad)))
print('v7',sum(1 for _,fs in C if hit(fs,{DL,PL},broad)))
print('now',sum(1 for _,fs in C if hit(fs,{DL,PL},narrow)))
print('DL-only',sum(1 for _,fs in C if set(fs)=={DL}),'PL-only',sum(1 for _,fs in C if set(fs)=={PL}),'both',sum(1 for _,fs in C if sorted(set(fs))==sorted([DL,PL])))"
# 2026-09-02 实测:commits 532 / v6 41 / v7 83 / now 82 / DL-only 40 PL-only 21 both 21
```

**判定程序(三步,机械可执行)**:

1. 跑 `git diff --name-only --no-renames origin/main...HEAD`,取它输出的完整路径清单;
2. 逐条对照上面枚举里的四条;
3. **只要有一条路径落在枚举之外,整个 PR 送审**;全部落在枚举之内,才免审。

**为什么判定命令必须带 `--no-renames`。** Git 默认开启重命名检测,而**检测一旦命中,
`--name-only` 就只打印新路径,旧路径根本不出现在输出里**。免审判定读的就是这份路径
清单,旧路径从清单里消失,判定便对重命名失明。失败场景是具体的:把一份闭集外的决议
文档移进证据包目录,清单里只剩下落在闭集内的那条新路径,于是这个本该送审的 PR 被判
成免审——而这次改动恰恰动了决议文档的所在位置,是最需要第二双眼睛的那一类。
`--no-renames` 关掉检测,同一次改动被还原成「删旧路径」加「增新路径」两条独立路径,
旧新两侧天然都在清单里,判定程序因此根本不需要知道「重命名」这个概念。它还顺带把
判定从本机配置里摘出来:`diff.renames` 无论被谁设成什么值,`--no-renames` 都压得住,
同一个 PR 在谁的机器上跑都得到同一份清单——这正是「免审是一道门,门的判据必须机械
可判」所要求的。

**为什么不改用 `git diff --name-status -M`。** 它同样给得出旧新两条路径,但它改变了
输出形状:每行前面多一个状态列,重命名那一行还把两条路径塞进同一行、用制表符分隔。
判定程序于是要先认状态列、再拆字段,凭空多出一道人可能做错的解析步骤。`--no-renames`
的输出形状与不带它时完全一致——一行一条路径,上面的判定程序一个字都不用改。同样是
拿到旧新两条路径,选不需要解析的那条路。

**实测证据**(2026-09-02,git 2.54.0.windows.1;在一个**临时仓**里把一份
`docs/design/` 下的文档 `git mv` 进 `docs/design/gskill-restructure-inventory-2026-08-31/domain-reports/`,
`diff.renames` 保持默认。下面出现的路径属于那个临时仓,不是本仓的文件;临时仓没有
remote,所以基线写成 `main` 而不是 `origin/main`——这里要看的是 `--name-only` 对
重命名的行为,与基线选哪一个 ref 无关):

```text
$ git diff --name-only main...HEAD                  # 只有新路径,旧路径丢了
docs/design/gskill-restructure-inventory-2026-08-31/domain-reports/some-decision.md

$ git diff --name-only --no-renames main...HEAD     # 旧新两条都在
docs/design/gskill-restructure-inventory-2026-08-31/domain-reports/some-decision.md
docs/design/some-decision.md

$ git diff --name-status -M main...HEAD              # 两条路径挤在一行,前面还有状态列
R100	docs/design/some-decision.md	docs/design/gskill-restructure-inventory-2026-08-31/domain-reports/some-decision.md
```

读这三段输出:第一条命令只给出一条路径,而这条路径落在枚举第 3 条之内——把它喂进
判定程序,这个 PR 会被判免审。第二条命令多出来的 `docs/design/some-decision.md` 落在
枚举之外,同一个 PR 的判定就翻转成送审。两条命令喂进同一个判定程序得出相反结论,
差别只在带不带 `--no-renames`;这就是判定命令必须带上它的全部理由。

**为什么用路径而不用内容性质。** 初版把免审集写成性质描述——「台账更新、裁决落盘、
证据归档」。交叉审席指出:一个既改决议文档又加门禁的 PR,两边都沾,两个人独立判定会
得出不同结论。免审是一道**门**,门的判据必须机械可判:同一份文件清单,任何两个人独立
判定必须得到同一个答案。路径闭集做得到,性质描述做不到。

**上面这个闭集比初版收紧,不是放宽。** 初版把「裁决落盘」整类算作免审;**现在决议文档一律
送审**。理由:决议文档的正文是后续每一份任务书的依据来源,一句措辞的松动会传导到它下游
的每一张工单;而「这次只是落盘、没有新决定」这个判断本身,恰恰是最需要第二双眼睛的
地方——自己判自己没有引入新东西,是循环论证。

**负向清单(照常送审,即使改动看起来只是记录)**,穷举常见误判:

- 任何决议文档、设计文档、规范正文(`docs/design/*.md`、`docs/development/` 下除
  两本台账之外的全部 `.md`、`docs/studio/**`、`docs/engine/**` 等);
- `AGENTS.md`、任何 `CLAUDE.md`、`.claude/` 下的任何文件;
- 任何测试、门禁脚本、CI 配置;
- 任何产线代码;
- **枚举之外的台账**——枚举的前两条是路径全等,不是「凡是叫台账的都算」。

**要扩张闭集,先改本文再执行。** 步骤是固定的:先拿**类判据**量一量提议进集的文件,
量得过,才往**枚举**里加一条,然后才按新枚举判定。先改文档再偏离,偏离才有记录;
临时判一个「这次也算记录类」等于当场把门拆了。

**判定示例**(同一份文件清单,照上面三步走,结论唯一):

| PR 的文件清单 | 判定 | 依据 |
|---|---|---|
| 只改 `docs/development/DELIVERY_LEDGER.md` | 免审 | 全部落在枚举第 1 条 |
| `docs/development/DELIVERY_LEDGER.md` + `docs/development/PROBLEM_LEDGER.md` | 免审 | 两条路径分别落在枚举第 1、2 条(30 天窗口内 21 个提交是这个形状) |
| `docs/design/gskill-restructure-inventory-2026-08-31/domain-reports/MANIFEST.md` + 同目录 `codex-review/r1-prompt.md` | 免审 | 两条路径分别落在枚举第 3、4 条 |
| `docs/design/gskill-restructure-inventory-2026-08-31/inventory-synthesis.md` | 送审 | 证据包**顶层**文件,不在枚举第 3、4 条里——设计综合定义后续要遵守的东西 |
| `docs/design/gskill-restructure-inventory-2026-08-31/adjudication-record.md` | 送审 | 同上,裁决被将来依赖,过不了类判据第二条 |
| `docs/development/DELIVERY_LEDGER.md` + `docs/design/gskill-restructure-decision-2026-08-31.md` | 送审 | 第二条路径是决议文档,在枚举外 |
| `docs/design/gskill-restructure-decision-2026-08-31.md`,只追加一行修订记录 | 送审 | 决议文档一律送审,不看改动幅度 |
| `docs/development/DELIVERY_LEDGER.md` + `apps/studio/backend/tests/docs/test_doc_code_references_exist.py` | 送审 | 门禁改动在枚举外 |
| 只改 `docs/development/PROBLEM_LEDGER.md` | 免审 | 全部落在枚举第 2 条 |
| 把 `docs/design/<某文件>.md` 移进 `docs/design/gskill-restructure-inventory-2026-08-31/domain-reports/` | 送审 | `--no-renames` 把这次改动拆成删旧路径加增新路径两条,旧路径 `docs/design/<某文件>.md` 在枚举外 |

## 六、状态与落盘纪律

1. **下面这三类产出各有唯一落点**(不是说一个程序只产出这三类):**状态**落交付台账
   [DELIVERY_LEDGER.md](DELIVERY_LEDGER.md),**裁决**落这个程序自己的决议文档,
   **证据**落这个程序的证据包目录(`docs/design/*-inventory-*/`)。
   台账是活动工作唯一可变状态源这一条本身是 AGENTS.md「Standard Documents」既有的
   规则,本文不重述它记什么。**编排层增量是这条三分**:并行期同时有多张工单在产出这
   三类东西,不预先分好落点,裁决会散进台账行、证据会散进决议正文,而后来的人无从
   判断同一件事的哪一份记录才是权威。

2. **不在聊天里存任何需要幸存的东西。** 会话上下文会被压缩或截断,聊天里的内容不保证
   下一轮还在。因此,任何需要在本轮对话之后仍然有效的东西——已批准的方案、裁决、
   关键设计决定、验收判据、证据——都必须**在发出实施指令之前**写进仓内文件。
   只存在于聊天或指令文本里的已批准设计,等于没有记录:它无法被下一个会话读到,
   也无法在事后证明当初批的是哪一版。

3. **实施席的界外发现挂 task chip,或在报告里列明,不许夹进自己的 PR。** 夹带会让
   审查失焦——审查者无法分辨哪些改动属于这张工单的验收范围。「一个任务一个 PR,不夹带
   无关重构」这条规则本身在 AGENTS.md「Coding Standards(编程规范)」的单一职责
   一条里,本文只是指明它在派单形态下的落法。

4. **协调方在等待通知的间隙,只做编排类工作(派单、写任务书与 brief、机械核验、
   开逐条修订清单),以及 §1.2 授权的那三类直写内容的落盘**,并且不与任何在跑工单
   碰同一文件。
   协调方一旦动了在跑工单领地内的文件,那张工单的 rebase 责任方就凭空多了一个不在
   任务书里的对手。

5. **「已完成」必须以第一手证据为据。** 实施席报告里的「已完成」,以其报告内的证据
   (测试输出、门禁输出、PR 号)为准;协调方向上转述时同样只认证据,没有当轮工具
   调用的成功结果就不得声称已完成。
