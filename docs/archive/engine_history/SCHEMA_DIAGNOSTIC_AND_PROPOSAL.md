# Graph Agent Schema Diagnostic & Optimization Proposal (V2.1)

**Date**: Current
**Status**: Final Diagnostic & Paradigm Shift Proposal
**Context**: An investigation into the "Schema 2.0" refactor, the loss of human-readable XML syntax, and a proposal for a hybrid resolution (V2.1) focused on extreme decoupling and PM cognitive ergonomics.

## 1. The Architectural Disconnect

### 1.1 The "V1 Reset" (Schema 2.0) Overcorrection
In late April 2026, the `graph_agent` framework underwent a massive refactor (PR #6 and #7) dubbed "Schema 2.0". To avoid fragile regex parsing of XML tags, developers moved everything into a single YAML frontmatter block validated by Pydantic.
*   **The Cost:** Human readability was destroyed. PMs were forced to write massive Anthropic prompts inside YAML multi-line strings, losing modularity.
*   **The Paradigm Anti-Pattern:** The engine stripped out declarative `subgraph` support, forcing developers to write manual Python loops (`script/orchestrator.py`) to compose skills.

## 2. The First-Principles Shift (V2.1)

A declarative Agent workflow engine is designed for PMs and Prompt Engineers. The DSL must map to their mental model, not the compiler's convenience.

**The Golden Rules of V2.1:**
1.  **YAML is strictly for Engine config** (metadata, limits, Studio properties).
2.  **XML is for Business Intent** (Prompting, Graph Topology).
3.  **JSON Schema is for IO Contracts** (No XML nesting for variables).
4.  **No explicit Context Mapping in main flow** (Rely on Global Blackboard and Studio auto-inference).
5.  **No output `target` attribute** (All outputs are inherently Artifacts).

## 3. The Ultimate Directory Blueprint

To achieve high cohesion, low coupling, and Studio tooling predictability, the folder structure is highly formalized. Every phase is an isolated directory.

```text
my-short-drama-analysis/
│
├── GRAPH.md                  # The Entrypoint: Declarative topology mapping
│
├── io/                       # Global IO Contracts
│   ├── inputs.json
│   └── outputs.json
│
└── phases/                   # All nodes, strictly isomorphic as directories
    │
    ├── 00_material_prep/     # Logic Node
    │   ├── LOGIC.md          # YAML config + <step action="..." />
    │   └── actions/          # High cohesion: python scripts only for this node
    │       └── extractors.py
    │
    ├── 01_subtask/           # Subgraph Delegate Node
    │   └── SUBGRAPH.md       # Target and mapping defined strictly in YAML properties (No XML)
    │
    └── 02_highlight_scoring/ # Agent Node
        ├── SKILL.md          # Pure DeerFlow Agent config (YAML) + XML Prompts
        ├── tools/            # Atomic LLM tools strictly for this agent
        │   └── web_search.py
        ├── examples/         # Few-shot examples
        └── references/       # Knowledge base references
```

## 4. The New Syntax Standard

### 4.1 The Main `GRAPH.md` (The Blueprint)
The main file contains ZERO prompts and ZERO nested IO tags. It is a flat, declarative topology mapping.

```markdown
---
schema_version: "2.1"
name: short-drama-analysis
type: graph
description: 短剧高光点提取。输入视频与剧本，输出高潮时间点。
---

<!-- 1. Strict IO Contracts linked to external JSON Schemas -->
<input src="io/inputs.json" />
<output src="io/outputs.json" />

<!-- 2. Flat Graph Orchestration -->
<phase id="material_prep" src="phases/00_material_prep" />
<phase id="subtask" depends_on="material_prep" src="phases/01_subtask" />
<phase id="scoring" depends_on="subtask" src="phases/02_highlight_scoring" />
```

### 4.2 The `LOGIC.md` Node
YAML controls the validator; XML handles the sequential execution flow.

```markdown
---
name: material_preparation
mode: logic
validator: script.validators.ensure_materials_ready
---

<!-- 扁平化声明，拒绝嵌套。按照从上到下的顺序同步执行。 -->
<step action="actions.parsers.extract_video_keyframes" />
<step action="actions.parsers.extract_docx_dialogues" />
```

### 4.3 The `SUBGRAPH.md` Node
Since mapping is a structural configuration (often generated by GUI drag-and-drop), it belongs purely in YAML. There is no Markdown/XML body.

```yaml
---
name: summarize_script
mode: subgraph

# PM 在右侧面板的 "Target Skill" 下拉框里选中的目标：
target_skill: script-summarizer

# PM 在面板的 "Inputs Mapping" 区通过下拉框或连线完成的配置：
data_inputs:
  document_content: raw_text
  analysis_mode: "'creative'"

# PM 在面板的 "Outputs Mapping" 区完成的配置：
data_outputs:
  summary_result: outline
---
```

## 5. Agent Loop & Cognitive Flow Optimizations (Summary)

Based on a deep-dive analysis of the engine's `finish_task` interception and ReAct lifecycle, the following structural and conceptual optimizations were identified to maximize LLM stability and engineering cleanliness:

### 5.1 The `finish_task` Visibility Problem (The `<exit_contract>` Tag)
*   **The Problem:** The compiler historically warned (`W-FINISH-TASK-VISIBILITY`) that burying the `finish_task` instruction at the end of a long list of `<steps>` causes the LLM to forget its exit condition, leading to infinite tool-calling loops.
*   **The V2.1 Solution:** Introduce a dedicated `<exit_contract>` XML tag. This physically decoucles the exit condition from the step-by-step SOP. The parser will inject this block with maximal attention weight (e.g., "⚠️ CRITICAL ACTION REQUIRED") at the very top or bottom of the system prompt to eliminate exit-hallucinations.

### 5.2 Strict Isolation of LLM Tools vs. Logic Actions
*   **The Problem:** Mixing execution scripts causes cognitive overload for PMs and breaks engine boundaries.
*   **The V2.1 Solution:** A rigid physical and conceptual barrier is enforced:
    *   **Logic Actions (`actions/*.py`)**: Machine-executed. They receive the entire global `context: dict` blackboard. They have "god mode" read/write access but zero LLM reasoning. They return nothing (`None`) but mutate the blackboard implicitly.
    *   **LLM Tools (`tools/*.py`)**: AI-executed. They are standard LangChain `StructuredTool` objects. They have severe tunnel vision, seeing only the specific type-hinted parameters the LLM passes (e.g., `def search(query: str)`). They **must** return stringified data (or JSON strings) back to the LLM's chat history. They never touch the global blackboard directly.

### 5.3 Multi-Agent Orchestration via Tooling (Actor-Critic)
*   **The Problem:** Review or auditing nodes were often modeled as separate graph phases, creating complex cyclic loops in the state machine when rejection occurred.
*   **The V2.1 Solution:** Sub-agent reviews (e.g., a "Producer" reviewing a "Writer") should be implemented as **LLM Tools**, not new nodes. The Actor LLM calls the Critic LLM via a tool (e.g., `producer_review_tool`). The Actor waits for the Critic's feedback within the *same* phase's ReAct loop, iterating until the Critic tool returns a passing grade, at which point the Actor calls `finish_task`.

### 5.4 The Middleware "Format Underworld" (md2json)
*   **The Mechanism:** The framework does not expect the LLM to output raw, complex JSON via `finish_task`, as this is highly prone to escaping errors. Instead, the LLM outputs structured Markdown.
*   **The Pipeline:** `finish_task(markdown)` -> Intercepted by Cognitive Middleware -> Converted to Python Dict via `md2json` -> Validated via Pydantic Schema.
*   **The Auto-Heal:** If Pydantic validation fails, the engine silently spawns a built-in `md-patch` sub-agent to surgically repair the format before bothering the user or retrying the main LLM.
*   **Conclusion:** This pipeline means authors should *encourage* models to generate markdown in their prompts, trusting the middleware to "hoist" it into perfect JSON/Dicts on the blackboard.
