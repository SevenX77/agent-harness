## 优化前 → 优化后 (PR-1~6 带来的质变)

优化前引擎大致处于"每个维度 2~3 分"的原型状态, 六个 PR 各补一块:

1. **PR-1 静默失败收敛** — 过去异常会被 `except Exception: pass` 这种黑洞悄悄吞掉, 出错了也看不见; 现在全部改成带原因的具名异常, 出错必然可见。(可靠性质变)
2. **PR-2 观测 + 轨迹真落盘** — 过去的执行轨迹是"假的/拼凑的", 现在是对齐真实执行生命周期的结构化日志文件 (两条 JSONL + 11 类事件), 离线排障成为可能。(可观测质变)
3. **PR-3 死码拆除 + fail-loud** — 物理删掉了一条已废弃的 persona 代码路径; 关键入口出错立即响亮报错而非默默降级。
4. **PR-4 缓存保真 + 递归防护** — 修复了缓存往返会丢字段的问题 (字段全量保真); 加了编译环检测 + 深度上限, 防死循环/栈溢出。
5. **PR-5 沙盒隔离 + 客户端生命周期** — 动态加载 skill 的 Python 模块时做快照隔离, 防跨 skill 代码串扰; 并发客户端加锁 + 统一关闭, 防资源泄漏。
6. **PR-6 治理收尾** — 删废弃 API / 死文件 / 过时文档, 清理认知负担。

## 残留真风险 (诚实定性, 都不阻塞使用)

### 1. 代码复杂度债 (维度二, 影响: 中, 证据: 高)
- ruff 圈复杂度: 30 个函数超过阈值 10, 最重的 `execute`=44 / `run`=25 / `_type_to_constraint`=24。
- mypy 严格模式 19 处报错, 其中 **15 个是第三方库缺类型标注** (装个 `types-PyYAML` 之类即解, 非引擎缺陷), **4 个是真代码问题**: 2 个是 PR-5 本轮沙盒代码引入的类型不匹配 (`module_sandbox.py:109/155`, 功能正确但类型标注需补一个 cast), 2 个是预存的跨模块私有引用。
- 这些不影响运行 (1010 条测试全绿), 是"代码健康度"层面的债。

### 2. 供应链扫描配置盲区 (维度三, 影响: 中, 证据: 高 — 主控亲测复现)
- CI 跑的依赖漏洞扫描命令带了一个 `--skip-editable` 参数, 实测它会在隔离环境里**重新解析一套全新依赖**来扫, 因此报"无漏洞"; 但**实际项目环境里真装着** idna 3.13 / starlette 1.0.0 / urllib3 2.6.3, 这 3 个包共 4 个已知漏洞 (都有现成修复版本: 升到 idna 3.15 / starlette 1.0.1 / urllib3 2.7.0 即解)。
- 即: 漏洞扫描的"门"装了, 但没对准实际锁定的版本, 给了假"通过"。建议改扫描方式 + 升 3 个传递依赖。

### 3. md_to_json 自愈能力降级 (维度一, 影响: 低, 证据: 高 — 非本轮新增)
- 过去 md_to_json 工具解析失败时会触发一个"补丁 Agent"自动修复 JSON; 这条自愈链路目前是降级的 (依赖的 md-patch skill 在新引擎下参数不兼容)。
- 但 **PR-3 已加守卫, 它不再崩溃, 只是受控地报错退出** (fail-loud), 不会导致引擎挂掉。这是 round-21 就已知并主动延后的债 (原因: 完整修复涉及面太大)。

## PR-7 教训 (审计纪律, 中性记录)

PR-7 原计划做"元数据隔离", 但经双重审计 + 主控 grep 实证发现: **这个隔离早已由 `state.py` 里的 `extra="forbid"` 机制完成**, 原审计 finding 是"没读够代码就下定性"的误判。**正确处置 = 不去修一个不存在的问题** (没有为了凑工作量硬造一个 [BREAKING] 改动)。这条教训已写进复评框架的"防误判反向验证铁律": 任何缺陷定性前必须先反向搜防御代码确认问题真存在。

由 PR-7 顺带挖出的 **2 项真实债务超出当前 charter, 待 PM 定 scope**:
- **债务 X**: 是否废除一层 legacy 兼容代码 (state.py 里新旧状态互转层, 唯一调用方已很窄);
- **债务 Y**: 是否恢复上面第 3 条的 md_to_json 自愈链路。

这两项都不是 bug 修复, 是范围决策, 等 PM 拍是否纳入。
