## 4. M4 / M6 工单复核

**M6 原守卫作废**。我写的是「`transform_applied != none` 时降级为 `url_plan_suspect`」—— openai 案的 `transform_applied` 恰恰**是** `none`（缺陷正是"该变换而没变换"），守卫直接漏过。协调方指认准确。

**订正后的 M6**（对两案都成立，判据不看变换是否发生，只看证据是否足够）：

&gt; **判则**：`404 + 包体非 provider 错误信封` ⇒ `url_plan_suspect`，**不再**判 `protocol_unsupported`。
&gt; **理由**：一个不带 provider 错误信封的 404 无法区分「我们把 URL 拼错了」与「该主机不说这个协议」。把它判成后者，是在没有正面证据的情况下替 provider 作证。
&gt; **`protocol_unsupported` 收窄为只在 provider 正面表态时给出**（三者皆已在 judge 中有实现）：`code == 405`（`judge.py:251`）／`_PROTOCOL_MISMATCH_MARKERS` 命中（`:185-200`）／`_has_foreign_protocol_error` 命中（`:211-227`）。这三种情况 provider **说了话**，判它才有依据。
&gt; **消费侧约束**：`url_plan_suspect.actionable = False` ⇒ 不进半衰期门（`llm.py:804-830`）、**不得触发任何销毁**（`llm.py:1087-1114`）。`protocol_unsupported` 同样只标记不删 —— 该销毁本就没有正当性，M0 已单独止血。

**M4 升格为两案的共同根治**（不再只是"整洁性"工单）。`UrlPlan` 单 owner 化同时消灭两个缺陷族：openai 案是"9 个 owner 里没有一个负责补版本段"，deepseek 案是"两个 owner 都认为自己该管 vendor 变换"。M6 只能防止误伤，**修不好 URL**；只有 M4 能让请求打对地方。

**M4 新增验收断言（可直接落成测试，无需真机）**：

1. `∀(endpoint, question)`：模型列表探测与生成探测由**同一个 `UrlPlan` 实例**派生 —— `wire.py:342` 与 `factory.py:69` 不得各算各的。
2. `UrlPlan(raw="https://api.openai.com", proto=openai_compatible).request_url("/chat/completions") == ".../v1/chat/completions"`（openai 案回归）
3. `UrlPlan(raw="https://api.deepseek.com", proto=anthropic_compatible).request_url(method="deepseek_chat_completions")` 必须**拒绝**（协议与 method 的 wire family 不匹配），而不是产出 `/anthropic/v1/chat/completions`（deepseek 案回归）
4. 四条测试通道（②表）对同一 `(endpoint, method)` 产出**逐字节相同**的 `request_url`（收口 C3 的 factory vs copilot 分裂）

**工单顺序不变，但优先级调整**：M4 从「M3 之后」提到与 **M0 并列的最高档** —— M0 阻止损失，M4 消除损因，二者缺一：只做 M0，用户仍然连不上 OpenAI 官方；只做 M4，其它未知的 UrlPlan 缺陷仍握有删数据的权力。
